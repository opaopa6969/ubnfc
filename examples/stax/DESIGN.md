# stax — 型定義と構造定義のできる、自己拡張型の連接言語

> issue #7 段階 1（設計文書＋文法草案）。2026-11-01 更新。
> 文法は [`stax.ubnf`](stax.ubnf)、サンプルは [`samples/`](samples/)、
> 走らせ方は [`README.md`](README.md)。

## 0. 要約

- **連接（concatenative）スタック言語**。語を並べると合成になる。Forth の系譜。
- **型と構造を宣言できる**。`type`（別名・和）、`struct`、そして語の**スタック効果**
  `( Int Int -- Int )` を型付きで宣言する。効果は stage 3 の検査器が静的に検証する。
- **制御構造は組込みではない**。`if` も `while` も `times` も、引用 `[ ... ]` を受け取る
  ただの語として言語の中で定義する（[`samples/04-prelude.stax`](samples/04-prelude.stax) が全部）。
- **構文は固定**。Forth の parsing word（入力ストリームを自分で読む語）は入れない。
  自己拡張は「構文を変える」のではなく「語彙と制御構造を増やす」方向へ寄せる（§5）。
- **文法だけで記号表が出る**。`@scopeTree` / `@declares` / `@symbolRef` を書いただけで、
  「語を定義する → 以後の参照が解決する → 未定義の語は WARNING」が動く。
  記号表のコードは 1 行も書いていない（[`samples/18-undefined-word.stax`](samples/18-undefined-word.stax)）。

## 1. 目的と非目標

### 目的

1. **UBNF の 3 つ目の実用文法**にする。P4（式言語）・JSON（データ形式）に対して、
   stax は「宣言とスコープのある手続き言語」という第 3 の形を持ち込む。
   `@scopeTree` / `@declares` / `@symbolRef` / `@catalog` / `@doc` を本気で使う最初の例である。
2. **UBNF の限界試験**。自己拡張＝構文が実行中に変わる言語を、静的 PEG と宣言的 scope で
   どこまで書けるかを測り、書けない場所を「UBNF に何を足せば書けるか」の形で残す（§5）。
3. **型の付いた連接言語を実際に成立させる**。Factor / Kitten / Cat の系譜で、
   スタック効果を宣言して静的に検査する。
4. **LSP / VSIX が文法から出ることの実証**。`--emit-lsp` で定義ジャンプ・未定義語・
   補完が出る（§8）。これが stax の「売り」であり、UBNF の売りでもある。

### 非目標（stage 1 では）

- **性能**。段階 3 は正しさ優先で AST をたどる。VM の呼出しスタックは明示的に管理する。
- **ジェネリクス**。将来案として記法を検討するだけ（§4.7）。段階 2 の必須範囲には含めない。
- **本物の Forth 互換**。`CREATE … DOES>` も `IMMEDIATE` も入れない（§5.3）。
- **モジュールシステム**。`use` は「取込む名前を明示列挙する」だけの最小形（§3.3）。
- **構造体の破壊的更新**。`!x` は構造体を差し替えた新しい値を返す。局所束縛の同型更新は認める（§4.6）。
- **例外・並行・FFI**。

## 2. 名前 — 3 案と仮決め

| 案 | 由来 | 良い点 | 悪い点 |
|---|---|---|---|
| **stax**（仮決め） | stack + syntax | 4 文字。拡張子 `.stax` がそのまま使える。ASCII 小文字。読みが一意 | 既存の同名プロダクトが世に複数ある（この repository の例題としては支障なし） |
| kumiki | 組木（釘を使わず部材が噛み合って構造になる木組み） | **組込みの制御構造を持たず、語が噛み合って制御構造になる**という性質そのもの。組木の比喩が設計に合う | 6 文字で拡張子が長い。非日本語話者に由来が伝わらない |
| catena | ラテン語で「鎖」= concatenative の語源 | 由来が正確。響きが良い | 既存の型付き連接言語 **Cat**（Christopher Diggins）と紛らわしい。この系譜の先行研究と名前で衝突するのは避けたい |

**仮決めは `stax`**。決め手は 3 つ: (a) ディレクトリ名・拡張子・grammar 名・生成クラス名の
すべてに短い ASCII 小文字がそのまま使えること、(b) stack machine であることが名前で分かること、
(c) 先行する型付き連接言語（Cat / Factor / Kitten）と字面で衝突しないこと。
kumiki は物語としては最良なので、公開する段になったら再検討の余地がある。

## 3. 構文（BNF 風の要約）

正確な定義は [`stax.ubnf`](stax.ubnf)。ここは読むための要約。

```
Program    ::= TopLevel* EOF
TopLevel   ::= UseDecl | WordDef | MacroDef | StructDef | TypeDef

UseDecl    ::= 'use' STRING '(' IDENT* ')' ';'
WordDef    ::= ':' IDENT Effect Term* ';'
MacroDef   ::= 'macro' IDENT Effect Term* ';'
StructDef  ::= 'struct' IDENT '{' FieldDecl* '}'
FieldDecl  ::= IDENT ':' TypeRef
TypeDef    ::= 'type' IDENT '=' ( SumBody | AliasBody ) ';'
SumBody    ::= '|' IDENT ( '|' IDENT )*
AliasBody  ::= TypeRef

Effect     ::= '(' TypeRef* '--' TypeRef* ')'
TypeRef    ::= QuotType | BuiltinType | IDENT
QuotType   ::= '[' TypeRef* '--' TypeRef* ']'
BuiltinType::= 'Int' | 'Float' | 'Bool' | 'Str'

Term       ::= Quotation | NumLit | StrLit | BoolLit
             | LetBind | FieldGet | FieldSet | Prim | WordRef
Quotation  ::= '[' Term* ']'
LetBind    ::= 'let' IDENT
FieldGet   ::= '.' IDENT
FieldSet   ::= '!' IDENT
WordRef    ::= IDENT
```

コメントは `//` と `/* */`（`@whitespace: javaStyle`）。

### 3.1 なぜこの形か — PEG に素直な 3 つの決定

1. **和には先頭の `|` を必ず書く**（`type C = | Red | Green ;`）。
   これで「別名か和か」が 1 token で決まり、順序付き選択が後戻りしない。
   先頭 `|` を省略可能にすると、`TypeRef` と最初の枝がどちらも `IDENT` で構造同一になり、
   `W-CHOICE-UNREACHABLE` が出る（＝どちらかの候補が黙って死ぬ）。
2. **利用者定義の語は識別子だけ**（`[A-Za-z_][A-Za-z0-9_]*`）。記号だけの語
   （`+` `<>` `>r`）は**組込みの固定語彙**に限る。
   こうすると組込み語を文法にリテラルで並べられ、UBNF v2 の**語境界**（D-040）が
   「`dup` が `duplicate` の頭を横取りしない」を保証してくれる。
   本物の Forth は任意の記号列を語にできるが、それをやると組込み語をリテラルで書けなくなり、
   語彙を実行時に注入する口（§5.4）が無い現状では未定義語の警告がすべての語に出てしまう。
   **これは UBNF の形に合わせた最大の妥協**であり、§5.4 で外し方を書く。
3. **`.` はフィールドアクセス専用**。Forth の `.`（表示）は `print` に改名した。
   `.` を語に使えるようにすると `p.x` が 1 語に見えてしまい、フィールド参照を
   `@symbolRef` で引けなくなる。

### 3.2 語の定義と「定義してから使う」

```
: square ( Int -- Int ) dup * ;
```

`WordDef` は `@scopeTree(mode=lexical)` と `@declares(symbol=name)` の両方を持つ。
UBNF の宣言登録は**規則を抜けたあとに親スコープへ**行われるので、

- 語名は**ファイルスコープ**に登録される（外から見える）
- **本体からは自分の名前が見えない**

という 2 つが同時に出る。後者は偶然ではなく、**Forth の smudge bit と同じ意味**である
（Forth も `;` を実行するまで定義中の語を辞書から隠す）。だから自己再帰は Forth と同じく
専用語 `recurse` で書く。**言語の意味論と UBNF の scope 意味論が一致した数少ない箇所**で、
stax がこの形を採った理由の一つでもある。

前方参照（後ろで定義された語を先に使う）も同じ理由で解決しない。
[`samples/18-undefined-word.stax`](samples/18-undefined-word.stax) がその 2 例を持っている。

### 3.3 `use` — 取込む名前を明示列挙する

```
use "16-veclib.stax" ( Vec2 vx vy vec_add vec_len_sq ) ;
```

静的 PEG は 1 ファイルしか見ない。そこで **取込む名前をソースに書かせる**。
列挙した名前は `@declares` でこのファイルのスコープに入るので、
**相手のファイルを読まずに参照が解決する**。相手に本当にその語があるかは stage 3 で見る。

Modula-2 の `FROM M IMPORT x, y` や Haskell の明示 import リストと同じ発想で、
「文法だけで完結させる」という制約から素直に出てきた設計である。
`import *` 相当を入れない理由もここにある（入れた瞬間に文法だけでは解決できなくなる）。

## 4. 型システム

### 4.1 型の語彙

| 種別 | 書き方 | 備考 |
|---|---|---|
| 組込み | `Int` `Float` `Bool` `Str` | 実行系が供給する固定語彙。文法にリテラルで書いてある |
| 構造体 | `struct Point { x: Int y: Int }` | **名前的**（nominal）。同じ形でも名前が違えば別の型 |
| 別名 | `type Meters = Int ;` | **透過**（transparent）。`Meters` と `Int` は同じ型。不透明な新型は将来案 |
| 和 / 列挙 | `type Color = \| Red \| Green \| Blue ;` | 枝は引数を取らない。引数付きの枝は将来案 |
| 引用の型 | `[ Int -- Int ]` | 「Int を 1 つ取って Int を 1 つ返す引用」 |

段階 3 の `+` / `-` / `*` / `/` / `neg` は同じ型の `Int` または `Float` を取る。
暗黙の数値変換はしない。`mod` と順序比較は `Int` 専用、Float の結果は有限でなければならない。

### 4.2 スタック効果の読み方

```
( I1 I2 ... In -- O1 O2 ... Om )
```

- 入力・出力とも**左から右へ、右端が最上段**。`( Int Str -- Bool )` は
  「最上段が `Str`、その下が `Int`」を取る。
- `( -- )` は何も取らず何も残さない。
- 効果は**語の宣言の一部**であって推論結果ではない。宣言と本体が合うかを検査する。

### 4.3 検査の規則（段階 3 で実装済み）

状態はスタックの**型の列** `S`（左が底）。項 `t` の効果を `(p -- q)` とすると:

> **合成則**: 現在の状態が `S` で、`S = S' ++ p` と書けるとき、`t` を適用した後の状態は
> `S' ++ q`。`S = S' ++ p` と書けなければ**型エラー**（深さ不足 or 型不一致）。

語 `w` の本体 `t1 … tk` は、`w` の宣言効果を `(P -- Q)` として

> 状態 `P` から始めて `t1 … tk` を順に適用し、**最終状態がちょうど `Q` に等しい**こと。
> 余っても足りなくても型エラー（[`samples/20-effect-mismatch.stax`](samples/20-effect-mismatch.stax)）。

各項の効果:

| 項 | 効果 |
|---|---|
| `42` | `( -- Int )`。字句に `.` か `e` があれば `( -- Float )` |
| `"x"` | `( -- Str )` |
| `true` / `false` | `( -- Bool )` |
| `[ body ]` | `body` の効果が `(p -- q)` のとき `( -- [ p -- q ] )` |
| `let x` | 最上段 `T` を取り出し、この定義の枠に `x : T` を記録する。`( T -- )` |
| `x`（`let` した名前） | `( -- T )` |
| `w`（定義済みの語） | `w` の宣言効果 |
| `V`（和の枝、`type C = \| V …`） | `( -- C )` |
| `Name`（struct 名） | `( T1 … Tn -- Name )`。`Ti` はフィールド宣言順 |
| `.f` | `( S -- T )`。`S` は `f : T` を持つ struct |
| `!f` | `( S T -- S )` |
| `recurse` | いま定義中の語の宣言効果 |

`call` と `choose` は**語の signature では書けない**（ジェネリクスが要る）ので、
検査器の規則として持つ:

- `call`: 状態が `S ++ [ [ p -- q ] ]` のとき、`S = S' ++ p` を要求し `S' ++ q` にする。
- `choose`: 状態が `S ++ [ Bool, [p -- q], [p -- q] ]`（**2 つの引用の効果が一致**）のとき
  `S ++ [ [p -- q] ]` にする。

これは Factor の `call(` や Kitten の行多相に相当する部分を、
「ジェネリクスが入るまでの間、検査器の特別則として持つ」形に落としたものである。
将来、行変数（row variable）を入れたら、この 2 つは普通の signature に戻る。

`=` / `<>` は**等価比較のできる型**（`Int` `Float` `Bool` `Str` と和の型）に対して
`( T T -- Bool )`。`<` `<=` `>` `>=` は `( Int Int -- Bool )`。

### 4.4 何を静的に検査し、何を先送りするか

| いつ | 何を | どこで |
|---|---|---|
| **stage 1 — 文法だけ** | 構文。未定義の語・型・フィールド名（WARNING）。定義順（前方参照は未解決） | `@scopeTree` / `@declares` / `@symbolRef` |
| **stage 3 — 型検査器** | スタック効果の整合、リテラルの型、struct の構築とフィールドの型、`let` の型、引用の効果、和の枝、`use` の相手に本当に語があるか、`.f` がどの struct の `f` か | Rust の checker |
| **実行時** | 0 除算、再帰の停止、文字列の添字範囲、`Float` の精度 | Rust のインタプリタ |

**`.f` の解決は stage 1 と stage 3 で役割が割れている**。文法は struct のフィールドを
**ファイルスコープの宣言**として登録するので、「`.x` という名前の宣言があるか」までは
文法だけで言える。しかし「どの struct の `x` か」は最上段の型が決まらないと言えないので
型検査器の仕事になる。同名フィールドを複数の struct が持つときは、型から一意に決まれば
通し、決まらなければエラーにする。

### 4.5 struct とフィールド

```
struct Point { x: Int y: Int }

: origin ( -- Point ) 0 0 Point ;
: shift_x ( Point Int -- Point ) let dx dup .x dx + !x ;
```

- struct 名はそのまま**コンストラクタの語**。フィールド宣言順にスタックから取る。
- `.f` は取得、`!f` は「そのフィールドを差し替えた新しい値」を返す（破壊しない）。

### 4.6 局所束縛

`let x` は最上段を取り出して、いま定義中の語の枠に `x` という名前で束縛する。
同じ名前に対する 2 度目の `let x` は**同じ型でなければならない**（枠の中では単型）。
引用は外側の定義の同一呼出し枠を共有し、引用内の `let x` で既存の `x` を同じ型の値へ更新する。
引用内で初めて導入する名前は、その引用の実行前には使えない。再帰呼出しは新しい枠を作る。
これにより FizzBuzz の `i` と while の `n` の更新が次の反復に見える（[`samples/12-while.stax`](samples/12-while.stax) の `n`）。
束縛は `WordDef` の `@scopeTree` が作ったスコープに入るので、定義の外へは漏れない。

### 4.7 ジェネリクス（将来案）— 構文の場所

候補の記法は次の 3 箇所。現行の文法は受理しない。段階 2 では境界の検証を先に行い、
ジェネリクス自体を追加する場合は別途受け入れ条件を決める。

```
: swap_pair <A B> ( A B -- B A ) swap ;     // 語の型パラメータ: 名前と '(' の間
struct Box <T> { value: T }                 // struct の型パラメータ
type Pair <A> = ... ;                       // 型の型パラメータ
List<Int>                                   // 型の位置での実引数
```

- `<` `>` は組込み語だが、現れるのは **項の位置**だけである。型パラメータが現れる
  「名前の直後・`(` の前」と「型の位置」には項が来られないので、字面が同じでも曖昧にならない。
- **UBNF v2 のパラメータ化ルール `Name<P>`（D-043）とは層が違う**。あちらは*文法*の雛形、
  こちらは *stax の型*。同じ字面だが混同しないこと。
- 行変数（row variable）を入れたら §4.3 の `call` / `choose` の特別則は普通の signature に戻る。
  そのときの綴りは `( ..a [ ..a -- ..b ] -- ..b )` を第 1 候補とする（Kitten 方式）。

## 5. 自己拡張の方式と、その境界

### 5.1 問題と評価対象

Forth の parsing word は入力領域を読み、辞書の状態と解釈 / コンパイル状態に従って動く。
`(`、`."`、`CREATE … DOES>` を、stax の固定構文と引用 macro でどこまで代替できるかを調べる。

固定 PEG でも一般の語列を AST にすることはでき、その上で言語側の VM が辞書を作る設計も可能。
extern scanner が宣言効果を返す仕組みも既にある。「固定 PEG では原理的に書けない」とは断定しない。
対象は、現行 stax の macro / Loader と、生成 parser が直接返す宣言・typed AST の契約である。
段階5の実測・標準への参照・v3 の提案は
[境界レポート](../../docs/reports/2026-11-01-stax-boundaries.md) にまとめた。

### 5.2 第 1 案（stage 1 で採る）— 引用 `[ ... ]` ＋ macro

Factor の流儀。**構文は固定し、拡張の力を語の側に移す**。

- 引用 `[ ... ]` は「まだ実行しない語の並び」で、値として積める。
- 制御構造は引用を受け取る**ただの語**として定義する。
  組込みは `choose`（真偽で引用を選ぶ）・`call`（引用を実行する）・`recurse` の 3 つだけで、
  `if_else` / `if` / `while` / `times` はすべて言語の中で書ける
  （[`samples/04-prelude.stax`](samples/04-prelude.stax) が全文）。
- `macro` は「引用を受け取って引用を返す、コンパイル時に走る語」。
  構文糖を利用者が足せる（[`samples/14-macro.stax`](samples/14-macro.stax) の `unless`）。

**これで届く範囲**: 制御構造・構文糖・DSL 風の語彙。届かない範囲は §5.3。
**なぜこれを採るか**: 構文が固定なので、(a) 文法が 1 本で済み、(b) LSP が文法から自動で出て、
(c) 型検査がソースだけで完結する。issue #7 の「UBNF の限界試験」としても、
**限界の手前で何が作れるかを最大化した形**が先に要る。

### 5.3 Forth の parsing word 3例の分類（段階5の実測）

| Forth の語 | stax の分類 | 実測と意味保存の範囲 |
|---|---|---|
| `( … )` | 固定構文で用途を代替 | Effect と `/* */` 注釈で値7・5を表示。本体の括弧コメントは構文拒否。同じ入力列や語としての再定義は保持しない |
| `."` | quotation + macro で代替 | `say` macro に文字列を返す引用を渡し、返された引用の call で hello を表示。入力領域を読む力は保持せず、コンパイル時 I/O は拒否 |
| `CREATE … DOES>` | 現行 stax の macro 契約では不可能 | macro が Term の代わりに TopLevel 定義を返す形は構文拒否。一般の名前の並びの受理だけでは宣言は作らない。固定 `: answer ( -- Int ) 42 ;` は動く |

最後の境界は現行 stax の言語側 API のもの。UBNF の extern に専用処理を実装すること、
語列 AST の後で意味処理をすることまで禁止する意味ではない。
実行可能な11ケースと両 backend の追加再現は `boundaries/`、報告は上記リンク。
Forth 実装自体はこのマシンで実行しておらず、標準上の期待と stax の観測を分ける。

### 5.4 X1〜X3 の再評価と最小 v3 提案

段階1の下書きは仮説であり、現行機能の欠落や実装承認ではない。
段階5では次のように見直した。`@vocabulary` や `volatile` は実装済みの構文ではない。

| 論点 | 現行機能で確認したこと | 判断 |
|---|---|---|
| X1: 外部語彙の scope 供給 | 不変 snapshot の名前を extern の Declare 効果で供給できた。失敗した候補からは巻き戻る。両 backend で6条件一致 | 単純な名前供給のための front 追加は不要。出所付きの初期語彙を共通 API にする案だけを v3 の最小提案として残す |
| X2: 解析中に変わる認識語彙 | scope の版付き memo は既存。保証の無い extern と祖先は memo 不可、Rust の literal cache は extern を含まない | 外部可変状態の rollback と依存版、診断再解析・最適化証明・将来の増分無効化は別の契約。未実装として扱い、今回採らない |
| X3: 語彙依存の構文形 | 固定 PEG で一般の語列を全文受理できたが、生成宣言は空。新しい語の実行意味と、生成時に固定した AST 型は別 | 固定 AST と言語側の意味処理で分ける。任意意味述語や実行中の IR 書換えは採らない |

X1 の現行再現は宣言位置0を仮に使うため、外部ファイルへの正しい定義ジャンプにはならない。
初期語彙の出所・種別・URI / 範囲、snapshot の同一性を両言語で扱う共通契約は提案段階。
診断だけが変わる場合でも、公開結果・memo の観測・出所の扱いは変わり得るので、
「契約への影響無し」という段階1の評価は採らない。

今回 stax に front の追加実装は必要ない。最小提案の設計条件と将来の受け入れ条件は
境界レポート §7 に記載した。実装の要求が生じた時点で別 issue にし、今回の成功には数えない。
グローバルな設計決定 D 行へ未採用案を追加しない。

### 5.5 段階5で検証した境界

1. コンパイル時の引用変換と実行時の表示を分離できた。コンパイル時 I/O は拒否した。
2. macro 内の TopLevel 定義と文字列の名前化は現行 stax では拒否。固定 WordDef は実行できた。
3. 一般語列4件は両 backend で受理・AST 一致、宣言ゼロ。Forth の実行成功には数えない。
4. 不変な外部語彙6条件は、両 backend・memo 切替・Rust 字句 cache 切替の36回で観測一致。
   rollback を実証したが、解析中に変わる辞書や外部 URI の出所 API は実装していない。
5. 現在の buffer reuse / 全文再解析と、編集をまたぐ増分再利用は別。X2 / X3 の成功件数は0。

## 6. 実行モデル

Rust の小さなインタプリタ（stage 3）。JVM は要らない。

```
ソース
  → ubnfc の生成した Rust パーサ（typed AST）      ← stage 1 で出来ている
  → 宣言効果と macro 引数の型検査                    ← §4.3
  → macro 展開（コンパイル時の引用変換）
  → 展開した本体のスタック効果を再検査
  → 評価（スタック機械）
```

- 値は `Int`（i64）/ `Float`（f64）/ `Bool` / `Str` / struct / 列挙 / 引用。
- 引用は「AST の断片＋定義の枠への参照」。`call` で実行する。
- `recurse` は引用を定義した語を呼び直す。引用を別の語で `call` しても、検査時と同じ語の効果を使う。
- 実行ファイルの入口は語 `main`。`( -- )` でなければならない。ライブラリは `main` を持たなくてよい。
- `use` は明示された名前だけを読み込む。実在・循環・欠落の検査は段階 3 で行う。
- macro の引数は直前の引用リテラルに制限し、展開結果を再度型検査する（§11）。
  展開・型検査・実行は段階3で実装済み。段階5で、Term 引用の変換と動的な TopLevel 宣言の違いも実測した。
  `unless` の効果は `( [ -- ] -- [ Bool -- ] )`。受け取る本体の引用は空入力だが、
  返す引用は実行時の Bool を消費するため、両者を同じ効果として扱わない。
- 型検査を通ったプログラムは「スタックの深さと型」については実行時検査が要らない。
  0 除算・整数 overflow・再帰の資源上限など、値や資源に依存する失敗は実行時に診断する。

## 7. この文法が使っている UBNF の機能

| 機能 | 書いた場所 | なぜ要るか |
|---|---|---|
| `@ubnf: 2` | 冒頭 | 以下の v2 既定を有効にする |
| **語境界**（D-040、`@literalBoundary: word`） | 組込み語 29 本と組込み型 4 本のリテラル | `dup` が `duplicate` を、`Int` が `Integer` を横取りしないこと。**「組込み語をリテラルで並べ、利用者定義語を IDENTIFIER にする」という §3.1 の設計全体がこれに乗っている**。v1 の既定（`none`）ではこの文法は成立しない |
| **中立な token 語彙**（D-041） | `IDENTIFIER` / `NUMBER` / `DOUBLE_QUOTED` / `END_OF_INPUT` | host のクラス名（`org.unlaxer.…`）を書かずに済む。extern token は 1 つも要らなかった |
| **到達不能候補の検査**（D-037、`W-CHOICE-*`） | 検証時 | 組込み語 29 本を 1 つの順序付き選択に並べている。**順番を間違えると候補が黙って死ぬ**ので、`--strict` で警告ゼロを CI の条件にしている |
| `@scopeTree(mode=lexical)` | `Program` / `WordDef` / `MacroDef` | ファイルスコープと語ごとのスコープ。`let` の束縛が定義の外へ漏れないこと |
| `@declares(symbol=…)` | 8 箇所（語・macro・struct・struct のフィールド・型・和の枝・取込み名・`let`） | 「定義」の 7 種類すべて。記号表のコードは 1 行も書いていない |
| `@symbolRef(name=…)`（D-046 の v2 綴り） | 4 箇所（語の参照・型の参照・`.f` / `!f`） | 未定義参照が WARNING で出る。旧綴りの `@backref` は「文法中に `@scopeTree` があるか」という非局所判定で意味が変わるので使わない |
| `@mapping(...)` | 27 箇所（**AST を作るすべての規則**） | typed AST。選択だけの規則（`TopLevel` / `Term` / `TypeRef`）にも付けて、sealed interface + record の和型を出している |
| `@catalog(context=…)` | 6 箇所（組込み語・組込み型・利用者の語・型・フィールド 2 種） | IR の静的カタログ。context の区分はあるが、現行 LSP の記号補完がこれを使って厳密に絞るわけではない（§12） |
| `@doc('…')` | 17 箇所（主要な規則すべて） | `--emit-lsp` の hover（D-062）。§8 |

**使わなかったもの**と、その理由:

| | なぜ使わないか |
|---|---|
| **左再帰**（D-039） | 連接言語に演算子の優先順位が無い。`3 4 +` は並びであって式木ではないので、優先順位塔そのものが存在しない。**UBNF v2 の目玉機能が 1 度も要らない文法**という意味で、P4 / JSON と性格が違う 3 本目の例になっている |
| **パラメータ化ルール**（D-043） | 同じ形の繰り返しが無い。P4 のような「型ごとに 4 本ずつ同じ規則」が stax には出てこない |
| **code point クラス**（D-063） | 文字列は組込み token（`DOUBLE_QUOTED`）に任せている |
| `@leftAssoc` / `@precedence` | 同上（演算子が無い） |
| **`@recovery`** | **置ける場所が無かった**。詳細は次項 |

### 7.1 `@recovery` を外した理由（実測）

> **追記（#71 / D-073）**: この形は `ubnfc validate` が `W-RECOVERY-IN-CHOICE` で警告する
> （`--strict` で exit 5）。回復を置くなら選択を含む規則そのもの（`@recovery TopLevel ::= …`）にする。

最初 `WordDef` に `@recovery(sync=';')` を付けたが、**正しいプログラムが壊れた**。

`TopLevel ::= UseDecl | WordDef | MacroDef | StructDef | TypeDef` の順序付き選択では、
`struct Point { … }` を読むときにも **まず `WordDef` が試されて失敗する**。
`@recovery` はその失敗を回復として拾ってしまうので、`struct` で始まるファイルが
「`WordDef` の回復」として受理され、宣言が 1 つもスコープに入らなくなった（実測）。
さらに、わざと壊した [`rejects/17-bad-syntax.stax`](rejects/17-bad-syntax.stax) が
**受理されてしまった**。

> **一般則**: `@recovery` は、**順序付き選択の最後でない候補から到達する規則には置けない**。
> その規則の失敗は「誤りである」ではなく「次の候補を試せ」の意味だからである。

stax の本番文法では `@recovery` を使わない。段階4では選択全体の TopLevel に置く案を
評価し、正常入力を保って後続宣言へ回復できることを既存 front で確認した。
一方、生成 LSP に回復領域のエラー診断が無いため、まだ本番へは採用しない（§12）。
段階1の報告 `docs/reports/2026-09-24-stax-stage1.md` は当時の実測と仮説として読む。

## 8. 副産物 — LSP / VSIX は文法から出る

`ubnfc-lsp --emit-lsp` は IR だけから LSP サーバを出す（opt-in。root `pom.xml` の Maven profile
`lsp`、D-060 / D-062）。stax はそのために書き足すものが無い。**すでに書いた注釈がそのまま機能になる**:

| 注釈 | LSP で何になるか |
|---|---|
| `@declares` + `@symbolRef` | **定義ジャンプ**（語・型・フィールド・取込み名・局所束縛）と**未定義語の波線** |
| `@scopeTree` | parser の局所 scope と未定義参照診断。現行 LSP の補完には他の語の局所名も残る |
| `@catalog(context=…)` | IR の静的メタデータ。現行補完は期待終端と文書内宣言を使い、型/本体位置で差があるが、フィールド専用候補は保証しない |
| `@doc('…')` | **hover の説明文**（生成される `Meta.RULE_DOC`） |

つまり「型定義のできる Forth」を作ると、**定義ジャンプと補完と hover が付いてくる**。
これが issue #7 の「副産物」である。段階4で実証した範囲と残る条件は §12。

## 10. 段階 2 の仕様由来 corpus（#12）

[`corpus/cases.json`](corpus/cases.json) は各入力と仕様の根拠、構文の受理/拒否、
型検査とは分けた期待分類、注目する AST の型・値・ソース断片、警告の名前と位置を持つ。
[`scripts/corpus.py`](scripts/corpus.py) はサンプルと同じ生成パーサを使い、両 backend の
canonical AST 全体の一致と、手書きした仕様期待値をそれぞれ検査する。
AST の span は半開区間で末尾 trivia を含む。ソース断片から Unicode code point 位置を算出する。
同じ断片が複数あるときは先頭、`occurrence: last` なら最後を明示的に選ぶ。
全受理入力で非空 Program AST、全拒否入力で syntax 診断を要求する。

予約語/primitive/型の接頭辞、符号付き数値・小数・指数とフィールドの境界、長い比較記号、
空/入れ子 quotation と引用型、前方/自己参照、局所束縛の宣言順と漏れ、
同名フィールド、明示 import、コメント/文字列を扱う。型エラーを構文拒否として数えない。
`cargo test -p ubnfc-harness --test stax` を通じ native CI で必須実行する。

最小の非対応例:

- `: >> ( Int -- Int ) dup ;` は現行 stax の IDENT 制約により拒否。
  固定された記号列を受理するだけなら文法の変更で済むため、front の欠落とは扱わない。
- `42 constant answer` は現行の固定した最上位構文では拒否。
  `constant` の意味に応じ `answer` を宣言として解析するには語彙依存の契約（§5.4 X3）が要る。
  単なる一般の語列の受理とは異なる。front は変更せず #16 で評価する。
- `struct Box <T> { value: T }` と `type Option = | Some Int | None ;` は将来の stax 構文。
  ジェネリクス/引数付き和の未実装であり、現行 UBNF がその固定構文を書けないという根拠にはしない。
- `use "absent.stax" ( exported ) ; : main ( -- ) exported ;` は名前が解決しても
  ファイルが存在するとは限らない。実在検査は #14、ファイル間の定義ジャンプは #15 の境界である。
- 同名 struct フィールドは名前の存在だけ検査される。型から所有宣言を決めるのは #14 の責任。

判断: 本段階では文法と front/backend を変更せず、既存契約を仕様から検証する。
これにより並行作業への干渉を避け、検証追加だけの PR として可逆性を保つ。

## 11. 段階 3 の実装契約（#14）

実装は [`interpreter/`](interpreter/)。build.rs は既存の front / Rust backend の公開 API で
文法を strict 検証・生成し、Cargo の OUT_DIR へ保存する。checker と VM は生成された
`Ast::g_StaxAST_2e_*` の型付きレコードを直接読む。JSON driver や JVM は起動しない。
workspace の `cargo test` が実行コマンドの終了コード・診断・20 本の期待結果を必須検証する。

### 検査と束縛

- 語と型は宣言順に登録する。語は定義時の辞書 snapshot を持ち、前方参照と自名の直接参照は拒否する。
- 透過別名は参照先の型、struct と列挙はモジュールの canonical path と宣言名による名前的な型。
  同名フィールドも最上段の struct 型から決める。`!f` は新しい値を作り、複製した元の値を変えない。
- 引用の不足入力を型変数として推論し、`call` / `choose` とスタック操作を特別則で合成する。
  空引用はスタック接頭辞を保存する恒等操作なので、`[ Int -- Int ]` として渡せる。
  引用値の代入は、値側の必要入力が受取側の要求より少なく、接頭辞を保存する向きにだけ限定する。
  逆向きに `[ Int -- Int ]` を `[ -- ]` として渡すことは拒否する。`let` 更新と field 更新でも同じ規則を使う。
  `choose` の結果は両方の枝が必要とする共通の入力を保持する。
  `false [ ] [ 1 + ] choose call` を空スタックで実行する語は、実行前に Int 不足で拒否される。
  型の分からない引用に対する `call` の完全な高階・行多相推論は提供しない。
  型変数の結合は rank を使い、親の探索には Rust の再帰を使わない。別名を経由した引用型にも深さ上限を適用する。
- 引用が作られる前に束縛済みの局所名だけを参照できる。既存名への `let` は同じ型の更新で、
  同じ呼出し枠を共有する。再帰や通常の語呼出しは新しい枠を作る。
  引用内で初めて導入する名前はその引用内だけで静的に利用でき、引用の外では参照できない。
  分岐や `call` の実行を追って新しい束縛を外へ流す解析はしない。実行前の未束縛を防ぐための保守的な規則。
  可視性とは別に、引用内の新規名も含め語全体で1つの束縛型を持つ。別の引用から同名を異なる型へ更新することは拒否する。
- 予約語・primitive 名の再定義と局所束縛、macro 名を隠す局所束縛、同じ名前の再宣言は拒否する。
  同名フィールドの metadata は共有できる。
- `use` は列挙名の実在を確認し、その名前だけを登録する。読み込んだ語の内部参照は元ファイルの辞書を保つ。
  canonical path で循環と欠落を検査する。ライブラリは `main` 不要、存在する `main` は必ず `( -- )`。

### macro の段と最小範囲

1. 元の本体を検査し、macro の宣言効果と実引数の引用効果を照合する。
2. 呼出し直前の引用リテラルを入力として、macro 本体をコンパイル時の VM で実行する。
   入力は引用だけ、出力は引用 1 個。`print` / `newline` をこの段で実行すると失敗する。
   返す引用内の表示は、展開後の実行時に走る。
3. macro の局所名が捕捉した引用を AST に代入し、残る名前は呼出し側の辞書・局所束縛で解決する。
   hygiene は提供しない。捕捉名を返す引用内で再束縛する形、引用以外の捕捉値、
   実行時に作った値や局所変数からの macro 引数は診断付きで拒否する。
4. 展開した本体を再検査し、VM は展開済み AST を実行する。`--expand` で語ごとの展開後 AST を確認できる。

この範囲で `14-macro.stax` の `unless` が動き、呼出し側で束縛した値も引用から参照できる。
任意の実行時辞書変更や parsing word の実装とは区別する。これらは #16 の境界材料である。

### 数値・失敗・資源上限

Int は i64 の checked 演算。0 除算と overflow は終了コード 1 の診断になる。
除算は 0 方向へ丸め、`mod` は Rust の剰余（被除数側の符号）。Float の 0 除算・非有限値も拒否する。
文字列の escape は `\n` / `\r` / `\t` / `\0` / `\"` / `\\`、長さは Unicode code point 数。
未対応の escape は型検査時に拒否する。診断位置も code point 単位。
macro 展開後の span は元 AST の値を保持し、展開元と呼出し先を対応させる source map は提供しない。

| 対象 | 上限 |
|---|---:|
| 実行ステップ | 既定 100,000、`--max-steps` は 1〜1,000,000 |
| VM の同時呼出し（引用を含む） | 既定 1,024、`--max-depth` は 1〜4,096 |
| 累積呼出し枠 / 値スタック | 4,096 / 65,536 |
| 文字列の累積割当 / 単一 concat 結果・stdout | 8 MiB / 1 MiB |
| 引用 AST の累積割当 / struct の累積 field slot | 100,000 / 1,000,000 |
| ソース 1 本 / 全ソース / モジュール数 | 1 MiB / 8 MiB / 64 |
| 全宣言 / 1 モジュールの名前 / 語 / struct field | 2,048 / 2,048 / 256 / 256 |
| 宣言名・局所名・field 名 / 辞書 snapshot の累積要素 | 256 byte / 100,000 |
| 型検査（語ごと）・macro 展開（全体）のノード / 引用の深さ | 100,000 / 64 |
| 型検査の操作（語ごと） / 引用型の深さ | 1,000,000 / 64 |
| macro VM のステップ / 同時呼出し | 10,000 / 64 |

VM は Rust の再帰呼出しで語を評価せず、明示的な作業スタックを持つ。引用の枠は arena の ID で保持し、
束縛と引用の循環参照を Rc の循環にしない。失敗時には途中までの stdout を公開しない。
成功は終了コード 0、構文・型・実行時エラーと資源上限は 1、コマンド引数の誤りは 2。

`samples/expected.json` の全 20 本に stdout または理由付きの型エラーを固定した。
ライブラリ 04 / 16 は自身の `--check` と利用側 05 / 15 の出力を検証する。
`cargo test -p ubnfc-stax` は上記の規則、200 回の有限ループ、Java の無い PATH での実行、
既定上限での非停止と指定上限による終了も検証する。

## 12. 段階4の生成 LSP・VSIX（#15）

生成・build・stdio 起動・VSIX 作成と実機確認の手順は
[`vscode/README.md`](vscode/README.md)。文法・front・両 backend・pin は変更せず、
既存 `--emit-lsp` と `--emit-tmlanguage` を使う。生成前後の parser byte 不変を検証し、
文法・IR・全生成ファイルの hash 対応を `generation.json` に記録する。
通常 workspace CI は `stax_lsp` テストから protocol・TextMate・回復配置の golden を照合する。

語・型・局所束縛・明示 import・フィールドの定義ジャンプ、未定義語の診断、3種の
`@doc` hover、型/本体位置での補完の違いを headless で実証した。`😀` と同じ行の
宣言の UTF-16 range、壊れた全文を修正した後の復帰、close 後の索引破棄も検証する。

parser の scope 規則と、文書内の綴り単位で記号を集める現行 LSP 索引の精度を区別する。
同名局所束縛の複数候補、他の語の局所名が残る補完は #49 に切り出した。
`use` は同じ文書の ImportName までのジャンプであり、実ファイル解決ではない。
同名 struct フィールドを型から選ぶことも文法注釈だけでは提供しない。

回復の評価用コピーでは TopLevel 案が正常入力を保ち、後続宣言を回復することを確認した。
しかし生成 LSP の回復診断が空となるため本番文法では採用しない。
不完全入力の正常前半の索引保持と合わせて #50 に切り出し、必要な契約と最小再現を記録した。
このマシンには実機 VS Code が無い（`which code` は exit 1）ため、実機確認のみ #48 に残す。
VSIX のローカル生成・内容照合は成功しており、公開・配布範囲は変更しない。
