# stax — 型定義と構造定義のできる、自己拡張型の連接言語

> issue #66 stage 1（設計文書＋文法草案）。2026-09-24。
> 文法は [`stax.ubnf`](stax.ubnf)、サンプルは [`samples/`](samples/)、
> 走らせ方は [`README.md`](README.md)。

## 0. 要約

- **連接（concatenative）スタック言語**。語を並べると合成になる。Forth の系譜。
- **型と構造を宣言できる**。`type`（別名・和）、`struct`、そして語の**スタック効果**
  `( Int Int -- Int )` を型付きで宣言する。効果は stage 3 の検査器が静的に検証する。
- **制御構造は組込みではない**。`if` も `while` も `times` も、引用 `[ ... ]` を受け取る
  ただの語として言語の中で定義する（[`samples/04-prelude.stax`](samples/04-prelude.stax) が全部）。
- **構文は固定**。Forth の parsing word（入力ストリームを自分で読む語）は入れない。
  自己拡張は「構文を変える」のではなく「語彙と制御構造を増やす」方向へ寄せる（§5）。
- **文法だけで記号表が出る**。`@scopeTree` / `@declares` / `@symbolRef` を書いただけで、
  「語を定義する → 以後の参照が解決する → 未定義の語は WARNING」が動く。
  記号表のコードは 1 行も書いていない（[`samples/18-undefined-word.stax`](samples/18-undefined-word.stax)）。

## 1. 目的と非目標

### 目的

1. **UBNF の 3 つ目の実用文法**にする。P4（式言語）・JSON（データ形式）に対して、
   stax は「宣言とスコープのある手続き言語」という第 3 の形を持ち込む。
   `@scopeTree` / `@declares` / `@symbolRef` / `@catalog` / `@doc` を本気で使う最初の例である。
2. **UBNF の限界試験**。自己拡張＝構文が実行中に変わる言語を、静的 PEG と宣言的 scope で
   どこまで書けるかを測り、書けない場所を「UBNF に何を足せば書けるか」の形で残す（§5）。
3. **型の付いた連接言語を実際に成立させる**。Factor / Kitten / Cat の系譜で、
   スタック効果を宣言して静的に検査する。
4. **LSP / VSIX が文法から出ることの実証**。`--emit-lsp` で定義ジャンプ・未定義語・
   補完が出る（§8）。これが stax の「売り」であり、UBNF の売りでもある。

### 非目標（stage 1 では）

- **性能**。stage 3 のインタプリタは正しさ優先の tree-walking で始める。
- **ジェネリクス**。stage 2。構文の場所だけ空けてある（§4.7）。
- **本物の Forth 互換**。`CREATE … DOES>` も `IMMEDIATE` も入れない（§5.3）。
- **モジュールシステム**。`use` は「取込む名前を明示列挙する」だけの最小形（§3.3）。
- **可変データ**。`!x` は構造体を差し替えた新しい値を返す（破壊的代入ではない）。
- **例外・並行・FFI**。

## 2. 名前 — 3 案と仮決め

| 案 | 由来 | 良い点 | 悪い点 |
|---|---|---|---|
| **stax**（仮決め） | stack + syntax | 4 文字。拡張子 `.stax` がそのまま使える。ASCII 小文字。読みが一意 | 既存の同名プロダクトが世に複数ある（この repository の例題としては支障なし） |
| kumiki | 組木（釘を使わず部材が噛み合って構造になる木組み） | **組込みの制御構造を持たず、語が噛み合って制御構造になる**という性質そのもの。名前が一意 | 6 文字で拡張子が長い。非日本語話者に由来が伝わらない |
| catena | ラテン語で「鎖」= concatenative の語源 | 由来が正確。響きが良い | 既存の型付き連接言語 **Cat**（Christopher Diggins）と紛らわしい。この系譜の先行研究と名前で衝突するのは避けたい |

**仮決めは `stax`**。決め手は 3 つ: (a) ディレクトリ名・拡張子・grammar 名・生成クラス名の
すべてに短い ASCII 小文字がそのまま使えること、(b) stack machine であることが名前で分かること、
(c) 先行する型付き連接言語（Cat / Factor / Kitten）と字面で衝突しないこと。
kumiki は物語としては最良なので、公開する段になったら再検討の余地がある。

## 3. 構文（BNF 風の要約）

正確な定義は [`stax.ubnf`](stax.ubnf)。ここは読むための要約。

```
Program    ::= TopLevel* EOF
TopLevel   ::= UseDecl | WordDef | MacroDef | StructDef | TypeDef

UseDecl    ::= 'use' STRING '(' IDENT* ')' ';'
WordDef    ::= ':' IDENT Effect Term* ';'
MacroDef   ::= 'macro' IDENT Effect Term* ';'
StructDef  ::= 'struct' IDENT '{' FieldDecl* '}'
FieldDecl  ::= IDENT ':' TypeRef
TypeDef    ::= 'type' IDENT '=' ( SumBody | AliasBody ) ';'
SumBody    ::= '|' IDENT ( '|' IDENT )*
AliasBody  ::= TypeRef

Effect     ::= '(' TypeRef* '--' TypeRef* ')'
TypeRef    ::= QuotType | BuiltinType | IDENT
QuotType   ::= '[' TypeRef* '--' TypeRef* ']'
BuiltinType::= 'Int' | 'Float' | 'Bool' | 'Str'

Term       ::= Quotation | NumLit | StrLit | BoolLit
             | LetBind | FieldGet | FieldSet | Prim | WordRef
Quotation  ::= '[' Term* ']'
LetBind    ::= 'let' IDENT
FieldGet   ::= '.' IDENT
FieldSet   ::= '!' IDENT
WordRef    ::= IDENT
```

コメントは `//` と `/* */`（`@whitespace: javaStyle`）。

### 3.1 なぜこの形か — PEG に素直な 3 つの決定

1. **和には先頭の `|` を必ず書く**（`type C = | Red | Green ;`）。
   これで「別名か和か」が 1 token で決まり、順序付き選択が後戻りしない。
   先頭 `|` を省略可能にすると、`TypeRef` と最初の枝がどちらも `IDENT` で構造同一になり、
   `W-CHOICE-UNREACHABLE` が出る（＝どちらかの候補が黙って死ぬ）。
2. **利用者定義の語は識別子だけ**（`[A-Za-z_][A-Za-z0-9_]*`）。記号だけの語
   （`+` `<>` `>r`）は**組込みの固定語彙**に限る。
   こうすると組込み語を文法にリテラルで並べられ、UBNF v2 の**語境界**（D-040）が
   「`dup` が `duplicate` の頭を横取りしない」を保証してくれる。
   本物の Forth は任意の記号列を語にできるが、それをやると組込み語をリテラルで書けなくなり、
   語彙を実行時に注入する口（§5.4）が無い現状では未定義語の警告がすべての語に出てしまう。
   **これは UBNF の形に合わせた最大の妥協**であり、§5.4 で外し方を書く。
3. **`.` はフィールドアクセス専用**。Forth の `.`（表示）は `print` に改名した。
   `.` を語に使えるようにすると `p.x` が 1 語に見えてしまい、フィールド参照を
   `@symbolRef` で引けなくなる。

### 3.2 語の定義と「定義してから使う」

```
: square ( Int -- Int ) dup * ;
```

`WordDef` は `@scopeTree(mode=lexical)` と `@declares(symbol=name)` の両方を持つ。
UBNF の宣言登録は**規則を抜けたあとに親スコープへ**行われるので、

- 語名は**ファイルスコープ**に登録される（外から見える）
- **本体からは自分の名前が見えない**

という 2 つが同時に出る。後者は偶然ではなく、**Forth の smudge bit と同じ意味**である
（Forth も `;` を実行するまで定義中の語を辞書から隠す）。だから自己再帰は Forth と同じく
専用語 `recurse` で書く。**言語の意味論と UBNF の scope 意味論が一致した数少ない箇所**で、
stax がこの形を採った理由の一つでもある。

前方参照（後ろで定義された語を先に使う）も同じ理由で解決しない。
[`samples/18-undefined-word.stax`](samples/18-undefined-word.stax) がその 2 例を持っている。

### 3.3 `use` — 取込む名前を明示列挙する

```
use "16-veclib.stax" ( Vec2 vx vy vec_add vec_len_sq ) ;
```

静的 PEG は 1 ファイルしか見ない。そこで **取込む名前をソースに書かせる**。
列挙した名前は `@declares` でこのファイルのスコープに入るので、
**相手のファイルを読まずに参照が解決する**。相手に本当にその語があるかは stage 3 で見る。

Modula-2 の `FROM M IMPORT x, y` や Haskell の明示 import リストと同じ発想で、
「文法だけで完結させる」という制約から素直に出てきた設計である。
`import *` 相当を入れない理由もここにある（入れた瞬間に文法だけでは解決できなくなる）。

## 4. 型システム

### 4.1 型の語彙

| 種別 | 書き方 | 備考 |
|---|---|---|
| 組込み | `Int` `Float` `Bool` `Str` | 実行系が供給する固定語彙。文法にリテラルで書いてある |
| 構造体 | `struct Point { x: Int y: Int }` | **名前的**（nominal）。同じ形でも名前が違えば別の型 |
| 別名 | `type Meters = Int ;` | **透過**（transparent）。`Meters` と `Int` は同じ型。不透明な新型は stage 2 |
| 和 / 列挙 | `type Color = \| Red \| Green \| Blue ;` | 枝は引数を取らない。引数付きの枝は stage 2 |
| 引用の型 | `[ Int -- Int ]` | 「Int を 1 つ取って Int を 1 つ返す引用」 |

stage 1 の組込み語（primitive）は **Int 専用**である。`Float` は型の語彙としては
予約してあるが、`Float` を取る primitive はまだ無い（stage 3 で足す）。

### 4.2 スタック効果の読み方

```
( I1 I2 ... In -- O1 O2 ... Om )
```

- 入力・出力とも**左から右へ、右端が最上段**。`( Int Str -- Bool )` は
  「最上段が `Str`、その下が `Int`」を取る。
- `( -- )` は何も取らず何も残さない。
- 効果は**語の宣言の一部**であって推論結果ではない。宣言と本体が合うかを検査する。

### 4.3 検査の規則（stage 3 の検査器が実装する）

状態はスタックの**型の列** `S`（左が底）。項 `t` の効果を `(p -- q)` とすると:

> **合成則**: 現在の状態が `S` で、`S = S' ++ p` と書けるとき、`t` を適用した後の状態は
> `S' ++ q`。`S = S' ++ p` と書けなければ**型エラー**（深さ不足 or 型不一致）。

語 `w` の本体 `t1 … tk` は、`w` の宣言効果を `(P -- Q)` として

> 状態 `P` から始めて `t1 … tk` を順に適用し、**最終状態がちょうど `Q` に等しい**こと。
> 余っても足りなくても型エラー（[`samples/20-effect-mismatch.stax`](samples/20-effect-mismatch.stax)）。

各項の効果:

| 項 | 効果 |
|---|---|
| `42` | `( -- Int )`。字句に `.` か `e` があれば `( -- Float )` |
| `"x"` | `( -- Str )` |
| `true` / `false` | `( -- Bool )` |
| `[ body ]` | `body` の効果が `(p -- q)` のとき `( -- [ p -- q ] )` |
| `let x` | 最上段 `T` を取り出し、この定義の枠に `x : T` を記録する。`( T -- )` |
| `x`（`let` した名前） | `( -- T )` |
| `w`（定義済みの語） | `w` の宣言効果 |
| `V`（和の枝、`type C = \| V …`） | `( -- C )` |
| `Name`（struct 名） | `( T1 … Tn -- Name )`。`Ti` はフィールド宣言順 |
| `.f` | `( S -- T )`。`S` は `f : T` を持つ struct |
| `!f` | `( S T -- S )` |
| `recurse` | いま定義中の語の宣言効果 |

`call` と `choose` は**語の signature では書けない**（ジェネリクスが要る）ので、
検査器の規則として持つ:

- `call`: 状態が `S ++ [ [ p -- q ] ]` のとき、`S = S' ++ p` を要求し `S' ++ q` にする。
- `choose`: 状態が `S ++ [ Bool, [p -- q], [p -- q] ]`（**2 つの引用の効果が一致**）のとき
  `S ++ [ [p -- q] ]` にする。

これは Factor の `call(` や Kitten の行多相に相当する部分を、
「ジェネリクスが入るまでの間、検査器の特別則として持つ」形に落としたものである。
stage 2 で行変数（row variable）を入れたら、この 2 つは普通の signature に戻る。

`=` / `<>` は**等価比較のできる型**（`Int` `Float` `Bool` `Str` と和の型）に対して
`( T T -- Bool )`。`<` `<=` `>` `>=` は `( Int Int -- Bool )`。

### 4.4 何を静的に検査し、何を先送りするか

| いつ | 何を | どこで |
|---|---|---|
| **stage 1（いま）— 文法だけ** | 構文。未定義の語・型・フィールド名（WARNING）。定義順（前方参照は未解決） | `@scopeTree` / `@declares` / `@symbolRef` |
| **stage 3 — 型検査器** | スタック効果の整合、リテラルの型、struct の構築とフィールドの型、`let` の型、引用の効果、和の枝、`use` の相手に本当に語があるか、`.f` がどの struct の `f` か | Rust の checker |
| **実行時** | 0 除算、再帰の停止、文字列の添字範囲、`Float` の精度 | Rust のインタプリタ |

**`.f` の解決は stage 1 と stage 3 で役割が割れている**。文法は struct のフィールドを
**ファイルスコープの宣言**として登録するので、「`.x` という名前の宣言があるか」までは
文法だけで言える。しかし「どの struct の `x` か」は最上段の型が決まらないと言えないので
型検査器の仕事になる。同名フィールドを複数の struct が持つときは、型から一意に決まれば
通し、決まらなければエラーにする。

### 4.5 struct とフィールド

```
struct Point { x: Int y: Int }

: origin ( -- Point ) 0 0 Point ;
: shift_x ( Point Int -- Point ) let dx dup .x dx + !x ;
```

- struct 名はそのまま**コンストラクタの語**。フィールド宣言順にスタックから取る。
- `.f` は取得、`!f` は「そのフィールドを差し替えた新しい値」を返す（破壊しない）。

### 4.6 局所束縛

`let x` は最上段を取り出して、いま定義中の語の枠に `x` という名前で束縛する。
同じ名前に対する 2 度目の `let x` は**同じ型でなければならない**（枠の中では単型）。
引用は外側の定義の束縛を見る（[`samples/12-while.stax`](samples/12-while.stax) の `n`）。
束縛は `WordDef` の `@scopeTree` が作ったスコープに入るので、定義の外へは漏れない。

### 4.7 ジェネリクス（stage 2）— 構文の場所

いま空けてある場所は 3 つ。**どれも現行の文法と衝突しない**ことを確認してある。

```
: swap_pair <A B> ( A B -- B A ) swap ;     // 語の型パラメータ: 名前と '(' の間
struct Box <T> { value: T }                 // struct の型パラメータ
type Pair <A> = ... ;                       // 型の型パラメータ
List<Int>                                   // 型の位置での実引数
```

- `<` `>` は組込み語だが、現れるのは **項の位置**だけである。型パラメータが現れる
  「名前の直後・`(` の前」と「型の位置」には項が来られないので、字面が同じでも曖昧にならない。
- **UBNF v2 のパラメータ化ルール `Name<P>`（D-043）とは層が違う**。あちらは*文法*の雛形、
  こちらは *stax の型*。同じ字面だが混同しないこと。
- 行変数（row variable）を入れたら §4.3 の `call` / `choose` の特別則は普通の signature に戻る。
  そのときの綴りは `( ..a [ ..a -- ..b ] -- ..b )` を第 1 候補とする（Kitten 方式）。

## 5. 自己拡張の方式と、その境界

### 5.1 問題

本物の Forth の自己拡張は **parsing word**（入力ストリームを自分で読む語）で出来ている。
`(` は `)` まで読み飛ばし、`."` は `"` まで読んで表示を compile し、
`CREATE … DOES>` は**新しい語を辞書に足す語**を作る。
つまり **Forth には固定した文法が無い**。あるのは「空白で区切って辞書を引く」だけで、
その先はすべて語の実行時の振る舞いである。これは静的 PEG では原理的に書けない。

### 5.2 第 1 案（stage 1 で採る）— 引用 `[ ... ]` ＋ macro

Factor の流儀。**構文は固定し、拡張の力を語の側に移す**。

- 引用 `[ ... ]` は「まだ実行しない語の並び」で、値として積める。
- 制御構造は引用を受け取る**ただの語**として定義する。
  組込みは `choose`（真偽で引用を選ぶ）・`call`（引用を実行する）・`recurse` の 3 つだけで、
  `if_else` / `if` / `while` / `times` はすべて言語の中で書ける
  （[`samples/04-prelude.stax`](samples/04-prelude.stax) が全文）。
- `macro` は「引用を受け取って引用を返す、コンパイル時に走る語」。
  構文糖を利用者が足せる（[`samples/14-macro.stax`](samples/14-macro.stax) の `unless`）。

**これで届く範囲**: 制御構造・構文糖・DSL 風の語彙。届かない範囲は §5.3。
**なぜこれを採るか**: 構文が固定なので、(a) 文法が 1 本で済み、(b) LSP が文法から自動で出て、
(c) 型検査がソースだけで完結する。issue #66 の「UBNF の限界試験」としても、
**限界の手前で何が作れるかを最大化した形**が先に要る。

### 5.3 Forth の parsing word 3 例の分類

| Forth の語 | 何をするか | stax での扱い | 分類 |
|---|---|---|---|
| `( … )` | `)` まで入力を読み飛ばす（注釈・スタック効果） | **固定構文にした**。スタック効果は `Effect` 規則、注釈は `//` `/* */`（trivia）。利用者は再定義できない | **書けた** |
| `."` | `"` まで入力を読んで「その文字列を表示する」を compile する | **字句 + 語 + macro で代替**。文字列は token（`DOUBLE_QUOTED`）、表示は `print`、`." x"` 相当の短縮は macro で作れる。「入力を読む」部分が字句の仕事に移っただけで、利用者から見た力は落ちていない | **quotation + macro で代替** |
| `CREATE … DOES>` | **新しい語を辞書に足す語**（defining word）を定義する。`42 constant answer` のように、利用者が作った語が**その場で新しい語名を導入する** | **不可能**。理由は 2 段ある（下記） | **不可能（UBNF に §5.4 が要る）** |

`CREATE … DOES>` が不可能な理由:

1. **構文の形が語彙に依存する**。`42 constant answer` を正しく読むには、
   「`constant` は defining word なので次の語は*宣言*である」と知っていなければならない。
   どの語が defining word かは**そのファイルを実行してみないと決まらない**。
   PEG の規則は語彙を知らないので、この形は構文の段では区別できない。
   意味述語（ANTLR の `{…}?`）があれば書けるが、UBNF は memo・候補除外・字句キャッシュの
   健全性のために意味述語を**入れないと決めている**（`docs/design/06-ubnf-v2.md` §4）。
2. **語彙が実行時に増える**。`CREATE` は実行時に辞書へ名前を足す。
   UBNF のスコープは**そのファイルの構文解析中に構築される**ので、
   ソースのどこにも書かれていない名前は原理的に登録できない。

stax はこれを **「固定した定義形」で置き換える**。`42 constant answer` の代わりに
`: answer ( -- Int ) 42 ;` と書く。**defining word を作る力は諦め、語を作る力は残す**、
という線の引き方である。

### 5.4 第 2 案（明文化のみ）— UBNF に何を足せば `CREATE … DOES>` が書けるか

stage 5 の提案の下書き。**3 つ要る**。

#### (X1) 実行系が供給する語彙を、解析時のスコープへ注入する口

```ubnf
// 案: 外から与えられた記号集合を、解析開始時にルートスコープへ積む
@vocabulary(context='primitive', source=extern)
```

- いまは組込み語（`dup` `+` `print` …）と組込み型（`Int` …）を**文法にリテラルで並べている**。
  これが動くのは語彙が固定だからで、実行系が語彙を決める言語では成立しない。
- CLI に `--vocabulary FILE`（名前と種別の一覧）を足し、front がルートスコープの初期状態として
  IR に載せ、`@symbolRef` がそこも引く。**受理範囲は変わらない**（スコープ診断だけが変わる）ので、
  memo・候補除外・字句キャッシュの健全性に触らない。**3 つの中でいちばん安い**。
- 既にある `@catalog` は「補完候補を*出す*」metadata である。これを「語彙を*入れる*」側にも
  使えるようにするのが最短路と見ている。

#### (X2) 実行時に定義される字句クラス

```ubnf
// 案: 語彙集合が版を持ち、その版が memo / 字句キャッシュのキーに入る
token WORD = extern 'vocabulary' volatile
```

- 利用者が任意の記号列（`>>`, `2dup!`, `日本語の語`）を語にできるようにするには、
  「語を構成する文字」の判定を実行系に委ねるしかない。
- **これは D-013 の「終端は (入力, 位置) の純粋述語である」を破る**。破らずに済ませるには、
  スコープが既に持っている **版付き無効化**（`scope.versionChanges` / `scopeUndo`）と同じ仕組みを
  字句キャッシュと memo にも入れ、`TokenSpec.Extern { volatile: true }` の token を含む memo 項目を
  版が変わったら捨てる必要がある。設計としては書けるが、**契約の中心を触る**ので安くはない。

#### (X3) 語彙に依存して構文の形が変わること

- `42 constant answer` の `answer` を**宣言**として扱うには、構文の段で「`constant` は
  defining word だ」と知る必要がある。これは意味述語そのもので、UBNF は入れないと決めている。
- **現実的な代案**: 「defining word の呼び出しは固定構文で囲む」。
  たとえば `define constant answer 42 ;` のように、*どの語が defining word でも形が同じ*に
  なる構文を 1 つ用意する。これなら `answer` の位置が構文的に決まるので `@declares` が書ける。
  **stage 5 ではこちらを推す**。(X3) を UBNF に足すのは、費用に対して得るものが小さい。

#### まとめ

| | 要るもの | UBNF の契約への影響 | 推奨 |
|---|---|---|---|
| X1 | 外部語彙のスコープ注入 | **無し**（診断だけ変わる） | **やる価値がある。stage 5 で起票** |
| X2 | 実行時に決まる字句クラス | D-013 を版付き無効化で緩める | 要るなら書けるが高い |
| X3 | 語彙依存の構文形 | 意味述語＝**入れないと決めた** | **入れない**。固定構文で代替する |

### 5.5 stage 5 で見る境界ケース

1. `IMMEDIATE` 相当（コンパイル時に走る語）は macro で代替できるか。できない形は何か。
2. macro が**新しい語を定義**したとき、その語名はスコープに入るか（いまは入らない。X1 の亜種）。
3. 語彙が版を持つとき、LSP の増分解析はどこまで再利用できるか。
4. `use` の相手ファイルの語彙を、解析時に引ける形で渡せるか（X1 のもう一つの用途）。

## 6. 実行モデル

Rust の小さなインタプリタ（stage 3）。JVM は要らない。

```
ソース
  → ubnfc の生成した Rust パーサ（typed AST）      ← stage 1 で出来ている
  → macro 展開（コンパイル時に走る語）
  → スタック効果の型検査                            ← §4.3
  → 評価（スタック機械）
```

- 値は `Int`（i64）/ `Float`（f64）/ `Bool` / `Str` / struct / 引用。
- 引用は「AST の断片＋定義の枠への参照」。`call` で実行する。
- `recurse` はいま実行中の語を呼び直す。
- 実行の入口は語 `main`。`( -- )` でなければならない。
- 型検査を通ったプログラムは「スタックの深さと型」については実行時検査が要らない。
  実行時に落ちるのは 0 除算・添字範囲・再帰の停止だけ。

## 7. この文法が使っている UBNF の機能

| 機能 | 書いた場所 | なぜ要るか |
|---|---|---|
| `@ubnf: 2` | 冒頭 | 以下の v2 既定を有効にする |
| **語境界**（D-040、`@literalBoundary: word`） | 組込み語 29 本と組込み型 4 本のリテラル | `dup` が `duplicate` を、`Int` が `Integer` を横取りしないこと。**「組込み語をリテラルで並べ、利用者定義語を IDENTIFIER にする」という §3.1 の設計全体がこれに乗っている**。v1 の既定（`none`）ではこの文法は成立しない |
| **中立な token 語彙**（D-041） | `IDENTIFIER` / `NUMBER` / `DOUBLE_QUOTED` / `END_OF_INPUT` | host のクラス名（`org.unlaxer.…`）を書かずに済む。extern token は 1 つも要らなかった |
| **到達不能候補の検査**（D-037、`W-CHOICE-*`） | 検証時 | 組込み語 29 本を 1 つの順序付き選択に並べている。**順番を間違えると候補が黙って死ぬ**ので、`--strict` で警告ゼロを CI の条件にしている |
| `@scopeTree(mode=lexical)` | `Program` / `WordDef` / `MacroDef` | ファイルスコープと語ごとのスコープ。`let` の束縛が定義の外へ漏れないこと |
| `@declares(symbol=…)` | 8 箇所（語・macro・struct・struct のフィールド・型・和の枝・取込み名・`let`） | 「定義」の 7 種類すべて。記号表のコードは 1 行も書いていない |
| `@symbolRef(name=…)`（D-046 の v2 綴り） | 4 箇所（語の参照・型の参照・`.f` / `!f`） | 未定義参照が WARNING で出る。旧綴りの `@backref` は「文法中に `@scopeTree` があるか」という非局所判定で意味が変わるので使わない |
| `@mapping(...)` | 27 箇所（**AST を作るすべての規則**） | typed AST。選択だけの規則（`TopLevel` / `Term` / `TypeRef`）にも付けて、sealed interface + record の和型を出している |
| `@catalog(context=…)` | 6 箇所（組込み語・組込み型・利用者の語・型・フィールド 2 種） | LSP の補完カタログ。**種別ごとに context を分ける**ので、型の位置で語が出るようなことが起きない |
| `@doc('…')` | 17 箇所（主要な規則すべて） | `--emit-lsp` の hover（D-062）。§8 |

**使わなかったもの**と、その理由:

| | なぜ使わないか |
|---|---|
| **左再帰**（D-039） | 連接言語に演算子の優先順位が無い。`3 4 +` は並びであって式木ではないので、優先順位塔そのものが存在しない。**UBNF v2 の目玉機能が 1 度も要らない文法**という意味で、P4 / JSON と性格が違う 3 本目の例になっている |
| **パラメータ化ルール**（D-043） | 同じ形の繰り返しが無い。P4 のような「型ごとに 4 本ずつ同じ規則」が stax には出てこない |
| **code point クラス**（D-063） | 文字列は組込み token（`DOUBLE_QUOTED`）に任せている |
| `@leftAssoc` / `@precedence` | 同上（演算子が無い） |
| **`@recovery`** | **置ける場所が無かった**。詳細は次項 |

### 7.1 `@recovery` を外した理由（実測）

> **追記（#71 / D-073）**: この形は `ubnfc validate` が `W-RECOVERY-IN-CHOICE` で警告する
> （`--strict` で exit 5）。回復を置くなら選択を含む規則そのもの（`@recovery TopLevel ::= …`）にする。

最初 `WordDef` に `@recovery(sync=';')` を付けたが、**正しいプログラムが壊れた**。

`TopLevel ::= UseDecl | WordDef | MacroDef | StructDef | TypeDef` の順序付き選択では、
`struct Point { … }` を読むときにも **まず `WordDef` が試されて失敗する**。
`@recovery` はその失敗を回復として拾ってしまうので、`struct` で始まるファイルが
「`WordDef` の回復」として受理され、宣言が 1 つもスコープに入らなくなった（実測）。
さらに、わざと壊した [`samples/17-bad-syntax.stax`](samples/17-bad-syntax.stax) が
**受理されてしまった**。

> **一般則**: `@recovery` は、**順序付き選択の最後でない候補から到達する規則には置けない**。
> その規則の失敗は「誤りである」ではなく「次の候補を試せ」の意味だからである。

stax では `@recovery` を 1 つも使わない。エディタ向けの誤り耐性は stage 4（LSP）の課題として、
「候補を試すための失敗」と「本当の構文誤り」を front が区別できるようにする話と一緒に扱う。
これは UBNF 側に残る宿題で、報告 `docs/reports/2026-09-24-stax-stage1.md` に書いてある。

## 8. 副産物 — LSP / VSIX は文法から出る

`ubnfc-lsp --emit-lsp` は IR だけから LSP サーバを出す（opt-in。root `pom.xml` の Maven profile
`lsp`、D-060 / D-062）。stax はそのために書き足すものが無い。**すでに書いた注釈がそのまま機能になる**:

| 注釈 | LSP で何になるか |
|---|---|
| `@declares` + `@symbolRef` | **定義ジャンプ**（語・型・フィールド・取込み名・局所束縛）と**未定義語の波線** |
| `@scopeTree` | 局所束縛が定義の外で補完に出ないこと |
| `@catalog(context=…)` | **補完**。項の位置では語、型の位置では型、`.` の後ではフィールドだけが出る |
| `@doc('…')` | **hover の説明文**（生成される `Meta.RULE_DOC`） |

つまり「型定義のできる Forth」を作ると、**定義ジャンプと補完と hover が付いてくる**。
これが issue #66 の「副産物」であり、UBNF を使う理由そのものでもある（stage 4 で実証する）。
