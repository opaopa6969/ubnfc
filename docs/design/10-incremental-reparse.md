# LSP の増分再解析の設計と着手条件

2026-11-01、issue [#5](https://github.com/opaopa6969/ubnfc/issues/5)。
この issue は**本設計文書と D 行の追加で完了する**。今回は実装しない。
実装段階は [#13](https://github.com/opaopa6969/ubnfc/issues/13) で追跡し、
**LSP の利用者 tinyexpression から 100 KB 級の文書を扱う具体的要求が出たら着手する**。
合成入力の計測だけでは、この着手条件を満たさない。

既存の [D-023・D-060・D-062](03-design-v1.md) と
[二重カーソル・診断の契約](04-cursor-and-diagnostics-contract.md) を維持する。
本決定は D-093。D-060 の「現時点では全文再解析」を継続し、導入の条件を具体化する。

## 1. 現状と測定範囲

`ubnfc-lsp/src/main/resources/lsp-templates/LanguageServerImpl.java` は
`TextDocumentSyncKind.Full` を広告し、`didOpen` / `didChange` ごとに全文を
`Analysis.of()` で解析して `DocumentStore` に差し替える。
同じ本文の definition / references / document symbols / hover などは解析結果を共有する。

`Analysis` は primary と scoped を分ける。primary の認識経路が診断を要するときは
生成パーサが D-023 の診断モードで再解析する。さらに失敗文書では主失敗位置までを別入力として
解析し、成功した前半だけの scope を使う（D-062）。全文失敗時の scope 巻戻しを変えてはならない。
semantic tokens の lexical は要求時に別途解析して保持する。completion も要求時の別処理である。
詳細は [LSP 段階 3 報告](../reports/2026-09-24-lsp-vsix-stage3.md) §3・§8。

本測定は従来と同じ `LanguageServerImpl.analyze(uri, text)`、すなわち
`Analysis.of`、文書の保存、LSP 診断への写像の合計を対象とする。
診断を誘発する入力なので D-023 の再解析費用も含む。
JSON-RPC の転送、エディタの描画、completion、遅延 lexical は含まない。
16 ms はこの打鍵時解析部分の目安であり、応答全体の保証ではない。

### 再現手順

JDK 21、Maven、必要な Maven 依存が取得できる環境で、対象 commit の隔離 worktree にて実行する。
Rust はこの測定では使わない（別途使う場合は `RUSTUP_TOOLCHAIN=stable`）。

```sh
MAVEN_FLAGS='' SKIP_VSIX=1 scripts/build-vsix.sh p4
CPU=28 WARMUP=200 SAMPLES=201 scripts/measure-lsp-reparse.sh
```

`MAVEN_FLAGS=''` は未取得の Maven 依存を取得するため。既定の `-o` は依存取得済みの場合に限る。
`CPU` を省略すれば固定しない。番号は実行環境で利用可能な CPU を選ぶ。
スクリプトは `mktemp -d` 内で計測用 Java をコンパイルし、終了時に一時ファイルを消す。
`-Xms512m -Xmx2g -Xss16m`、入力ごとに 200 warmup、201 回の個別計測で min / p50 / p90 を出す。
p50 はソート後の中央、p90 は nearest-rank。入力生成・事前の構文成功確認・UTF-8 長算出は計時外。
観測結果は volatile に保存する。GC は通常どおり含め、測定間の強制 GC は行わない。

`complex` と `complex-x64` は既存 fixture。合成入力は `complex.tiny` の宣言・式・関数を別々に束ね、
`price` / `country` / `bonus` に通番を付け、式を `+` で連結する。
小さい入力を無効な形で反復したり、先頭だけ読んで失敗する入力で長文の費用を代用したりしない。
すべて `primary.ok()` を確認し、構文失敗・資源例外なら測定を中止する。
既存の scope 診断は除去せず件数を出すため、純粋な成功認識だけのベンチとは異なる。

## 2. 段階 1: 成功 memo を版を跨いで再利用する

再利用の候補は**変更範囲を跨がない規則の成功 memo**。
ただし「消費区間が変更と交わらない」だけでは不十分であり、次の条件をすべて満たすものに限る。
失敗 memo の持越しは最初の段階に含めない。

1. D-023 の決定性を前提に、文法・入口・scanner 設定・解析オプションが同じことを確認する。
   認識、診断、AST、occurrences、lexical の要求が違う結果を流用しない。
   決定性は**同じ入力と状態**の性質であり、編集後の入力の同値を保証するものではない。
2. memo ごとに実際の読取り依存範囲を記録する。採用枝の消費範囲に加え、先読み・負の先読み、
   失敗した先行候補、反復の停止判定、trivia、EOF 判定、scanner が参照した範囲を含める。
   子 memo の依存も親に伝える。読取り範囲を証明できない scanner は再利用しない。
3. 旧入力の変更 `[a,b)` を新しい文字列で置き換えたとき、依存が触れる memo を失効させる。
   挿入は `[a,a)` と空集合で判定せず**境界への依存**も失効させる。
   例えば `A ::= 'a' !'b'` の `a` の直後に `b` を入れたら、消費が 1 文字のままでも無効。
   EOF に依存する結果は旧末尾への挿入で無効になる。
4. 変更の後ろの有効な結果を `deltaCp = 挿入 cp 数 - (b-a)` だけシフトする。
   キーの consumed / matched、終了 C/M、span、効果内の位置など**全位置**が対象。
   `mode` / `invert` / `reset` のキーと結果状態も保つ。
   先頭側は delta 0。C と M が変更の両側にあるものは単一シフトで扱わず失効させる。
   UTF-16 の差分から直接 cp のシフト量を推測せず、`Positions` 相当の変換で編集位置を確定する。
5. scope の入出状態と効果を検証する。現行の `ScopeStore.stateVersion()` は解析内の世代であり、
   次の解析の同じ整数は同じ意味状態を表さない。最初は scope を読まず変更しないことを
   文法から証明できる規則に限定し、拡張時は永続状態の同一性または意味状態の検証と効果再生を設計する。
   extern scanner も純粋性と依存範囲が必要で、効果がある経路は当初全文解析へ戻す。

現行 `MemoTable` の thread local は配列の再利用だけで、内容は世代ごとに破棄する。
payload は `Session` 内の Match・効果等を参照するため、表だけ残して古い arena の handle を使ってはならない。
版ごとの所有権を持つ持越し表と位置変換が必要である。旧版を変更せず、新版の結果を組み立ててから公開する。
公開 occurrence ID、親子 ID、完了順は全文解析と同じ値に再構成する。

**診断再解析は当初すべて全文参照経路で行う**。成功した規則の内側にも投機的失敗があり、
expected / hints / deepest rule / 呼出し経路を成功 memo だけで再生できるとは限らない。
失敗・末尾入力・recovery・scope/mapping/resource 診断を要する場合は D-023 の分岐をそのまま通す。
前半 scoped は切断位置と `requireFullInput=false` を持つ別入力として扱い、全文用の表と混ぜない。
lexical も初期段階では全文解析を続け、認識の memo を流用しない。
資源上限の判定も観測であり、節約した処理数で結果が変わる場合は参照経路へ戻すか、同じ資源会計を再現する。

この段階は安全性と再利用率を測るためのもの。全文同期、全 memo のシフトや全位置索引の作り直しが
O(文書長) のままでは打鍵費用が変更量に比例するとは主張しない。既定の全文経路を残して比較する。

## 3. 段階 2: 文法から独立性を証明できる単位だけ再解析する

候補は文・宣言など。`@recovery` の同期点（IR の `resolvedSyncPatterns` / FOLLOW）や
`;` の区切りを手掛かりにするが、**区切り文字があるだけで分割可能とは認めない**。
文字列・コメント内の `;`、入れ子、trivia、境界を越す先読み、順序付き選択、scanner、scope の依存を調べる。
`@recovery` は試行失敗でも発火する契約（D-073）を持ち、任意の文の独立性の証明にはならない。

front が将来出す分割計画には、対象規則、開始・終了境界、同期文字列の消費有無、
読み越し上限、入出 scope の条件、親への AST/capture/recovery 投影を明記する。
証明できない規則は分割しない。IR の既存情報だけで十分と仮定せず、計画追加は実装段階の別途検証とする。

編集時は変更に触れた単位と境界の隣接単位を失効させ、安定した左境界から再開する。
新旧の境界・出力状態が一致するまで右へ再解析する。宣言変更で後続の参照解決が変わる場合は、
依存する単位まで再計算し、安定しなければ全文へ戻す。壊れた文字列や同期点の削除で EOF まで
失効することも許容する。失敗文書の primary と前半 scope の選び方を変えない。
部分結果の連結は親の採用順・capture 完了順・scope rollback・recovery 投影を全文と一致させる。

目標は、通常の局所編集の**再解析部分**を変更量と依存の失効範囲で決めること。
全文同期の文字列差分探索、cp/UTF-16/行索引、位置シフトのための全走査が支配的なら、
遅延シフト可能な区間索引や文書表現を検討する。LSP の Incremental sync を広告する変更は
内部の memo 再利用とは別であり、Full sync のまま総費用を O(変更量) と称しない。
必要ならプロトコル互換性を保つ別変更で増分同期を検討する。
診断一覧や semantic tokens 全量の出力は結果サイズの費用を持つため、解析・写像・転送を分けて報告する。

## 4. 段階 3: tree-sitter 型の木の再利用は保留する

本設計では、既存の木を編集で部分的に差し替える方式を採らない。
この parser の再利用可否は scannerless PEG の候補順・失敗した枝の読取り・二重カーソル・scope に依存し、
採用された木の span だけでは条件を判定できない。さらに Match → Recipe → typed AST と
capture/lexical の観測は別の投影を持ち、木を残すだけでは診断や完了順を再現できない。
認識だけなら木を作らない現行経路に、再利用のための常設の木を加える費用も発生する。

これは一般的な方式の優劣の断定ではなく、既存の観測契約に対する導入費用の判断である。
まず要求入力で段階 1〜2 の再利用率、失効範囲、残る費用を測る。
不足が実測で示された場合に限り、木の形式、所有権、依存情報、メモリ上限、公開 ID の再構成を
新しい設計判断として比較する。今回の設計完了に完全な木の再利用を要求しない。

## 5. 観測契約不変を検証する差分ファジング

実装時は同一 backend・同一生成 parser に全文参照モードと増分モードを用意する。
文法、入口、scanner、オプション、資源上限を揃え、各編集後の**最終本文が同じ**になるよう適用する。
旧版を引き継ぐのは増分側だけ。参照側は版ごとに新しい解析を作り、過去の結果を共有しない。

| 観測対象 | 比較方法 |
|---|---|
| 受理・カーソル | ok、consumedCp、matchedCp、native failure を完全一致 |
| AST・capture・lexical | canonical AST、node/value span、catalog、採用枝、値、公開 occurrence/parent ID・完了順を完全一致。Java のオブジェクトアドレスだけは比較しない |
| 診断 | kind、主 offset/length、farthest、expected/hints、deepest/rulePath、recovery/resource/mapping を配列順も含め全文と一致 |
| scope・回復 | 宣言・参照・解決先・イベントと順序・警告・深さ、回復領域・同期点・skipped span・capture 投影を一致 |
| LSP | diagnostics の code/message/severity/range、definition、references、symbols、hover、completion、semantic tokens の公開 JSON を一致 |
| 版と寿命 | didClose/reopen、別 URI、古い Analysis の読取り、遅延 lexical の要求順、失敗から成功への復帰で結果が混ざらないこと |

既存 `crates/ubnfc-fuzz` の文法・入力生成と縮小の方法、P4/UBNF の
`GoldenDiagnosticsTest` / `GoldenCapabilitiesTest` / `PositionsTest` を土台にする。
backend 間の比較だけでは両側の同じ増分バグを見逃すため、必ず全文対照を先に行う。
配列をソートして診断順序や occurrence ID の差を消すことはしない。

実装段階で最低限固定する campaign は、seed `0..99`、各 200 編集の連続列。
挿入・削除・置換・undo/redo・複数編集を混ぜ、空文書・EOF・入力先頭・規則境界・memo の両端を狙う。
`'a' !'b'`、失敗した先行候補、反復の停止点、宣言名の変更・shadowing、区切り・コメント・引用符の削除、
recovery、効果付き/不透明 scanner、非 BMP・結合文字・CRLF/単独 CR、資源上限直前直後を専用ケースにする。
文法が受理する入力に加え、途中で壊れ、後の編集で直る列も生成する。

各版で全観測を比較し、LSP は先頭・末尾・編集前後・全記号位置を probe する。
lexical を先に/後に要求する列、completion の位置を変える列も対照する。
反例は seed、文法/IR、元本文、編集列、オプション、最初の差の JSON path とともに保存し、
文法・初期入力・編集列を縮小して通常 CI の固定回帰に加える。大きい campaign は拡張検査とする。
これは検証計画であり、今回増分実装や campaign を追加したという報告ではない。

## 6. 実装の受け入れと切戻し

[#13](https://github.com/opaopa6969/ubnfc/issues/13) の全受け入れ条件を満たして実装段階を close する。
着手後は要求入力と合成入力の両方で、1/10/100 KB 以上の長さに対する先頭・中間・末尾の
一定サイズ編集を測る。再解析規則数、再利用率、割当、min/p50/p90、全文フォールバック率を示す。
局所編集と scope 変更・同期点削除の波及を別表にし、位置変換・出力等の全量処理も計時する。
要求された 100 KB 級で打鍵経路の合意した 16 ms 予算と変更量への追随を確認し、残る文書長依存を隠さない。

増分経路は opt-in で導入し、全文参照経路と parser の依存ゼロを維持する。
段階ごとの小さな PR に分け、不一致があれば全文経路へ切り戻せるようにする。
今回の変更は文書と計測スクリプトだけなので、設計 PR の revert で戻せる。
