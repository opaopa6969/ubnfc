# P4 Java 生成 parser の性能改善 M5（2026-09-22〜23）

[`2026-09-22-p4-java-bench.md`](2026-09-22-p4-java-bench.md)（fixture と計測法の正本）の続き。
目標は complex ≤ 0.2 ms（AST 付き）、complex-x64 ≤ 15 ms。意味論は変更していない
（corpus は round7 と同じ verdict、P4 golden AST byte 一致、ubnfc-java / runtime-template /
examples/p4-java の test 全緑）。

本文書は 4 段に分かれる作業のうち第 3 段・第 4 段（本 round）を記録し、第 1 段・第 2 段の値も
段階別 A/B に並べる。第 1 段 = 診断 O(depth²) の除去・定数巻き上げ・部分式 memo 省略の証明、
第 2 段 = Label 登録簿・trivia 計画・event-log 診断・in-place frame、第 3 段 = 診断 event log の
廃止と memo 表の持ち越し、第 4 段 = trivia 越しの FIRST 集合による候補除外。

## 結論

- complex.tiny（332 byte）は **認識 0.60 ms / AST 付き 0.64 ms**、
  complex-x64（20,923 byte）は **認識 37.1 ms / AST 付き 44.4 ms**。
  目標（0.2 ms / 15 ms）には**届いていない**。
- 1 parse の割当は complex（AST 付き）1,018 KB → 546 KB、complex-x64 79.8 MB → 35.7 MB。
- 本 round で効いたのは **候補除外**（同一 binary の predict on/off 比較で x4〜x64 が一貫して 0.58〜0.60 倍）。
  診断 event log の廃止と memo 表の持ち越しは割当を 27〜41% 減らしたが、時間は共有ホストの
  負荷に埋もれて有意差が出なかった。
- 残る差の内訳は「1 byte あたりの操作数」で、候補除外後でも complex 1 parse あたり
  rule 呼出し 1,076・失敗記録 5,813・trivia 呼出し 1,301（= 326 byte に対し 1 byte あたり約 23 操作）。
  Rust backend が同じ算法段階（round 2 末）で 1,063 rule 呼出し・0.24 ms だったのに対し
  Java は同じ操作数で約 2.8 倍かかる。目標に届かせるには Match 木の構築を
  event arena へ置き換える構造変更（Rust が M5 round 1 で行ったもの）が要る。

## 計測環境の注意（重要）

共有ホストで別エージェントの Rust 側計測・ビルドが並走し、作業中の load average は 2〜55 の範囲で
動いた。同じ binary・同じ fixture の再計測が 1.0 ms と 1.9 ms になる区間があり、**絶対値と
「段階ごとの小さな差」は信頼できない**。そのため本文書では

1. **負荷に依存しない計数**（rule 呼出し・memo hit・失敗記録・trivia 呼出し・1 parse の割当 byte）を一次証拠とし、
2. 時間は **同一プロセス内で on/off を交互に測る A/B**（`-Dubnfc.predict=false`）と
   **baseline binary と最終 binary を交互に 3 回ずつ実行した中央値**だけを載せる。

## 第 3 段: 診断 event log の廃止と memo 表の持ち越し

第 2 段は失敗を「追記専用の event log」に貯め、frame の expected 集合が必要になったときに
区間を走査して作っていた。complex 1 parse で追記 20,379 件・走査 44,980 件になり、`log()` を
潰すと 22% 速くなる（上記 ablation）ことから、frame ごとの expected 集合を持つ形へ戻した。
第 2 段が集合を捨てた理由（frame ごとの確保と O(depth) の吸収）は、**1 本の共有 stack の区間**に
することで解消する:

- `push` は区間の開始位置を記録するだけ。`failAt` は最内 frame の区間に線形探索で重複除去して追加する
  （区間長 = 最遠位置の候補数で、P4 では数件）。
- frame を離れるときの吸収は「子の最遠位置が親より遠ければ親の区間を子の区間で置き換え（前詰め）、
  同じなら親に無い id だけを親の区間の末尾へ詰め、手前なら子の区間を捨てる」。in-place で O(k)。
- snapshot は作成時に区間を複製するので、memo payload が Diagnostics の内部配列を参照しない。
- 負の先読みの `restore` は「その区間の event を囲む frame の走査から除外する」規則ではなく、
  checkpoint が保存した区間の内容をそのまま戻す。除外区間の管理が不要になり、厳密に同値。

memo 表（complex で `long[16384]` = 131 KB）と診断の配列は解析ごとに確保していたので、
`Session.parse` の `finally` で thread local の pool へ返し、次の解析で outcome 語だけ消して使い回す。
内容は持ち越さないので観測結果は変わらない。

結果: 割当が complex（AST 付き）1,018 KB → 741 KB、complex-x64 79.8 MB → 47.3 MB。
時間は有意差なし（下の段階別 A/B）。

## 第 4 段: trivia 越しの FIRST 集合による候補除外（本 round の主要変更）

Rust backend の M5 round 2（`crates/ubnfc-rust/src/predict.rs`）と同じ解析を Java emitter に実装した
（`ubnfc-java/src/main/java/org/ubnfc/java/emit/Prediction.java`）。

### 先頭文字集合

候補 expression ごとに `direct`（候補の呼出し位置で読む文字）と `skipped`（候補が最初の token の前に
必ず通る trivia policy で読み飛ばした位置で読む文字）を最小不動点で求める。Seq の入口・各要素後の
trivia 境界で `direct` を `skipped` へ移し、policy が混ざれば Unknown。Known になるのは
literal（大小区別あり）・組込み token（Number は `+ - . 0-9`、Identifier は英字と `_`、引用符、
文字集合）・文字範囲・DFA の開始遷移・**宣言のある Extern**（IR の `TokenSpec.firstChars`、
`scanners/first-chars.json`。Rust round 3 で入った field をそのまま読む）。
nullable な候補・先読み・最長一致・`childMode` の切替は Unknown。

### 再生（Java 版の設計）

Rust は候補ごとに失敗経路を関数へ展開する（`guard_e{i}`）。Java 版は**静的な表**（`Session.Guard`）にした。
実行時条件を次に限ることで、候補が記録したはずの失敗が**全て同じ位置 P に並ぶ**ようにしている:

1. `!f.invert`（否定先読みの中では判定しない）
2. `f.reset || f.c == f.m`（記録位置 `max(c,m)` と読み取り位置 `position()` が一致する）
3. `cp(P)` が `direct ∪ skipped ∪ 文法中の全 trivia 区切りの先頭文字` に**無い**
   （3 番目の条件により、候補の経路上の trivia は 1 文字も進まず、失敗した区切り集合の
   group label を P に 1 件記録するだけになる。区切りの先頭文字だったら本物の候補へ戻す。）
4. `depth + 経路の最大 rule 深さ < maxDepth`（深さ上限が発火し得るときは本物の候補へ戻す）

このとき P での観測は「label 列（記録順・重複除去）」「rule 経路（最大長の記録のうち最初のもの）」
「consumed / matched（最遠位置を更新した記録のもの。ここでは常に P）」だけで決まるので、
生成時に経路を辿って label 列・最深 rule suffix・最大 rule 深さへ畳み込める。
`Diagnostics.failBatch(pos, ids, suffix, c, m)` が現在の rule stack の上に静的 suffix を 1 回だけ載せて
まとめて記録する。

経路を辿れる node は Seq（先頭要素）・順序付き Choice（全候補）・Group・RuleRef（入口 scope
イベントと recovery を持たない rule）・literal で、展開 node 数の上限は 192（Rust と同じ）。
token 葉・repeat・separated・先読みを含む経路は対象外にした（Rust は token 葉で本物の関数を呼ぶが、
Java 版はそこまで実装していない。下記「残り」）。

再生と本物の差は **memo（lookup / store）と rule ごとの局所 frame**だけで、どちらも観測量を変えない
（memo 有無の同値は既存の性質。frame は「最内 frame へ記録して frame 終了時に親へ吸収する」規則が
「囲む frame へ直接記録する」と同値であることを第 1 段で確認済み）。`rule()` の recovery hint は
`localFarthest == max(c,m)` のときだけ記録するが、経路は必ず P に 1 件以上記録するので条件は常に成立する。

### 適用した選択（P4、41 選択のうち 12 選択・86 候補）

| 選択（rule） | 除外した候補 / 候補数 |
|---|---:|
| MathFunction | 14 / 14 |
| BooleanComparable | 16 / 19 |
| StringTerm | 14 / 16 |
| NumberFactor | 12 / 13 |
| SliceBaseReceiver | 11 / 12 |
| VariableDeclaration | 4 / 4 |
| ReturnType | 4 / 4 |
| StringPredicateReceiver | 4 / 4 |
| ObjectExpression | 3 / 6 |
| Expression | 2 / 6 |
| MethodInvocationHeader | 1 / 2 |
| BranchExpression | 1 / 8 |

### 見送った候補・選択と理由

- **葉の候補（literal / tokenRef そのもの）**: 本物の呼出しの方が安い（Rust backend と同じ判断）。
- **経路に token 葉を含む候補**（`Expression` の 4 候補、`BranchExpression` の 7 候補、
  `ObjectExpression` の 3 候補、`StringTerm` の 2 候補など）: 組込み token（NUMBER / Identifier）や
  Extern（STRING）は失敗時の記録位置が入力依存（`number()` は数字を読み進めた位置に記録する）なので、
  静的な 1 位置の表へ畳み込めない。Rust はここで本物の token 関数を呼ぶが、Java 版は
  rule suffix を積んで本物を呼ぶ仕組み（`pushRules`/`popRules`）を入れていないので対象外にした。
- **nullable な候補・先読みを含む候補・最長一致の選択**: 先頭文字では失敗を証明できない。
- **`repeat` / `separated` を先頭に持つ候補**: 失敗時に `failureCursor` と `Repeat` label を
  記録し、記録位置が周回数に依存する。
- **入口 scope イベントまたは recovery を持つ rule を通る候補**: 失敗経路にも副作用が出る。
- **plan が `predict` の選択（2 件）**: 既存の `eligible` 経路と重ねない。

- 認識どうしの比で **約 23 倍**、AST どうしで **約 23 倍**、1 parse の割当で **約 51 倍**。
  complex-x64 は認識 43 倍 / AST 38 倍（旧実装側だけ `-Xmx6g`。1.68 GB/parse 割り当てるため 2g では GC が支配する）。
- 旧 facade は認識より速い。候補選択を含むが `Diagnostics.AUTO` で成功経路の失敗記録を作らないため。
  入口の実務コストを見る副次値で、認識 / AST の対比には使わない。
  なお 10 秒の内部 deadline に当たり得るので `-Dtinyexpression.p4.parse.timeout.millis=0` で無効化して測る。
- `docs/design/02-facts-tokens-bench-corpus.md` §B の記録（complex 12.32 ms / complex-x64 958 ms）は
  **再現する**。同じ構成の JMH `parseOnlySafe` complex.tiny は記録 15.049 ms に対し本日 14.96 ms（0.6% 差）。

## 残り

1. **経路に token 葉を含む候補の除外**（`Expression` / `BranchExpression` / `ObjectExpression` /
   `StringTerm` の残り 22 候補）。`Session.pushRules(int[])` / `popRules(int)` で rule suffix だけを積み、
   本物の token expression を呼ぶ再生を足せば対象にできる。
2. **共通接頭辞の左因数分解**（Rust round 3 §因数分解。SliceBaseExpression / SliceNestedExpression の
   8 候補 × 2 段）。Java の runtime では共有接頭辞の評価結果が `Match` 木（`local` / `captures` の
   `Occurrence` に capture site id と name が焼き付いている）なので、採用候補が変わるときに
   site / name を付け替える `retag` に相当する操作と、その後の `combine` / `Values` / `completed`
   の順序が候補ごとの評価と同じであることの論証が要る。本 round では論証を確かめきれなかったので
   適用していない（Rust は event arena 上の `Session::retag` で解決している）。
3. **Match 木の廃止**（目標到達に必要な構造変更）。候補除外後も complex 1 parse で `Session$Match`
   と不変 List の確保が割当の半分以上を占め、`sequence` / `capture` / `combine` / `project` が
   自己時間の 2 割を占める。Rust が M5 round 1 で行った「認識中は event arena に追記し、
   AST は最後に組む」への置き換えが、Java で残っている最大の項目。
4. `MemoTable` の slot 縮小（現在 4 long = 32 byte/slot、complex で 131 KB の表を probe する）と
   load factor（0.5）の見直し。`MemoTable.locate` が自己時間の 12%。
5. `analysis.mayStart` への `firstChars` の反映（front 側）。現在の Java の `eligible` 経路は
   front の `mayStart` に依存していて P4 ではほぼ効いていない。
