# Java backend への D-066 移植 — 排他 predict が外れたら候補を 1 つも試さずに失敗する（issue #49）

2026-09-24。issue [#49](https://github.com/opaopa6969/ubnfc/issues/49)。
前提は [`2026-09-24-json-perf.md`](2026-09-24-json-perf.md) §3.4（Rust backend の D-066）と
§8 の申し送り 1「Java backend に D-066 が無い」。

## 0. 結論

**移植した**。front が `exclusiveCandidates` を証明した選択（plan が `strategy=predict` /
`fallback=none`）で、呼出し位置の文字がどの候補の先頭でもないとき、**fast mode（`diag=false`）だけ**
候補を 1 つも呼ばずに失敗を返す。診断モードは従来どおり元順で全候補を走らせる（D-023 により観測は
構成上一致）。

| もの | before | after |
|---|---:|---:|
| JSON literal 照合 / byte（100 KB・1 MB とも） | **1.617** | **0.671** |
| JSON 1 MB 認識（最小値、同一 JVM 交互） | 56.91 ms / 0.0569 µs/byte | **50.20 ms / 0.0502 µs/byte** |
| JSON 1 MB 認識の割当 / parse | 169.0 MB | **163.3 MB** |
| Operators 512 atom 認識（最小値） | 0.0865 ms | **0.0780 ms** |

**JSON の Java 認識は D-066 の前からサイズで平坦だった**（1 MB / 1 KB の µs/byte は before 1.00 /
after 0.99。§2.2）。Rust で平坦化を担った D-064 / D-065 は front の memo plan なので、Java は
`ProofKind` を文字列で読むだけで既に効いていた。D-066 が足すのは**サイズに依らない一律 10〜14%**である。

**JSON 1 MB の絶対値（同一走行・最小値）: ANTLR4 0.0107 / ubnfc Rust 0.0348 / ubnfc Java 0.0519 µs/byte。
Java は Rust の 1.49 倍、ANTLR4 の 4.85 倍**（§2.3）。

## 1. 何を移植したか

### 1.1 条件（Rust と同一）

front の `crates/ubnfc-front/src/analysis/choices.rs::exclusive` が証明するのは
「候補がすべて**非 nullable・trivia なし・capture site なしの単一 code point の case-sensitive literal**で、
先頭文字が EOF 込みで**互いに素**」。この証明が付いた選択だけ plan が `strategy=predict` /
`fallback=none` / `proof.kind=exclusiveCandidates` になる。

`JavaEmitter.exclusiveMiss()` はその 3 つ（strategy / fallback / proof.kind）を見たうえで、
**生成時にもう一度候補の形を確かめる**（literal / case sensitive / 1 code point / 先頭文字が重複しない）。
どれか 1 つでも崩れたら短絡を出さない。Rust 側 `expressions.rs::predict_literals` が
`ExprNode::Literal { case_sensitive: true, .. }` を自分で確かめているのと同じ二重化である。

### 1.2 生成されるもの

JSON の `Ws ::= { ' ' | '\t' | '\n' | '\r' }` の選択は

```java
private static Match e7C(Session s, Frame f) {
    if (s.exclusiveReady(f) && switch (s.cp(f.c)) { case 9, 10, 13, 32 -> false; default -> true; }) return s.exclusiveFail(f);
    return s.choice(f,K40,false,new boolean[]{true,true,true,true},false);
}
```

出るのは JSON で 2 か所（`Ws` と `Exp` の `[ '+' | '-' ]`）、P4 で 2 か所（`AddOp ::= '+' | '-'`、
`MulOp ::= '*' | '/'`）、Operators で 2 か所。**Rust backend が短絡する箇所と同じ**である。

### 1.3 健全性（なぜ観測が変わらないか）

`Session.exclusiveReady(f)` は `exclusive && !diag && !f.invert && (f.reset || f.c == f.m)`。

- **`!diag`**: 短絡するのは診断を 1 件も記録しない経路だけ。診断モードでは偽になるので、両経路は
  同じ機械語（元順の全候補試行）を通る。D-023 の二段構えにより、失敗・末尾入力は必ず診断モードで
  再解析されるので、公開される診断は参照経路のものと一致する。
- **`f.reset || f.c == f.m`**: 候補除外（`Guard`、`Prediction`）と同じ条件で、候補が literal を読む位置が
  `f.c` に確定する（`choice` は候補を `f.c = c0; f.m = reset0 ? c0 : m0` で呼ぶ）。
- **`!f.invert`**: 否定先読みの中では短絡しない（Rust の `!out.state.invert` と同じ）。

短絡しなかった場合に fast mode が残す観測は**到達位置 `reached` の更新だけ**である。候補は
`Session.literal` の `startsWith` で失敗し、`fail()` が `!diag` では `reached` を上げるだけで
（`f.advance(0)` の後 `choice` が `f.c` / `f.m` を戻す）、memo・scope・capture・event には触れない。
`Session.exclusiveFail(f)` はその `progressAt(f.c)` を 1 回だけ行って `null` を返す。

**参照経路への戻し方**: `-Dubnfc.exclusive=false`（`Session.exclusive = false`）。

## 2. 計測

共有機（AMD Ryzen 9 7950X / WSL2）で **load average 13〜29** の中を測っている。**最小値を主に読む**
（中央値も併記）。`taskset -c 28`、JVM は `-Xms2g -Xmx2g`、暖機 200 反復。

### 2.1 1 parse の操作回数（`examples/json/evidence/ops-json-49-java.csv`）

計数用の Session の複製に静的カウンタを入れて 1 parse を数えた（計時には使っていない）。
**100 KB と 1 MB で 1 byte あたりの回数は小数第 3 位まで一致する**（＝サイズに対して平ら）。

| 操作 | before / byte | **after / byte** | Rust（`2026-09-24-json-perf.md` §3.2） |
|---|---:|---:|---:|
| **literal 照合（`Session.literal`）** | **1.617** | **0.671** | 1.553 → 0.608 |
| 選択（`Session.choice`） | 0.786 | **0.550** | — |
| 排他 predict の短絡（`exclusiveFail`） | 0 | **0.236** | — |
| 文字クラス（`Session.range`） | 1.201 | 1.201 | — |
| 組込み token（`Session.builtin`） | 0.338 | 0.338 | — |
| 規則呼出し（`Session.rule`） | 0.867 | 0.867 | 0.866 |
| `Match` の生成（`Match.empty`） | 2.534 | 2.534 | — |

**消えた literal 照合は 1 byte あたり 0.946 回**（1.617 → 0.671）で、**Rust の 0.945 回（1.553 → 0.608）と
一致する**。短絡した回数 0.236 / byte は `Ws` の評価回数（Rust 報告の 23,638 / 100,039 = 0.236）と同じで、
`Ws` の反復の脱出が毎回 4 候補を空振りしていたことを裏づける。

### 2.2 速度（JSON 認識、`examples/json/evidence/speed-json-49-java.csv`）

**同一 JVM の中で `Session.exclusive` を 1 run ごとに反転**して交互に測った（system property
`-Dubnfc.exclusive` と同じ静的スイッチ）。暖機も両変種を交互に回して JIT に両方の分岐を見せている。

**session 1（9 run × 0.5 秒、load 29.1 → 19.9）— 中央値 ms / 最小値 ms**

| 入力 | before | **after** | 比（最小） |
|---|---:|---:|---:|
| json-1k (1,067 B) | 0.0762 / 0.0608 | **0.0652 / 0.0540** | **0.888** |
| json-10k (10,066 B) | 0.6742 / 0.6081 | **0.5962 / 0.5312** | **0.874** |
| json-100k (100,039 B) | 6.917 / 5.832 | **6.175 / 5.024** | **0.861** |
| json-1m (1,000,112 B) | 61.91 / 56.91 | **56.01 / 50.20** | **0.882** |

**session 2（11 run × 1.0 秒、load 29.1 → 18.7）**: 10k 0.6356 → 0.5708（0.898）、
100k 5.756 → 5.090（0.884）、1m 56.90 → 51.01（0.896）。1k は load 変動で最小値が 2〜4 倍に乱れたので読まない。

**session 3（別 JVM を `-Dubnfc.exclusive=true/false` で交互に 2 周）**: 100k 最小 5.823 → 5.204（0.894）、

**µs/byte（session 1 の最小値）とサイズ耐性**

| 変種 | 1 KB | 10 KB | 100 KB | 1 MB | 1 MB / 1 KB |
|---|---:|---:|---:|---:|---:|
| before | 0.0570 | 0.0604 | 0.0583 | 0.0569 | **1.00** |
| **after** | **0.0506** | **0.0528** | **0.0502** | **0.0502** | **0.99** |

**issue の見立て「Java の JSON 認識が Rust と同じくサイズで平坦になる」は、平坦化の部分だけ前提が違った**。
Java は D-066 の**前から平坦**である。Rust で平坦化を担ったのは D-064 / D-065 で、これは front の
`plan.memo.entries` の変更なので、`ProofKind` を文字列で読む Java backend には PR #46 の時点で
自動的に効いていた（`2026-09-24-json-perf.md` §1.4 の IR golden 差分が両 backend の生成物に入っている）。
D-066 が Java に足すのは**サイズに依らない一律 10〜14%**である。

**割当**: 1 MB で 169,019,024 → 163,343,768 B（**−5,675,256 B**）。
これは `236,469 回（短絡した回数）× 24 B`（`new boolean[]{true,true,true,true}` 1 個）と**ぴったり一致**する。
Java backend の predict 選択は `eligible` 配列を呼出しごとに確保しており、短絡するとその確保ごと消える。

## 3. 申し送り — Java だけの回数の異常（本 PR の範囲外）

§2.1 の計数で D-066 と無関係な項が 1 つ目立つ。**認識専用経路でも、成功した終端 1 つごとに
`Match` record を 1 個作っている**。

- json-1m 1 parse で **`Match.empty` 2,533,873 回（2.53 / byte）**。D-066 の on / off で不変。
- 同じ parse の割当は **163,343,768 B** で、`163,343,768 / 2,533,873 = 64.5 B / Match`。
  **割当のほぼ全部が `Match` である**（`Match` は 8 参照 + 2 int + boolean の record）。
- 同じ入力の ubnfc Rust は 76,557,120 B（arena。Java の 0.47 倍）、ANTLR4 は 27,067,376 B（同 0.17 倍）。

`Session.literal` / `range` / `builtin` は成功のたびに `Match.empty(at, at + len)` を返すが、
**認識専用（`!tree`）では中身（nodes / local / captures / traces / recoveries / items / values）は
すべて空の共有 `List.of()` で、使われるのは `start` / `end` だけ**である。ここは「区間 2 本を
long 1 個に詰める」か「失敗を `null`、成功を `Frame` の前進だけで表す」形に畳める見込みがあるが、
`Match` は連接・反復・capture・左因数分解の全経路が返り値として使う型なので、契約
（`04-cursor-and-diagnostics-contract.md`）の検討込みで別 issue にする。
