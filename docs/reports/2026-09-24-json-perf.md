# JSON の認識性能 — `defaultSafe` 15 式の始末と 1 byte あたりの単価（issue #33）

2026-09-24。issue [#33](https://github.com/opaopa6969/ubnfc/issues/33)。前提は
[`2026-09-24-antlr-treesitter-comparison.md`](2026-09-24-antlr-treesitter-comparison.md) §3
（JSON の µs/byte がサイズで 4 倍悪化する。原因は memo で、`memo:false` にすると平らになる）と
[`2026-09-24-memo-plan.md`](2026-09-24-memo-plan.md)（D-058 の再入判定）。

## 0. 結論

**JSON 1 MB の認識は 0.2148 → 0.0305 µs/byte（7.0 倍）**になり、**µs/byte は入力サイズで平ら**
（1 KB 0.0291 → 1 MB 0.0305、**1.05 倍**。issue の条件 ≤1.2 倍を満たす。§2 の走行の最小値）。
**ANTLR4 比は 21 倍 → 2.7 倍**（ANTLR と交互に測った別走行の最小値。§2 末尾）。
**issue の目標 ≤0.022 µs/byte（ANTLR の 2 倍以内）には届いていない**。残ったギャップの内訳は §3 の
回数 × 単価の表にあり、**単価ではなく回数**（scannerless PEG が 1 byte あたりに評価する式の数）である。

効いた手は 3 つで、すべて**観測（受理・AST・診断）を 1 bit も変えない**。

| # | 手 | 決定 | JSON 1 MB µs/byte（最小値） |
|---|---|---|---:|
| 0 | before（`origin/master` 75dec71） | — | 0.2148 |
| 1 | 再入判定に mayStart の素性を足す（`Pos∩Pos` の絞り込み） | **D-064** | 0.0757 |
| 2 | 本体が終端走査だけの規則には memo を入れない | **D-065** | 0.0457 |
| 3 | 排他 predict が外れたら候補を 1 つも試さずに失敗する（fast mode） | **D-066** | **0.0305** |

不採用: **位置ごとの字句 cache（`lexical_cache`、既定 off）は JSON でも負ける**（§4.3）。

## 1. Part 1 — `defaultSafe` の 15 式

JSON IR の `plan.memo.entries` は 117 式のうち 102 式を証明付きで省き、残り 15 式が `defaultSafe` だった。
**15 式は全部「rule 本体」**で、16 規則のうち `Json` 以外のすべてである。

| # | 規則 | 旧判定の根拠（なぜ残っていたか） | 新しい始末 |
|---|---|---|---|
| 1 | `Value` | `Value ::= Object \| Array \| String \| Number \| True \| False \| Null` の候補どうしを `Pos∩Pos` で衝突とみなしていた。候補 `Object` の内部は開始位置より後で `Ws`・`Value`・`Member`… を試し得て、候補 `Array` の内部も同じ集合を試し得るので、全規則が交わる | **D-064 で消える** |
| 2 | `Object` | 同上（`Value` の候補として） | **D-064** |
| 3 | `Member` | 同上 | **D-064** |
| 4 | `Array` | 同上 | **D-064** |
| 5 | `String` | 同上 | **D-064** |
| 6 | `Char` | `Value` 候補 `Array` と `String` の `Pos∩Pos` | **D-064** |
| 7 | `Escape` | 同上 | **D-064** |
| 8 | `Number` | `Value` 候補 `Object` と `Array` の `Pos∩Pos` | **D-064** |
| 9 | `Int` | `Value` 候補 `Array` と `Number` の `Pos∩Pos` | **D-064** |
| 10 | `Frac` | 同上 | **D-064** |
| 11 | `Exp` | 同上 | **D-064** |
| 12 | `True` | `Value` 候補 `Object` と `Array` の `Pos∩Pos` | **D-064** |
| 13 | `False` | 同上 | **D-064** |
| 14 | `Null` | 同上 | **D-064** |
| 15 | `Ws` | **本物の再入**。`[ Member { Ws ',' Ws Member } Ws ]` の反復は脱出のとき本体をもう 1 度試す（位置 p で `Ws` が成功し `','` で失敗して巻き戻る）ので、続く末尾の `Ws` が同じ位置 p で 2 度目に評価される。`Zero∩Zero` の衝突は正しい | D-064 では**消せない**。**D-065 で消える**（本体が終端走査だけなので割に合わない） |

### 1.1 D-064 — 同じ開始位置の兄弟は「同じ 1 文字目」を消費しない限り `Pos` で衝突しない

D-058 は「同じ位置から評価され得る兄弟の組」について `Zero∩Zero` と `Pos∩Pos` の両方を衝突として数えていた。
`Pos∩Pos` は「両方が開始位置より**先**へ進んで、そこで同じ規則を踏み直す」形だが、入力は 1 本なので
**両方が先へ進むには同じ 1 文字目を消費するしかない**。`mayStart`（`Facts::chars`、
front が既に持っている**必要条件の上界**）が交わらない兄弟は、片方が 1 文字でも消費できる入力では
他方は開始位置から 1 文字も動けない（動くにはその文字を消費する終端が要る）。よって `Pos∩Pos` は起こらない。

上界なので「交わらない」は実際に交わらないことを含意する。判定不能（Extern / recovery / regex）は
`chars` が全 code point になるので交わる側に倒れ、安全方向は保たれる。`Zero∩Zero` は開始位置での衝突
なので絞らない。実装は `crates/ubnfc-front/src/analysis/reentry.rs` の `may_share_prefix`（4 行）。

JSON では `Value` の 7 候補が `{` `[` `"` `-`/数字 `t` `f` `n` で互いに素なので、14 規則がまとめて落ちる。

### 1.2 D-065 — 本体が終端走査だけの規則に memo は割に合わない

`Ws ::= { ' ' | '\t' | '\n' | '\r' }` は本当に同じ位置へ再入する。しかし **memo の hit で省けるのは
「同じ位置で同じ終端列を走査し直す」ことだけ**で、計算量の階級は変わらない。一方、**保存は評価のたびに
必ず払い**、表は入力長に比例して育つ。JSON 1 MB の実測で `Ws` は **hit 34,348 / 保存 202,121**（hit 率 17%）、
その代金は **0.0457 → 0.0757 µs/byte**（§4.1 の A/B。memo を `Ws` だけに絞ってもまだ 1.66 倍）。
hit 1 回で省ける仕事は「空白 1 文字ぶんの走査」なので、明らかに負ける。

そこで「再入し得る」に加えて「**本体の局所木が規則呼出しへ到達する**」を要求する。到達しない
（＝終端走査だけで再導出が終わる）規則は memo を入れない。走査長が静的に分からない token
（`REGEX` / `UNTIL` / Extern）は「終端だけ」に数えない。scope / recovery / Extern の効果を持つ本体は
D-058 のとおり保持側に倒したまま。`MemoEntryReason::ProvedOmission` +
新しい `ProofKind::unprofitableTerminalScan` を付ける。

これは**証明ではなく計画上の判断**なので、全 fixture 文法で A/B した（§4.2）。P4 は 118 → 102 規則になり、
**悪化しない**（complex-x64 認識の最小値 6.062 → 4.903 ms、hit 10,564 → 10,372）。

仕込み**、落とす規則が 1 度も hit しないことを確かめた（commit していない一時計測）。

| 文法 | 入力 | 落とす規則 | **落とした規則の hit** | 残す規則の hit |

| `mixed-values/Shared.ubnf` | 記号 `f s a x y 😀 z` 上の長さ 3 以下の全文字列 400 件 | `LeafRule`（D-064） | **0** | — |

## 3. Part 2 — 1 byte あたりの操作回数（ubnfc と ANTLR4）

### 3.1 数え方

- **ubnfc**: 生成 Rust（json-100k / json-1m）の複製に計数フックを入れて 1 parse を数えた
  （commit していない一時計測。計時値は乱れるので別走行）。100 KB と 1 MB で **1 byte あたりの回数は
  小数第 3 位まで一致**する（＝サイズに対して平ら）。
- **ANTLR4**: 同じ入力を `Parser.setProfile(true)` / `getParseInfo()` と `ParseTreeListener`
  （`setBuildParseTree(false)` のまま `addParseListener`）で数えた。字句側は「1 文字 = DFA 遷移 1 回」と数える。

### 3.2 回数（json-100k、1 byte あたり）

| 操作 | before（`origin/master`） | Part 1 後 | **本 PR** | ANTLR4 |
|---|---:|---:|---:|---:|
| 字句 DFA 遷移 | — | — | — | **1.000** |
| token 生成 | — | — | — | 0.204 |
| parser の規則呼出し | 0.866 | 0.866 | 0.866 | **0.137** |
| parser の token 照合 | — | — | — | 0.204 |
| **適応予測（`adaptivePredict`）** | — | — | — | **0**（JSON は LL(1) 相当で 1 度も呼ばれない） |
| 式関数の評価 | 5.47 | 5.465 | **4.520** | — |
| 終端照合 `primitive` | 2.528 | 2.528 | **1.583** | — |
| ├ literal 照合 | 1.553 | 1.553 | **0.608** | — |
| └ 文字クラス token | 0.976 | 0.976 | 0.976 | — |
| 文字読み `cp_at` | 1.752 | 1.752 | 1.752 | — |
| `starts_with` | 1.553 | 1.553 | **0.608** | — |
| `mark` | 2.757 | 2.757 | 2.757 | — |
| `restore` | 3.296 | 3.296 | **2.115** | — |
| cursor 更新（`begin`+`commit`+`advance`） | 8.466 | 8.471 | **6.581** | — |
| memo 保存 | **0.832** | 0 | 0 | — |
| memo hit | 0.034 | 0 | 0 | — |
| event 呼出し（認識では即 return） | 2.154 | 2.154 | 2.154 | — |
| display / diag 呼出し（fast mode では機械語から消える） | 11.07 | 11.07 | 8.80 | — |

（`before` 列の memo 以外は Part 1 後と同じ。memo を切ること自体は回数を減らさず、**表の局所性**で効く。）

### 3.3 回数 × 単価

| 実装 | 実測 µs/byte（1 MB 最小） | 実質的な操作 / byte | 1 操作あたり |
|---|---:|---:|---:|
| ANTLR4 | 0.0114 | **1.34**（DFA 遷移 1.00 + token 0.204 + 規則 0.137） | **8.5 ns** |
| ubnfc Rust（本 PR） | 0.0312 | **19.3**（式評価 4.52 + 終端 1.58 + 文字読み 2.36 + mark/restore 4.87 + cursor 6.58 + 規則 0.87 — event/display は除く） | **1.6 ns** |

**単価差ではない。** ubnfc の 1 操作は ANTLR の 1/5 の値段で回っていて、**回数が 14 倍**多い。
最大項は「式関数の評価 4.52 / byte」と「cursor 更新 6.58 / byte」で、どちらも
**scannerless PEG が 1 文字ごとに文法そのものを歩く**ことから出る:

- **文字列の本体**: `String ::= '"' ( { Char } ) '"'`、`Char ::= Escape | SAFE` は
  **文字列 1 文字につき規則呼出し 1 回 + 選択 1 回 + 終端 1 回 + mark/restore 1 組**を払う。
  json-100k で `Char` の評価は 32,496 回（0.325 / byte）＝全規則呼出し 86,651 回の **37%**。
  ANTLR は同じ文字列を字句 DFA の連続遷移 1 本で食べ、パーサには token 1 個しか渡らない。
- **数値**: `Number ::= ( [ '-' ] Int [ Frac ] [ Exp ] )` は入れ子の Optional 3 段で、
  `Frac` の先頭 token だけで 10,956 回（0.110 / byte）試される。
- **空白**: `Ws` は 23,638 回（0.236 / byte）呼ばれ、**呼ばれるたびに反復の脱出で選択が 1 回失敗する**。
  ここが D-066 の対象だった（§3.4）。
- **trivia の試行**: JSON の文法は `@whitespace: none` なので**暗黙 trivia の試行は 0 回**である
  （issue が挙げた候補のうち、これだけは JSON では最初から費用になっていない）。

### 3.4 D-066 — 排他 predict が外れたら候補を 1 つも試さない

`Ws ::= { ' ' | '\t' | '\n' | '\r' }` の選択は front が **`exclusiveCandidates`** を証明していて、
plan は `strategy=predict` / `fallback=none` になっている。ところが生成コードは、予測が
「どの候補の先頭文字でもない」（`predicted == usize::MAX`）ときに**元順で 4 候補すべてを試して失敗**していた。
json-100k で `Ws` の反復は 28,924 回まわり、その大半が 4 回の literal 照合を空振りしていた
（literal 照合 155,353 回のうち約 99,800 回、**1 byte あたり 1.0 回**）。

`exclusiveCandidates` は「候補はすべて 1 文字の case-sensitive literal、nullable でなく trivia も無く、
先頭文字が互いに素」を意味するので、**予測が外れた時点で全候補の失敗が確定する**。
fast mode（D-023、`Session::<false>`）は display も主診断 DAG も記録しないので、その走行が残す観測は
**無い**——失敗そのものだけが結果に効く。したがって候補を 1 つも呼ばずに同じ失敗を返せる。
診断モード（`Session::<true>`）は従来どおり元順で全候補を走らせるので、**観測は構成上 byte 一致**。
`ParseOptions::predict = false` で参照経路へ戻せる。

実装は `crates/ubnfc-rust/src/expressions.rs` の `predict_literals`（1 行の生成）。JSON では
`Ws` の選択と `Exp` の `[ '+' | '-' ]` の 2 か所に出る。効果は literal 照合 1.553 → 0.608 / byte、
`restore` 3.296 → 2.115 / byte、式評価 5.465 → 4.520 / byte で、**1 MB 0.0457 → 0.0305 µs/byte**。

## 4. 採った手・採らなかった手（1 手ずつ A/B）

### 4.1 D-064 / D-065 の分離（JSON）

`taskset -c 30`、同一 binary に 4 変種の生成 parser を link して入力ごとに交互実行（§2 の表）。
D-065 だけを取り出すと **1 MB 0.0757 → 0.0457 µs/byte（0.60 倍）**。これは実行時 `memo=false` と同値で、
同じ走行での対照（`D-064 + 実行時 memo off`）が 0.0473 µs/byte だったのと一致する。

### 4.2 D-065 が他の文法を壊さないこと（P4 = 「memo を切ると 67 倍」の文法）

`examples/p4-rust` の bench を **before / after の 2 binary で交互に 6 周**（`taskset -c 30`、5 サンプル中央値）。
D-065 で P4 は 118 → 102 規則になり、memo hit は complex-x64 で 10,564 → 10,372（−1.8%）、
memo entry は 35,362 → 29,341（−17%）。

| large-match | 認識 | 0.605 / 0.456 | **0.385 / 0.363** |

**最小値はすべて after が同じか速い**（唯一 comparison-heavy-x64 AST が +1.3% で、これは雑音の幅）。
P4 の塔（`Expression` → `NumberExpression` → … → `VariableRef` / `MethodInvocation`）は残っており、
`crates/ubnfc-front/tests/memo_plan.rs` がそれを固定している（`AddOp` / `MulOp` は
終端走査だけなので塔の一覧から外し、落ちる 22 規則を証明の種別つきで列挙した）。

### 4.3 採らなかった: 位置ごとの字句 cache（`lexical_cache`、既定 off）

[`2026-09-23-p4-rust-lexical-cache.md`](2026-09-23-p4-rust-lexical-cache.md) は P4 で負けた理由を
「リテラルが 1〜2 byte で、cache を引くほうが命令数が多い」と書いていた。**JSON なら文字列や数値が
長い run なので結論が変わり得る**——という issue の見立てを測った。

| 入力 | cache off µs/byte（中央値 / 最小） | cache on（中央値 / 最小） | on/off（最小） |
|---|---:|---:|---:|
| json-1k | 0.0552 / 0.0488 | 0.0704 / 0.0659 | **+35%** |
| json-10k | 0.0567 / 0.0529 | 0.0654 / 0.0563 | **+6.4%** |
| json-100k | 0.0715 / 0.0690 | 0.0792 / 0.0726 | **+5.3%** |
| json-1m | 0.0553 / 0.0487 | 0.0564 / 0.0519 | **+6.5%** |

**JSON でも負ける。**理由は測ると明快で、**cache が覆うのは ASCII の literal だけ**であり、
JSON の「長い run」は literal ではなく **token**（`SAFE = NEGATION('"\\')`、`DIGIT`、`XDIGIT`、
`CHAR_RANGE`）で食べているからである。JSON の literal は `{` `}` `[` `]` `,` `:` `"` `\` と
`true` / `false` / `null` だけで、P4 と同じく**大半が 1 byte**。
既定は off のまま、この結果を報告に残す（P4 の判断が JSON でも変わらないことの確認）。

### 4.4 やらなかった（次の issue にする）

- **文字クラスの一括走査**。`{ Char }` のような「1 文字の規則の反復」を、生成側で run 単位の
  走査へ畳む。json-100k の規則呼出し 86,651 回のうち 32,496 回（37%）がこれで消える見込みだが、
  規則ごとの event / 診断の記録位置が変わるので、契約（`04-cursor-and-diagnostics-contract.md`）の
  検討込みで別 issue。
- **数値の DFA**。`Number` の入れ子 Optional 3 段を 1 本の走査にする。同じ理由で別 issue。
