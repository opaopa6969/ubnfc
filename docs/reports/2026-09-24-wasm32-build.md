# wasm32 ビルド対応（issue #65 / D-070 の追記）

2026-09-24。issue [#65](https://github.com/opaopa6969/ubnfc/issues/65)。

## 0. 結論

D-070（#35、PR #63）の native stack 番兵エスカレーション（`std::thread::scope` /
`Builder::spawn_scoped`）は `wasm32-unknown-unknown` に `std::thread` が無いため、
生成 Rust parser がそもそもコンパイルできなかった。エスカレーション実装を
`#[cfg(not(target_arch = "wasm32"))]` / `#[cfg(target_arch = "wasm32")]` の 2 実装に
分け、wasm32 側は専用 thread を起こさず、番兵budget（`NATIVE_STACK_SENTINEL_BYTES`）
での再解析結果——既に `"maximum parse depth exceeded"` が入った診断——へそのまま
fallback する（crash しない。D-070 の契約は変えない）。**native の実装・挙動・
既存テストは無変更**。

**wasm32 で 3 クレートのビルドが通る**: `examples/p4-rust`（`--lib`）、
`crates/ubnfc-selfhost`（`--lib`）、`examples/json`（都度生成、JSON Lines driver bin 込み）。

## 1. 変更点

`crates/ubnfc-rust/src/emit.rs` が生成する `parser.rs` のうち、escalation を持つ
2 関数を分割した:

- `parse_with_options` の escalation 部分 → 新しい private 関数
  `parse_with_options_escalated` に切り出し、native / wasm32 の 2 実装を用意
- `parse_entry_escalated`（`parse_entry_with_options` から呼ばれる）も同様に
  native / wasm32 の 2 実装を用意

wasm32 側の実装は、native stack 番兵の budget（`NATIVE_STACK_SENTINEL_BYTES` =
256 KiB 相当）のまま `parse_with_options_budget` / `parse_entry_budget` を呼び直すだけ
（thread を起こさない）。呼出し元・引数・戻り値の型は native 側と同一。

`crates/ubnfc-rust/driver.rs`（scanner 変種）と `examples/p4-rust/build.rs` が
`/*STACK_ESCALATION*/parse_entry_escalated(grammar,entry,text,options)/*STACK_ESCALATION*/`
という呼び出し箇所の文字列を丸ごと `Ok(result)` に置換する既存の仕組みには触れていない
（`parse_entry_escalated` の**定義**だけを分割したので、呼び出し側の文字列は不変）。

生成物（`crates/ubnfc-selfhost/src/generated/parser.rs`、
`examples/p4-rust/src/generated/parser.rs`）は手で編集せず、`ubnfc-rust` CLI で同じ
IR から再生成し、`tests/regenerate.rs`（byte 一致の golden test）で確認した。

## 2. wasm32 ビルド確認

`scripts/check-wasm32.sh`（ローカルで再現可能。`rustup target add
wasm32-unknown-unknown` を自動で行う）:

```
cargo build --release --target wasm32-unknown-unknown -p ubnfc-p4-rust --lib      # OK
cargo build --release --target wasm32-unknown-unknown -p ubnfc-selfhost --lib     # OK
# examples/json: ubnfc / ubnfc-rust CLI で都度生成した driver crate（bin 込み）を
# 同じ target でビルド                                                            # OK
```

`examples/p4-rust` と `ubnfc-selfhost` は生成 parser をライブラリ module として
埋め込む構成（driver bin なし）なので `--lib` でビルドする。`examples/json` は
committed crate ではなく、PR #32 の bench 手順
（`benchmarks/scripts/prepare-external.sh`）と同じ流儀で `ubnfc` / `ubnfc-rust`
CLI から都度生成する。JSON Lines driver bin 込みで生成すると実際にリンクされる
`.wasm` ができるので、そのサイズを測った。

## 3. wasm サイズ（examples/json 生成 driver bin、release）

| ビルド | サイズ |
|---|---:|
| `--release`（既定 opt-level） | 610,299 bytes |
| `--release` + `-C opt-level=z`（`cargo rustc` での one-off 上書き。Cargo.toml のprofileは変更していない） | 606,430 bytes |

opt-level=z の効果は約 0.6%（このドライバは JSON Lines の小さい read/write ループが
support code の大半で、生成 parser 本体の割合が小さいため差が小さい）。

`examples/p4-rust` / `ubnfc-selfhost` は `--lib` ビルド（driver bin を持たない
embedded module 構成）なので、リンク済み `.wasm` は生成されない（`.rlib` のみ）。

## 4. CI

`.github/workflows/ci.yml`（このリポジトリに CI が無かったので新規追加）:

- `wasm32` job: 上記 3 クレートを `wasm32-unknown-unknown` でビルドする。これが
  issue #65 の受け入れ条件に対する merge-blocking gate
- `native` job: `cargo test --workspace` を実行する。ただし多くのテストが sibling の
  private repo `unlaxer-parser`（`UNLAXER_PARSER_DIR`、既定 `../../../unlaxer-parser`）
  を前提にしており、cross-repo checkout 用の token が未整備なため、今回は
  `continue-on-error: true` の informational job にとどめた（issue #65 の範囲外。
  follow-up として残す）。native/corpus の無退行は本 PR ではローカルで検証している
  （§5）

  （`crates/ubnfc-rust/tests/support/review_assertions.rs::recursion_aborts_optional_and_recovers_next_call`、
