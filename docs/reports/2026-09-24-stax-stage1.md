## 0. 何をしたか

owner の指示は「型定義、構造定義の出来る言語を定義してみたい。簡易言語というわけではなく
forth みたいな自己拡張型言語」。これを **UBNF の 3 つ目の実用文法**かつ
**UBNF/ubnfc の限界試験**として作った。

- 言語名は **`stax`**（stack + syntax）。対抗は `kumiki`（組木）と `catena`。理由は DESIGN §2。
- 文法 `examples/stax/stax.ubnf`（UBNF v2、**27 規則**）が `validate --strict` を
  **エラー 0 / 警告 0** で通る（`W-CHOICE-*` もゼロ）。
- サンプル **20 本**（受理 16・拒否 4）が **Rust backend と Java backend で
  受理・canonical AST・スコープ診断すべて一致**。
- Grammar IR の golden を `ir/examples/stax.ir.json` に commit し、
  `crates/ubnfc-front/tests/pipeline_golden.rs` に 3 本の試験を足した。

## 1. 言語の骨格（結論だけ）

```
: square ( Int -- Int ) dup * ;          // 語の定義。( 効果 ) は型付き
struct Point { x: Int y: Int }           // 構造定義。フィールドは宣言
type Color = | Red | Green | Blue ;      // 和（列挙）。先頭の | は必須
type Meters = Int ;                      // 別名（透過）
: if_else ( Bool [ -- ] [ -- ] -- ) choose call ;   // 制御構造は組込みではない
```

- **連接スタック言語**。語を並べると合成。
- **制御構造は言語の中で定義する**。組込みは `choose` / `call` / `recurse` の 3 つだけで、
  `if` / `if_else` / `while` / `times` は `samples/04-prelude.stax`（32 行）が全部。
- **スタック効果は宣言**であって推論結果ではない。検査規則は DESIGN §4.3。

## 2. 「文法だけで記号表が出る」ことの確認

`@scopeTree(mode=lexical)` 3・`@declares` 8・`@symbolRef` 4 を書いただけで、
記号表のコードを 1 行も書かずに次が出る（`samples/18-undefined-word.stax`、実測）:

```
: uses_missing ( Int -- Int ) not_defined_anywhere later_word ;
: later_word   ( Int -- Int ) 1 + ;
```

```
accepted=true allConsumed=true
WARNING at 233: 未定義のシンボル: 'not_defined_anywhere'
WARNING at 256: 未定義のシンボル: 'later_word'
```

**構文は成功したまま未定義参照だけが WARNING で出る**。両 backend で位置も文言も一致した。

### 2.1 いちばん面白かった一致 — Forth の smudge bit と UBNF の宣言登録

UBNF は `@declares` の登録を**規則を抜けたあとに親スコープへ**行う。
`WordDef` に `@scopeTree` と `@declares` を両方付けると、

- 語名はファイルスコープに入る（外から見える）
- **本体からは自分の名前が見えない**

が同時に出る。これは Forth が `;` を実行するまで定義中の語を辞書から隠す
**smudge bit とまったく同じ意味**である。だから stax の自己再帰は Forth と同じく
`recurse` で書く。**言語の意味論と UBNF の scope 意味論が偶然ではなく一致した**箇所で、
この言語がこの形に落ち着いた理由の一つになった。

## 3. UBNF のどの機能が効いたか

| 機能 | 効き方 |
|---|---|
| **語境界（D-040）** | **この文法の生命線**。組込み語 29 本と組込み型 4 本をリテラルで並べ、利用者定義語を `IDENTIFIER` にする、という設計全体がこれに乗っている。`dup` が `duplicate` を、`Int` が `Integer` を横取りしない。**v1 の既定（`none`）ではこの文法は成立しない** |
| **到達不能候補の検査（D-037）** | 組込み語 29 本が 1 つの順序付き選択。`'<'` を `'<='` より前に置くといった誤りが `--strict` で止まる。CI の条件にした |
| **中立な token 語彙（D-041）** | `IDENTIFIER` / `NUMBER` / `DOUBLE_QUOTED` / `END_OF_INPUT` の 4 つだけで足りた。**extern token はゼロ**なので `--extern-first-chars` も要らない |
| `@scopeTree` / `@declares` / `@symbolRef`（D-046 の v2 綴り） | §2 のとおり |
| `@mapping` 27 箇所 | 選択だけの規則（`TopLevel` / `Term` / `TypeRef`）にも付けて sealed interface + record の和型にした |
| `@catalog` 6 箇所 / `@doc` 17 箇所 | stage 4（LSP）の補完カタログと hover。**種別ごとに context を分けた**ので、型の位置に語が出ることがない |

**使わなかった v2 の目玉**:

- **左再帰（D-039）**: 連接言語に演算子の優先順位が無い。`3 4 +` は並びであって式木ではない。
  UBNF v2 の最大の機能が 1 度も要らない文法として、P4（式言語）・JSON（データ形式）と
  性格の違う 3 本目になった。
- **パラメータ化ルール（D-043）**: 同じ形の繰り返しが無い。
- **code point クラス（D-063）**: 文字列は組込み token に任せた。

## 4. 自己拡張の境界 — Forth の parsing word 3 例

DESIGN §5.3 の表を要約する（詳細は同節）。

| Forth | stax での扱い | 分類 |
|---|---|---|
| `( … )` | 固定構文にした（`Effect` 規則 + `//` `/* */` の trivia） | **書けた** |
| `."` | 字句（`DOUBLE_QUOTED`）+ 語 `print` + macro で代替。「入力を読む」部分が字句の仕事に移っただけ | **quotation + macro で代替** |
| `CREATE … DOES>` | **不可能**。(1) `42 constant answer` を読むには「`constant` は defining word」と知る必要があり、これは意味述語＝UBNF が入れないと決めたもの。(2) `CREATE` は実行時に辞書へ名前を足すが、UBNF のスコープはそのファイルの構文解析中にしか構築されない | **不可能（§5 の X1〜X3 が要る）** |

第 2 案（UBNF に何を足せば書けるか）は DESIGN §5.4 に 3 段で書いた。要点:

| | 要るもの | 契約への影響 | 推奨 |
|---|---|---|---|
| X1 | 実行系が供給する語彙を解析時のスコープへ注入する口（`--vocabulary` / `@catalog` の入力側利用） | **無し**（受理は変わらず診断だけ変わる） | **やる価値がある。stage 5 で起票** |
| X2 | 実行時に定義される字句クラス（`extern … volatile`） | D-013「終端は (入力, 位置) の純粋述語」を版付き無効化で緩める必要がある | 書けるが高い |
| X3 | 語彙に依存して構文の形が変わること | 意味述語そのもの。**入れないと決めた**（06 §4） | **入れない**。固定構文（`define <defining-word> <name> … ;`）で代替 |

## 5. 見つかった 2 つの落とし穴

### 5.1 `NUMBER` token を直接 capture すると両 backend の AST が食い違う

`@mapping` の field へ `NUMBER @text` と**直接** capture すると、

- Rust backend: `"text": "3"`（字句の文字列）
- Java backend: `"text": 3`（`int` へ変換。driver 契約の `java_int`）

となり canonical AST が一致しない。20 本中、数値リテラルを含む **16 本すべて**が食い違った。
`examples/json/json.ubnf` と同じく **group を 1 つ挟む**と両者とも原文の文字列になり、一致する。

```ubnf
NumLit ::= ( NUMBER ) @text ;   // NUMBER @text ではなく
```

これは D-011 の「Numeric は Rust=rust_lexeme / Java=java_int」という**既知の分岐**が
canonical AST に漏れている形で、契約違反ではない。ただし**文法を書く側からは見えない**ので、
`examples/stax/README.md` と本報告に書き留めた。
`@mapping` の field 型に「原文のまま」を指示する手段があると避けやすい（将来の課題）。

### 5.2 `@recovery` は順序付き選択の非末尾候補から到達する規則に置けない

最初 `WordDef` に `@recovery(sync=';')` を付けたところ、**正しいプログラムが壊れた**（実測）。

`TopLevel ::= UseDecl | WordDef | MacroDef | StructDef | TypeDef` では、
`struct Point { … }` を読むときも**まず `WordDef` が試されて失敗する**。`@recovery` は
その失敗を回復として拾うので:

- `struct` で始まるファイルが「`WordDef` の回復」として受理され、**宣言が 1 つもスコープに入らない**
- わざと壊した `17-bad-syntax.stax` が**受理されてしまう**

> **一般則**: `@recovery` は、**順序付き選択の最後でない候補から到達する規則には置けない**。
> その規則の失敗は「誤りである」ではなく「次の候補を試せ」の意味だからである。

現状の UBNF はこれを検証していない（`@recovery` の実言語での使用は 0 件なので露出していない）。
**`W-RECOVERY-IN-CHOICE` 相当の警告を出せるはず**で、issue #71 として起票した。
stax 側は `@recovery` を 1 つも使わないことで回避した。
