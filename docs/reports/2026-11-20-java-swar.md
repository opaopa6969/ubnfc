# Java の一括走査を portable SWAR で比較する（issue #29）

固定 JSON 1 MB の認識は交互 7 周の中央値で **19.277764 → 34.107364 ms（0.565 倍）**。D-080 後比 1.5 倍の目標には届かなかった。既定は scalar とし、`--swar` で候補を試せるようにした。短区間の費用の切り分けと再評価は [#68](https://github.com/opaopa6969/ubnfc/issues/68) に残す。

## 実装

D-080 の一括走査は、front が `plan.scans` で証明した終端領域を走査関数へ畳む。今回の変更は、その中の上限なし文字クラス反復の内側に限る。生成時の `ubnfc-java --swar` で候補版を選び、既定の生成は従来の scalar とする。

許容 ASCII 集合か、その補集合（非 ASCII を含む）の少ない方を最大 3 区間の比較として生成する。4 つの UTF-16 コード単位を入力位置順に `long` の下位から格納し、各 16 bit lane の上位 bit を番兵にした減算で区間を判定する。不一致 mask があれば `Long.numberOfTrailingZeros(mask) >>> 4` 個の一致を反復数に加え、最初の不一致位置を従来の code point 判定へ渡す。非 ASCII は word 経路で常に不一致となるので、surrogate pair を分割しない。末尾 3 コード単位以下と区間の多い表にも従来の走査を使う。両経路とも同じ停止位置から既存の escape 等の選択肢を試す。

生成物は JDK 17 の標準 API と `char[]` を使う。固定シフトで lane 順を決めるため、CPU のエンディアンに依存しない。実機検証は x86_64 で行った。

## 計測方法

比較基準は #66 と #47 を含む `a990dac`。基準と候補の生成器に同一の JSON、P4、Operators の IR を与えた。固定 JSON は JSONTestSuite `1ef36fa01286573e846ac449e8683f8833c5b26a` から既存の手順で作る 1,000,112 byte。JSON と Operators 512 atom の SHA-256 は D-080 の入力と一致した。P4 6 fixture は作業ブランチ内の固定入力で、両側とも同一のファイルを読む。

Ryzen 9 7950X、WSL2、Oracle JDK 21.0.9、論理 CPU 28 に固定。各 JVM は `-Xms512m -Xmx512m -Xss16m -XX:+UseSerialGC -XX:ActiveProcessorCount=1`。同一セッションの 7 周で、各対象について毎周 JVM を別々に起動し、奇数周は scalar → SWAR、偶数周は逆順とした。JSON と Operators の認識は既存の `UbnfcRunner` で暖機 200 回（20 秒上限）、計時は 0.5 秒相当に較正して各 JVM 1 値。P4 の認識は既存の `Benchmark` の `recognize-fast` で、1 fixture あたり暖機 200 回、各 JVM 5 値。P4 の 4 fixture は既定の Formula、comparison-heavy の 2 fixture は BooleanExpression を入口とした。表は計時値をすべて含める。各 JVM の起動前後の `uptime`、反復数、各計時値は生データに掲載する。

- [準備と入力のハッシュ](2026-11-20-java-swar-data/prepare.txt)、[入力照合で中断した初回](2026-11-20-java-swar-data/prepare-first.txt)
- [各周の時間と uptime](2026-11-20-java-swar-data/time.txt)
- [計装版の word 判定回数](2026-11-20-java-swar-data/profile.txt)

最初の準備では、JSON 生成スクリプトが出力しない Power なども含めてハッシュ一覧の全体を照合したため中断した。対象入力のハッシュで検証するよう修正した。次の準備は生成・コンパイル・ハッシュ出力の後、実行中のスクリプトへの計装手順の追記により末尾で構文エラーになった。固定後の構文と生成ソースの一致を再確認し、完成済みの同じクラスで `time` を単独実行した。いずれの準備の中断時にも計時値は出ていない。

比較データの生成と実行には JDK 21、Maven、Python 3、`rg` と `taskset` を使用する。再現する場合は本 PR を含む checkout で実行する。

```bash
work=$(mktemp -d)
git init -q "$work/suite-repo"
git -C "$work/suite-repo" fetch -q --depth 1 https://github.com/nst/JSONTestSuite.git \
  1ef36fa01286573e846ac449e8683f8833c5b26a
mkdir "$work/suite" "$work/ab"
git -C "$work/suite-repo" archive FETCH_HEAD | tar -x -C "$work/suite"
export WORK="$work/ab"
BASE_REF=a990dac JSON_TEST_SUITE="$work/suite" benchmarks/scripts/run-java-swar-ab.sh prepare
CORE=28 ROUNDS=7 benchmarks/scripts/run-java-swar-ab.sh time | tee "$work/time.log"
benchmarks/scripts/run-java-swar-ab.sh profile
```

## 計測結果

値は 1 parse あたりの ms。倍率は scalar の中央値を SWAR の中央値で割った値。「SWAR が速い周」は周内の中央値で比較した。

| 認識入力 | サンプル数（scalar / SWAR） | scalar 中央値 | SWAR 中央値 | scalar 最小 | SWAR 最小 | 倍率 | SWAR が速い周 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| JSON 1 MB | 7 / 7 | 19.277764 | 34.107364 | 13.660915 | 16.557838 | 0.565 | 1/7 |
| Operators 512 atom | 7 / 7 | 0.240113 | 0.247110 | 0.101183 | 0.143263 | 0.972 | 3/7 |
| complex | 35 / 35 | 0.287376 | 0.279499 | 0.126244 | 0.109388 | 1.028 | 3/7 |
| complex-x4 | 35 / 35 | 0.875551 | 0.787740 | 0.420267 | 0.450124 | 1.111 | 7/7 |
| complex-x16 | 35 / 35 | 3.305224 | 3.055087 | 1.878934 | 1.204509 | 1.082 | 4/7 |
| complex-x64 | 35 / 35 | 17.669353 | 17.100450 | 10.483939 | 10.167598 | 1.033 | 4/7 |
| comparison-heavy | 35 / 35 | 0.103900 | 0.089441 | 0.069940 | 0.052407 | 1.162 | 5/7 |
| comparison-heavy-x64 | 35 / 35 | 7.773881 | 8.079930 | 3.237616 | 2.905317 | 0.962 | 4/7 |

`uptime` の load average（1 / 5 / 15 分）は開始 **44.76 / 44.93 / 40.66**、終了 **26.77 / 39.09 / 45.92**。全 112 記録の範囲は 24.60–135.60 / 39.09–83.10 / 40.11–56.63。JSON は 7 周中 6 周で SWAR が遅かった。全データの中央値、最小値ともに 1.5 倍の目標は未達。

P4 の中央値は fixture によって約 −14%〜+4%、Operators は +2.9%。両文法の生成ソースが byte 一致する対照でもこれだけ実時間が動き、たとえば complex-x4 は 7 周すべてで候補 JVM の方が速かった。今回の条件では、対照の差を実装による速度変化に帰属できず、実時間の無退行確認は保留する。既定の生成物を scalar のまま byte 一致に保つ。

## 短い一致区間の内訳

計装版は計時版と別の class 出力に生成し、各 word 判定で一致した先頭 lane 数を固定 JSON 1 MB の 1 parse 分だけ数えた。

| 一致した先頭 lane 数 | 0 | 1 | 2 | 3 | 4（全体） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 回数 | 272,146 | 73,981 | 6,605 | 15,852 | 59,446 |

428,030 回の判定のうち 63.6% は先頭 lane で止まり、86.1% は 4 lane 全体を進めなかった。先頭 lane で止まる場合も 4 文字のロードと `long` の組み立て、区間判定を行う。短い区間でもこの固定費を払うことが構造上の原因候補で、実時間への寄与は未計測。計装版から経過時間や CPU 時間は採っていない。

## 検証

- `SwarScanTest` で固定 seed 29 の変異 256 入力と境界・escape・非 BMP・孤立 surrogate・反復下限等 738 入力を比較し、ドライバの `options.scan` の両値で差分 0 件。認識・typed AST、出現表・診断・lexical の切り替え、rollback でも差分 0 件。別の IR で走査領域の外側で生じる capture・scope イベント・AST span も比較した。
- 既定で生成した対象の全ソースが `a990dac` 版と byte 一致し、P4 と Operators は `--swar` を指定しても全ソースが byte 一致した。
- OpenJDK 17.0.21 で opt-in の JSON 生成物を `javac -Xlint:all -Werror` で依存なしにビルドし、同じ JDK 上で非 BMP と長い数字列を含む入力をドライバで受理した。Maven の生成器ビルド `mvn -q -DskipTests package` は JDK 21 で成功した。
