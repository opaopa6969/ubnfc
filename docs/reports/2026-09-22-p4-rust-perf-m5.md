# P4 Rust 生成 parser の性能改善 M5（2026-09-22）

[`2026-09-22-p4-rust-bench.md`](2026-09-22-p4-rust-bench.md) の診断（診断 DAG が 1 parse で 108 万 node・170 MB）を受けて、
Rust emitter（`crates/ubnfc-rust`）と埋め込み runtime template を変更した。意味論は変更していない
（corpus round7 と同じ verdict、selfhost 固定点、P4 golden AST byte 一致、`crates/ubnfc-rust/tests` 全緑）。

## 結論

- complex.tiny（332 byte、AST 付き）は **0.50 ms**（同一負荷下の M5 前 47.4 ms、同日報告値 26.3 ms）、
  complex-x64 は **60〜92 ms**（M5 前 3,487 ms）。1 parse の確保は 170 MB → 1.7 MB（確保回数 3,793 → 2,754）。
- 目標（complex ≤ 0.2 ms、x64 ≤ 15 ms）には届いていない。残りは「失敗の多い型付き choice を rule 呼出しごとに
  辿る」構造コスト（rule 呼出し 2,455・expression 呼出し 7,205 / parse は不変）と、x64 での作業集合（memo 表・診断 arena）
  の cache 効果。次の候補は末尾に挙げる。
- 既定 `limits.diagnostics`（2,000,000）で全 fixture が受理される（M5 前は 700 byte 級で予算超過）。

## 変更点（emitter / template）

| # | 変更 | ファイル |
|---|---|---|
| 1 | 公開 farthest 候補（D-014）の frame を DAG から「(far, base, reached) + 1 本の label log」へ。失敗 1 件は O(1)、leave で親へ O(1) 伝播、Not 成功は frame を破棄（`discard`）、Not 失敗は `leave_guard`。memo は局所 snapshot（far, reached, saved label 範囲）を保存・再生 | `templates/diag.rs`, `src/expressions.rs` |
| 2 | frame を **memo 保存点（rule 本体・共有 expression）と lookahead だけ**に置く。rule 関数と非 memo expression は `reach` のみ | `src/emit.rs`, `src/expressions.rs`, `src/tokens.rs` |
| 3 | memo を plan が許す expression のうち **rule 本体と共有 expression（複数の親を持つ ExprId）**に限定。scope を読み書きしない（analysis.effects が空の）expression は key の `stateVersion` を 0 に固定。SipHash → 乗算混合の固定長 hash、probe 計数は `Cell` | `src/expressions.rs`, `templates/memo.rs` |
| 4 | `limit()`（stack 検査）は rule 入口だけ。`mark/restore` は memo 保存点だけ（失敗時 rollback は choice / repeat / optional / separated / lookahead / rule が自前で行う） | `src/expressions.rs` |
| 5 | floor 刈り込み: Not の外で記録した最遠位置 `floor` より手前の候補は記録しない（最終 farthest の下界なので summary にも memo 再生にも現れない）。`fail`/`failures` は frame 状態を 1 回だけ判定。label の重複除去は世代印付き pointer 表で O(n) | `templates/diag.rs` |
| 6 | 主診断 DAG の handle `Diag { id, pos }` が位置を持ち、`join` が arena を参照しない。node を 24 byte に縮小。memo 表と診断 arena を入力長から事前確保 | `templates/diag.rs`, `templates/runtime.rs` |
| 7 | AST の `value_spans` の path を共有バッファで組み立て（field ごとの `format!` を廃止） | `templates/value_spans.rs`, `src/mapping.rs`, `templates/finish.rs` |
| 8 | `limits.diagnostics` の意味を固定: 主診断 DAG の node 数と、公開候補の記録回数（候補が残った `fail`/`failures`/`merge` 呼出し）をそれぞれ上限にする。fixture テストで全 13 件の受理と、小予算での Resource 診断を固定 | `examples/p4-rust/tests/fixtures.rs` |

memo の限定（3）は plan の `provedOmission` ではなく emitter の方針である。根拠: 単一の親しか持たない expression は、その親の
1 回の評価で高々 1 回・互いに異なる位置でしか実行されず（Seq の各要素、Choice の各候補、Repeat の各周回は前進を要求）、
同じ状態での再訪は最寄りの memo（rule 本体か共有 expression）が吸収する。したがって結果は不変で、計算量は rule 単位 packrat と同じ。
`crates/ubnfc-rust/tests/review.rs` の共有 expression（Not と Lookahead が同じ literal を参照、2 候補が同じ Extern token を参照）は
共有 expression として memo され、scanner 呼出し 1 回・memo hit の契約を保つ。

## 段階別 A/B（`examples/p4-rust` の bench、release、warmup 後 5 run の中央値、ms/parse）

同一 worktree で emitter を段階的に変え、その都度 `src/generated` を再生成して計測した。共用ホストで他の計測（Java M5）が並走して
いたため段階 1〜6 の絶対値は run ごとに 1.5 倍程度ぶれる（段階 3 の x64 など）。最終行（段階 7）と M5 前の行は、最後に
**同じセッションで baseline binary と最終 binary を続けて実行**した値（baseline: complex 24.43 / 25.49 ms、x64 1,878.6 / 1,921.8 ms、
同日報告の 24.9 / 26.3 ms と一致）。最終 x64 AST の 92.2 ms は計測中に load average が 5 → 9 に上がった区間の値で、
直前の段階 7 計測では 59.7 ms だった。allocs / bytes は GlobalAlloc の計数（AST 付きの列）。

| 段階 | complex 認識 | complex AST | x4 AST | x16 AST | x64 AST | complex allocs (AST) | complex bytes (AST) |
|---|---:|---:|---:|---:|---:|---:|---:|
| M5 前（a23ab4f、同セッション再計測） | 24.429 | 25.492 | 100.0 | 440.8 | 1,921.8 | 3,793 | 170 MB |
| M5 前（作業開始時、高負荷下） | 39.108 | 47.408 | 173.4 | 699.4 | 3,486.4 | 3,793 | 170 MB |

| 3 limit/mark を rule 単位に | 1.297 | 1.355 | 5.9 | 22.7 | 135.2 | 3,423 | 2.27 MB |
| 4 floor 刈り込み・予算を呼出し単位に | 0.887 | 1.039 | 4.3 | 18.8 | 93.1 | 3,423 | 2.27 MB |

段階 1 の時点で複雑度は解消（node 108 万 → 数千）し、残りは定数の削減である。段階 2 で memo lookup 7,108 → 2,455、
store 6,292 → 1,639（hit 816 は不変、rule 評価 2,455 も不変）。段階 4 で display の label push が 1 parse 約 25,000 → 数千。
計測込み profile（`--features counters`、`Instant` を runtime 関数に挿入した一時計測）では段階 4 時点の 1 parse で
memo `store` 354 µs（snapshot の label 複製が O(n²)）、`lookup` 171 µs、`combine` 210 µs、literal/primitive 250 µs、trivia 118 µs
だったので、段階 5・6 はそこを潰した。

| 入力 | bytes | 認識 ms | AST ms | µs/byte (AST) | 目標 | 手書き目安 0.4 µs/byte |
|---|---:|---:|---:|---:|---:|---:|
| complex | 332 | 0.416 | 0.496 | 1.49 | ≤ 0.2 ms | 0.13 ms |
| complex-x4 | 1,293 | 2.27 | 1.84 | 1.42 | — | 0.52 ms |
| complex-x16 | 5,179 | 9.6 | 7.2 | 1.39 | — | 2.1 ms |
| complex-x64 | 20,923 | 60.5 | 92.2 | 4.41（認識 2.89） | ≤ 15 ms | 8.4 ms |

M5 前（同セッション再計測）比で complex 51 倍（認識 59 倍）、x64 21〜31 倍。Java 生成（同日報告 17.3 ms）の約 35 倍速い。
x64 の µs/byte が complex の約 2.5 倍になるのは、memo 表（約 5 entry/byte × 72 byte）と診断 arena（約 18 node/byte × 24 byte）が
L2 を超えてからの cache 効果で、算法上は線形（rule 評価 7.1〜7.4 / byte で一定）。

## 契約の検証

- `docs/design/04-cursor-and-diagnostics-contract.md` §1（cursor）: 生成 cursor コードは無変更。
- §2（診断）: 主 offset / `expected` / rulePath は主診断 DAG（`Step.diag`）が担い、構造は不変（handle が位置を持つだけ）。
  farthest / `farthestExpected` は display frame の「最遠位置とその位置の label 集合」で、旧 DAG の `summary` と同じ観測量。
  Not 成功時の子診断破棄（`discard`）、Not 失敗時の保持（`leave_guard`）、memo hit の局所診断再生（`merge`）を
  `crates/ubnfc-rust/tests/runtime.rs` の単体テストと `tests/round2.rs` の oracle（memo 有無で同一）で確認した。
- floor 刈り込みの健全性: Not の外の frame は破棄されないので、そこで記録した最遠位置は最終 farthest の下界。
  それより手前の候補は summary に現れず、memo に保存しても再生時に（その時点の farthest 以下なので）捨てられる。
- `docs/design/03-design-v1.md` §3.7: memo key の `stateVersion` は effects が空の expression だけ省略（scope を読み書きしない）。
  memo の範囲限定は上記の根拠による emitter 方針で、plan の `provedOmission` は従来どおり尊重する。
- corpus: `docs/reports/2026-09-22-rust-corpus-m5.{md,json}`。系統別の表が round7 と完全に同じ
  （Pass 1292 / 期待拒否 Pass 30 / Known 28 / Fail 0 / 未観測 75。round6 の Fail 4 は master の comment-trivia で解消済み）。
- selfhost 固定点（`crates/ubnfc-selfhost/tests`）緑、`src/generated` を再生成して commit。P4 golden AST は byte 一致。

## 残りの候補

1. **rule 参照で始まる choice の予測分岐**（Expression の 4 typed alternative、SliceBaseExpression の method 候補）。front の
   `mayStart` は P4 では `unknown`（`$` 変数・`if`・`(` が全型に共通）なので、先頭 code point だけでは候補を絞れない。
   複数文字の trie（関数名）と、型付き式の「先頭 primary を 1 回だけ解析して型で分岐」が要る。rule 評価 2,455 / parse を減らす
   唯一の手段で、これが無い限り 0.2 ms（= 呼出し 1 回あたり 20 ns）には届かない。
2. memo entry の縮小（72 → 64 byte）と、失敗 entry の省略（hit の半分は失敗）。x64 の cache 効果を下げる。
3. trivia の先頭 1 文字 fast path（空白・`/` 以外なら即 return）。1 parse 約 4,000 呼出し × 約 15 ns。
4. AST 経路: `field_text` / `owned_captures` の Vec、`text_spans` HashMap、`ValueSpan` の String（API 契約）。
   認識 → AST の差 約 0.1 ms の大半。
5. 主診断 DAG の遅延化（成功経路で `Rule` node を作らない）。rulePath は D-020 で情報提供のみだが、既存 oracle を守るため未着手。
