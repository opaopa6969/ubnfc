# Java の LL(1) 認識表（issue #39）

`ParseOptions.RECOGNIZE.withLl1(true)` で D-091 の `plan.ll1` を Java でも実行できる。固定 JSON 1 MB の認識は変更前 **0.009674 µs/byte**、変更後 off **0.009742 µs/byte**、on **0.007075 µs/byte**。on は off より **27.4%** 短く、目標の **≤0.015 µs/byte** を満たした。既定の有効化は、表が走る JSON 以外の文法と深い入力での割当・fallback の評価を経て判断できるよう、今回は opt-in とした。

## 被覆と意味論

| IR | 表の式 | 表の規則本体 | 認識時に表を使える範囲 |
| --- | ---: | ---: | --- |
| JSON | 120/120（100%） | 16/16（100%） | 入口から 120 状態すべてに到達可能 |
| 固定 P4 `f86ce8a5` | 386/1,043（37.0%） | 5/124（4.0%） | 0% |
| pin `c736c2c` の P4 | 388/1,089（35.6%） | 5/130（3.8%） | 0% |

Java の式・クラス・参照から計画を検証し直す。scope / recovery のある文法と、memo 対象を含む閉領域は従来経路で評価する。P4 は両 IR とも scope 効果があるため認識表の呼出しを生成しない。JSON の入口から既存の一括走査も使え、on/off とも UTF-16 の consumed / matched を維持する。表の失敗や深さ上限では従来経路で結果を確定する。詳しい条件は [設計](../design/09-ll1-tables.md) を参照。

## 計測環境と再現

変更前は #35 と #29 を含む `cdd17a8`。両生成器に同じ IR を渡した。変更後の on/off は同一生成物と JVM 設定を使う。既存の一括走査は両側とも有効で、`--swar` は指定しない。JSONTestSuite `1ef36fa01286573e846ac449e8683f8833c5b26a` から生成した JSON は 1,000,112 byte。P4 は固定 IR の Formula 入口に既存の `complex-x64.tiny`（20,923 byte）を渡した。各計時で受理、全消費、matched を検査する。

Ryzen 9 7950X、WSL2 Linux 6.18.33.2、Oracle JDK 21.0.9。論理 CPU 28 に固定し、各 JVM に `-Xms512m -Xmx512m -Xss16m -XX:+UseSerialGC -XX:ActiveProcessorCount=1` を指定した。6 周を変更前 → off → on、off → on → 変更前、on → 変更前 → off の順に回した。各セルは別 JVM で 200 回暖機し、約 0.2 秒相当の反復数で 5 回測って中央値を採った。下表は各 JVM の中央値 6 個の中央値。共有負荷の上がった周も集計に含めた。

```bash
work=$(mktemp -d)
git init -q "$work/suite-repo"
git -C "$work/suite-repo" fetch -q --depth 1 https://github.com/nst/JSONTestSuite.git \
  1ef36fa01286573e846ac449e8683f8833c5b26a
mkdir "$work/suite" "$work/ab"
git -C "$work/suite-repo" archive FETCH_HEAD | tar -x -C "$work/suite"
export WORK="$work/ab"
BASE_REF=cdd17a8 JSON_TEST_SUITE="$work/suite" benchmarks/scripts/run-java-ll1-ab.sh prepare
CORE=28 ROUNDS=6 benchmarks/scripts/run-java-ll1-ab.sh time | tee "$work/time.txt"
```

[入力 SHA-256](2026-11-20-java-ll1-data/inputs.txt) と [各 JVM の計測値・uptime](2026-11-20-java-ll1-data/time.txt)。

## 結果

| 認識入力 | 変更前 ms / µs/byte | 変更後 off ms / µs/byte | 変更後 on ms / µs/byte |
| --- | ---: | ---: | ---: |
| JSON 1 MB | 9.675 / 0.009674 | 9.743 / 0.009742 | 7.076 / 0.007075 |
| P4 complex-x64 | 12.498 / 0.597337 | 9.385 / 0.448526 | 11.260 / 0.538178 |

`uptime` の load average（1 / 5 / 15 分）は **9.60 / 14.12 / 22.50 → 81.93 / 34.87 / 27.98**。全 72 記録の範囲は 8.54–81.93 / 12.28–34.87 / 20.78–27.98。JSON の on は全 6 周で同じ周の off より速く、最も遅い on も 0.012812 µs/byte。変更前から off への中央値の変動は +0.7%。JSON の計測中のスレッド割当は変更前と off が 1,986,992 byte/parse、on が 1,990,112 byte/parse だった。

固定 P4 では変更前と変更後の生成 parser 本体のソースが一致した。変更後の P4 の on/off は同じ解析経路を通るため、中央値の差を LL(1) の効果として扱わない。JSON の改善と同時に、共有負荷と対照の変動の大きさを記録し、既定は off のままとした。

## 同値の検証

- Java のテストは JSON corpus、語境界、非 BMP と孤立 surrogate、Optional / Repeat の部分消費の巻戻し、深い再帰と明示的な深さ上限を on/off で比較する。AST、canonical JSON、診断、capture、scope、consumed / matched、rollback の観測を含む。旧 IR・破損した任意表・memo のある閉包・scope 文法での従来経路も確認する。
- 差分 fuzz campaign は既存の Rust–Java 比較と Rust 内 on/off を維持し、Java 内ではドライバの全応答を比較する。Java の比較には `maxDepth=2` の要求も含む。
