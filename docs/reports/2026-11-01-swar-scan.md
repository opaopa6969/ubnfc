# Rust bulk scan 内部の portable SWAR（issue #3）

2026-11-01。対象は Rust backend の `plan.scans` に載った文字クラス反復のみ。
基準は旧 [#48](https://github.com/opaopa6969/ubnfc-archive/issues/48) 後の `66a18ff`。
Java backend は [#29](https://github.com/opaopa6969/ubnfc/issues/29) へ切り出す。

**性能目標は未達**。最終版の JSON 1 MB は合算中央値で **1.1461 倍**、
P4 / Operators の無退行も実測では未確認。性能の残件は [#31](https://github.com/opaopa6969/ubnfc/issues/31)。

## 実装

ASCII bitset を連続区間へ分解し、許容集合と補集合のうち区間数が少ない方（最大 3 区間）で
8 byte を判定する。各 byte の上位 bit を番兵にした減算で lane 間の borrow を防ぎ、
非 ASCII または非許容文字の上位 bit を立てる。`u64::from_le_bytes` と
`trailing_zeros / 8` により先頭からの許容 byte 数 0..8 を求め、停止文字を越えない。
反復下限のある場合は消費した ASCII byte 数だけ回数を加算する。

読み込みは `slice.get(..8)` と `[u8; 8]` への安全な変換を使う。
非 ASCII は必ず従来の `cp_at` へ渡し、UTF-8 の文字境界を維持する。
8 byte 未満の末尾と複雑な文字集合は従来の表引きで走査する。
CPU feature・alignment・native endian に依存しない同一コードを全 target へ生成する。
`unsafe` と依存 crate は追加せず、生成ライブラリの `#![forbid(unsafe_code)]` を保つ。

front・IR・走査の適用条件・PEG の候補順は変更しない。D-072 と同じく診断 session、
lexical / occurrences 要求、invert では参照経路を通る。SWAR はこの既存の走査関数の中だけで働く。

空の反復には先頭 byte の表引きガードを置き、そこで止まる場合は word を読まない。
これはガードなしの試行版で確認した短い走査の負担を減らすためである。
試行版のデータも [1 回目](evidence/2026-11-01-swar-scan/preliminary-1.csv)・
[2 回目](evidence/2026-11-01-swar-scan/preliminary-2.csv) として残す。

## 検証

- SWAR の不一致 mask をコンパイルして実行し、参照表が返す停止位置と比較した。
  区間・補集合 256 ケース × 背景 6 種 × 8 lane × 全 256 byte 値の **3,145,728 比較**が一致した。
  デバッグ時の整数 overflow 検査も有効にしている。
- `crates/ubnfc-fuzz/tests/swar_scan.rs` は word 境界 0..40、ASCII / UTF-8 / 非 BMP、escape、
  反復下限、EOF、不正入力、固定 seed 3 の変異を含む **1,363 入力**を、生成 Rust driver の
  `options.scan` on/off で比較する。campaign 共通の `differences` で **差分 0・未観測 0**。
  外側の capture の text・span と失敗時の診断も比較に含む。
- 最終版の JSON 生成ライブラリは `wasm32-unknown-unknown` の release build が成功した。
  非 x86 の実機実行は行っていない。特定の命令集合へ分岐する実装は持たない。
- 最終版 JSON 生成物の clippy は `-D warnings -A clippy::while_let_loop` で成功。
  除外は従来からある `HEX{4}` の一般反復ループの警告 1 件だけで、before にも同じ警告が出る。
- workspace 全体は CI と同じく Java jar を `mvn -q -DskipTests package` で作った後、
  固定外部 fixture を指定して `RUSTUP_TOOLCHAIN=stable cargo test --workspace --no-fail-fast` を実行する。
  merge には native / wasm32 CI の成功を要求する。

## 計測条件

before は `66a18ff8e71839b893d2edabdad14825f8436dae`（旧 #48 の bulk scan は有効）、
after は実装 commit `2fc6dbed9ae4a4df016ac85edc069ead68c83714`。
同じ IR を各生成器へ渡し、同じ binary に両生成物を入れ、同一の認識オプションで比較した。
歴史的な #48 の絶対時間とは直接割り算しない。

AMD Ryzen 9 7950X / Linux 6.18.33.2-microsoft-standard-WSL2、Rust stable
`rustc 1.99.1 (58cf8f9c3 2026-10-13)`、release、単一 thread、`taskset -c 30`。
各入力で before により反復数を決め、半数を warmup、各 round は先後を交替する。
目標 0.5 秒 / run、7 round × 2 セッション。両側の反復数は入力・セッションごとに同じ。
各 run の壁時計時間を記録し、外れ値を捨てず中央値を比較する。

JSONTestSuite は既存規約の commit `1ef36fa01286573e846ac449e8683f8833c5b26a`。
`make-json-inputs.py` で作った 4 入力の SHA-256 は
`examples/json/evidence/inputs.sha256` と全一致し、1 MB は **1,000,112 byte**。
P4 は既存 6 fixture、Operators は既存の 512 atom（1,023 byte）を使った。
共有マシンで他担当の build / CI が同時に動いている。負荷を減らした条件へ切り替えたり、
都合のよい run のみを選んだりしていない。

## 実測結果

## 効く範囲と次の手

固定の 1 MB 入力は短い文字列と escape を多く含む。文字列内部を escape / UTF-8 / quote で
区切って数えると、文字列 50,200 個、連続 ASCII 40,953 区間の長さの中央値は **3 byte**、
ASCII 合計は **207,403 byte（入力の 20.74%）**である。
8 byte 以上の区間は 3,963 個 / 122,853 byte（入力の 12.28%）、
escape は **63,424 個**、非 ASCII は 3,963 code point。
これは入力の分布であり、実行時間の割合の測定ではない。

SWAR は長い ASCII 区間をまとめて進めるが、短い区間では mask 計算・停止位置計算の固定費が残る。
escape は表に含まれないため従来の走査関数へ戻り、構造規則の評価・cursor 更新・規則呼出しも残る。
先頭 byte ガードは空の反復の word 判定を省くが、非空の短い区間の固定費までは消さない。
したがって word 化だけから JSON 全体の 1.5 倍を保証する根拠はない。
共有負荷による時間差も大きく、今回の壁時計値だけで各要因の寄与を断定しない。

次は既存の計測基盤（#6）で空・短・長い走査と escape の回数 / 自己時間を分け、
集合ごとの少ない演算での判定と、短い区間への適用閾値を評価する。
その後も同じ 1 MB 入力で足りなければ、`plan.scans` 内の escape / 終端列の呼出しを減らす案と、
別課題の構造領域の表駆動化（#2）を区別して検討する。入力や計時条件を目標へ合わせて変更しない。

## 再現

```sh
export RUSTUP_TOOLCHAIN=stable
export WORK=$(mktemp -d)
BASE=66a18ff JSON_TEST_SUITE=/path/to/pinned/JSONTestSuite benchmarks/scripts/run-swar-ab.sh prepare
CORE=30 RUNS=7 benchmarks/scripts/run-swar-ab.sh time "$WORK/session1"
CORE=30 RUNS=7 benchmarks/scripts/run-swar-ab.sh time "$WORK/session2"
```

実装 commit `2fc6dbe` の worktree で実行すれば本報告と同じ生成器になる。
各 CSV は全 round を含み、`ms` を入力・variant ごとに集めて中央値・最小値を計算する。
2 セッションを合わせる場合は全 14 値の中央 2 値の平均を中央値とする。
