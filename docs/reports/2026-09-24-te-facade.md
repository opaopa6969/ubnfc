# tinyexpression の P4PreferredAstMapper を ubnfc 生成パーサで差し替える（2026-09-24）

issue #62。tinyexpression の facade と**同じ公開面**を持つ差し替え版を ubnfc 側に作り
（`examples/p4-java-facade`）、AST の一致・実運用経路の通り・段別の時間を測った。
tinyexpression と `examples/p4-java` のソースは変更していない。

対象は次の 3 つの checkout（隣接、読み取り専用）:

| | 版 |
|---|---|
| tinyexpression | 作業ツリー `target/classes`（`c70416e1`）。公開 jar 1.4.15 は古く、facade が使う `mapParsedTree` を持たない |
| unlaxer-common / unlaxer-dsl | 3.0.15（共有 `~/.m2` から読むだけ） |
| ubnfc | `103842e`（PR #64 の bulk scan を含む master）+ このブランチ。`examples/p4-java/scripts/generate.sh --check` で commit 済み生成パーサが現行生成器の出力と byte 一致することを確認してから測った |

## 1. 旧 facade の面

`org.unlaxer.tinyexpression.p4.P4PreferredAstMapper`（884 行）の公開面は次のとおり。

### 1.1 入口 4 つ

| 入口 | 戻り | 実運用での使われ方 |
|---|---|---|
| `parse(String[, ExpressionType])` | `TinyExpressionP4AST` | テスト・診断 |
| `parseDetailed(String[, ExpressionType])` | `ParsedAst` | **本番経路はここだけ**（`DslGeneratedAstJavaEmitter:31`、`P4ParseProbe:15`） |
| `parseByAstSimpleName(s)(...)` / `...Detailed(...)` | `TinyExpressionP4AST` / `ParsedAst` | `GeneratedAstRuntimeProbe:48,84` |
| 候補名 API 4 つ（`preferredAstSimpleNames` ほか） | `List<String>` | `AstEvaluatorCalculator:244` |

`ParsedAst(TinyExpressionP4AST ast, String selectionMode, P4SourceText sourceText)` は record。
2 引数コンストラクタは `sourceText` を `P4SourceText.lexicalOnly()` にする。

**下流が実際に読むのは `ast` と `sourceText` だけ**で、`selectionMode` は
`DslGeneratedAstJavaEmitter` では使われない（emitter の `mode` は `"p4-typed-emitter"` 固定）。
`sourceText` は必須で、`P4TypedJavaCodeEmitter` がコンストラクタで `requireNonNull` し、
スライス添字の描画（`renderSliceIndexExpr`）で `sourceText.text(index)` を呼ぶ。

### 1.2 候補の順序と `selectionMode`

`preferredAstSimpleNames(formula, resultType)` は結果型だけから決まる決定的な列で、
ソースを目視走査しない。順序は
`match 系 → IfExpr → TernaryExpr → external 呼び出し →（型未指定なら match 3 種）→
構造化関数 35 種 → 型ごとの根（StringConcatExpr / BooleanOrExpr / ObjectExpr / BinaryExpr）→
VariableRefExpr → FormulaExpr`。`DECLARATION` プロファイルだけ boolean の根が `BooleanExpr` になる。

`selectionMode` の取り得る値は 4 形:

| 値 | 意味 |
|---|---|
| `preferred:<Name>` | 候補列のうち、全ソースを覆う最初の一致 |
| `default` | 候補が当たらず、既定（根）を許す呼び方だったとき |
| `explicit:object` | 明示された結果型が object で、`ObjectExpr` に包み直したとき |
| `document:<inner>` | 宣言や import を持つ文書で、式だけを型付きの族ルートで再解析したとき |

`parseByAstSimpleNamesDetailed` だけは追加の後処理を持つ。候補列のうち
「型付き族の根」（`StringConcatExpr` / `BooleanOrExpr` / `ObjectExpr` / `*MatchExpr`）が
選ばれたものより前にあれば、`selectExplicitResultFamily` を通してもう一度選び直し、
候補列で**前にある**ほうを採る。

### 1.3 `P4SourceText`

`fromSnapshot(parserSource, spans)` / `lexicalOnly()` / `withWholeSourceNode` /
`spanOf(node)` / `text(value)` が public、`withOverlay(...)` は package private。
**span は code point の半開区間**、ノードは identity で引く。

旧実装の混在表現は `P4SourceMapping#normalizeLegacySpan` に残っている。公開 3.0.15 の
generator は「**code point の開始 + UTF-16 の長さ**」を保持しており、そのままでは
BMP 外の文字を含む span の終端がサロゲート 1 個ぶん長くなる。旧 facade はこれを
新 API が無いときの経路でだけ後から正規化する。

**ここが「旧側の誤り」の所在**で、2026-09-23 の実装比較（`examples/p4-java/evidence/ast-differences.json`）
が拾った 4 件はこの混在表現によるもの。ただし **tinyexpression の作業ツリーの現行ビルドでは
この差は再現しない**。`mapParsedTree` を持つ新しい mapper API が使われ、大域表
（`TinyExpressionP4Mapper.sourceSpanOf`）も snapshot も code point を返す
（`LegacySourceSpanTest` がこの事実を固定する）。ubnfc 版は元から code point しか持たない。

### 1.4 失敗時

| 条件 | 例外とメッセージ |
|---|---|
| 解析が成功しない | `IllegalArgumentException("Parse failed: " + source)` |
| 成功したが消費不足 | `IllegalArgumentException("Parse failed at offset " + consumed + ": " + source)` |
| 全ソースを覆う候補が無く既定も許さない | `IllegalArgumentException("No whole-source generated AST mapping found: " + parserSource)` |
| match の case と default で結果型が割れる | `IllegalArgumentException("P4 match type mismatch: ...")` |
| 期限超過 | `P4PreferredAstMapper.ParseDeadlineExceededException` |

下流（`DslGeneratedAstJavaEmitter:32`）は **`RuntimeException` なら全部握り潰して
`Optional.empty()`** にし、`DslJavaCodeCalculator` が `UnsupportedOperationException` に、
`JavaCodeCalculatorV3` のコンストラクタが `CompileError` に変える。したがって差し替え版の
最低条件は「失敗は必ず `RuntimeException`」。`Error` や checked 例外を投げると
`CompileError` にならず、`FormulaInfoStoredByteCodePolicyTest` などの期待が壊れる。

## 2. 作ったもの

`examples/p4-java-facade`。

- `UbnfcP4PreferredAstMapper` — 旧 facade と同じ公開面。
- `UbnfcP4Parse` — 解析・候補選択・型付き族の再選択。候補列と `selectExplicitResultFamily` の
  分岐は旧実装から移した（順序・fallback・`selectionMode` の文字列まで同一）。
- `UbnfcAstConverter` — **機械生成**。`scripts/generate-converter.py` が両側の record 定義
  （ubnfc 生成ソースと tinyexpression の jar の javap）から 86 件ぶんを出す。
- `src/shadow/java/.../P4PreferredAstMapper.java` — **機械生成**。
  `scripts/generate-shadow.py` が本体から出す。同 FQN の classpath shadow 用。

### 2.1 変換器を手書きしなかった理由

両側の AST は同じ IR から生成されており、**86 record すべてで名前・component 名・順序が一致**する。
宣言型の違いは 1 か所だけ。

| record.component | ubnfc | tinyexpression |
|---|---|---|
| `SliceExpr.start` / `.end` / `.step` | `Optional<BinaryExpr>` | `Optional<Object>` |

（`ExternalXInvocationExpr.className` は commit 済みの生成ソースでは `Optional<QualifiedNameExpr>`
と `QualifiedNameExpr` に見えるが、**tinyexpression の現行ビルドの class ファイルでは
`Optional<QualifiedNameExpr>`** で、実体は一致している。生成器は jar 側の宣言型を見る。）

そのため変換は 1:1 の機械変換で、`generate-converter.py --check` が commit 済みの生成物と
再生成結果の byte 一致を確かめる。

### 2.2 選択規則の移し方

旧側の `select(preferred)` は生成 mapper の `findBestMappedToken`
（`unlaxer-dsl/.../MapperRuleEmitter.java:205-`）で、**トークン木**を前順に歩き
「preferred 一致を最優先 → 最小深さ → 開始位置が大きい方」で 1 つに決める。
preferred が 1 つも無いときは深さ 0、すなわち根になる。

ubnfc 版は typed AST を直接持つので、**同じ順序を AST 上で**行う（深さは AST の深さ）。
preferred が無ければ根を返すところまで同じ。旧側の「トークン木の深さ」と
「AST の深さ」は一致しないが、直後に `coversWholeSource` で全ソースを覆うものだけに
絞られるため、選ばれる節点は変わらない。**これは設計上の主張ではなく、
次章のパリティで 340 件すべてについて確かめた事実**である。

### 2.3 意図的に違えたところ

1. **解析期限**: 旧実装は `TransactionListener` を登録して解析ループの途中で throw する
   （深いネストで指数バックトラックになる #19 / #20 への対処）。ubnfc 版は packrat +
   深さ上限で構造的にそれが起きないので、**解析の前後でしか期限を見ない**。
   `ParseDeadlineExceededException` は公開面として残す。
2. **メモ化の切り替え**: `tinyexpression.p4.memoize` は ubnfc 版では効かない（常に packrat）。
3. **診断の二段構え**: 旧実装は `ParseOptions.Diagnostics.DETAILED_ON_FAILURE` を反射で
   組み立て、失敗時に同じ入力を作り直して再解析する。ubnfc 版は生成パーサ自身が
   同じ二段構え（`ParseOptions.withDiagnostics`）を持つので反射は要らない。

## 3. パリティ

入力は tinyexpression のテストが facade に渡す式 **324 件**
（`src/test/**` の文字列リテラル、`src/jmh/**`、`rust/tinyexpression-rs/tests/fixtures/**` の TSV、
`benchmarks/fixtures/*.tiny`。採取の範囲と除いたものは
`examples/p4-java-facade/src/test/resources/parity/README.md`）に、
`examples/p4-java` の fixture **16 件**を足した **340 件**。

同一 JVM 内で旧 facade（`org.unlaxer.tinyexpression.p4.P4PreferredAstMapper`）と
ubnfc 版（`...p4.ubnfc.UbnfcP4PreferredAstMapper`）を同じ入力に流し、
`ParsedAst` の 3 つ組をすべて突き合わせた。AST は canonical JSON
（`{"type","span","fields"}`、span は **両側とも `P4SourceText.spanOf`** から引く）で比較する。
正規化は一切していない。比較の間は両側とも解析期限を外す
（`tinyexpression.p4.parse.timeout.millis=0`）。共有マシンの負荷が高いと旧側だけが
深い入力（`complex-x64` や fraud-alert #5 など 8 件）で既定 10 秒の期限に当たり、
それは実装の差ではないため。`ParityTest` は `same` / メッセージまで一致する `both-reject`
以外が 1 件でもあれば落ちる。

| 判定 | 件数 | 内訳 |
|---|---:|---|
| `same`（AST・`selectionMode`・span すべて一致） | **320** | — |
| `both-reject`（両者とも拒否） | **20** | 例外型・**メッセージまで全件一致** |
| `ast-differs` | **0** | — |
| `mode-differs` | **0** | — |
| `legacy-only-reject` / `ubnfc-only-reject` | **0** | — |

**差分は 1 件も無い。** 全 340 行は `examples/p4-java-facade/evidence/parity.tsv`。
再現は `mvn -o -q test`（`ParityTest`）。

### 3.1 非 BMP について

事前の見込みは「差は BMP 外 span だけ（旧側のバグ）」だったが、**その差も出なかった**。

コーパスには非 BMP を含む入力が 24 件ある（`'😀'=='😀'`、`/*😀*/1<2/*終*/`、
`'😀a'[1:2]`、`複雑😀` を含む `complex.tiny` など）。いずれも span まで一致する。

理由は、2026-09-23 の実装比較が拾った 4 件
（`examples/p4-java/evidence/ast-differences.json` の valid-unicode 3 件と complex 1 件、
いずれも span 終端が 1 多い）が **tinyexpression の当時のビルドに固有**だったため。
現行の作業ツリービルドでは生成 mapper の大域表 `TinyExpressionP4Mapper.sourceSpanOf` も
`P4SourceText` の snapshot も code point 半開区間を返す。`LegacySourceSpanTest` が
`'こんにちは😀'`（UTF-16 9 / code point 8）で 3 つの経路すべてが `[0, 8]` を返すことを固定しており、
混在表現が戻ってきたら落ちる。

したがって「旧側のどこが間違っているか」は次のとおり述べるのが正確:

- **誤りが残っているのは公開 3.0.15 の generator が作る mapper**。そちらは
  「code point の開始 + UTF-16 の長さ」を保持する。旧 facade はその経路でだけ
  `P4SourceMapping#normalizeLegacySpan` を通して後から直しており、直さずに
  `sourceSpanOf` を直接読む利用者（LSP / DAP、外部ツール）はずれた span を受け取る。
- **作業ツリーの現行ビルドでは誤りが解消済み**。よって今日の突き合わせでは差が出ない。
- **ubnfc 版は表現そのものを持たない**（`Span(int start, int end)` が code point 固定）ので、
  この種の取り違えが起きる余地が無い。

## 4. 経路の実証

tinyexpression には parser facade の SPI が無い（`ServiceLoader` の使用ゼロ、
`META-INF/services` ディレクトリもゼロ）。`P4PreferredAstMapper` は `public final class` +
private コンストラクタ + 全 static、呼び出し元の `DslGeneratedAstJavaEmitter` は
package private final。よって**差し込み口は同 FQN クラスによる classpath shadow だけ**で、
これは tinyexpression 自身が unlaxer のコアクラスを shadow しているのと同じ手口
（memory `tinyexpression-shadows-unlaxer-core-classes`）。

`scripts/path-proof.sh` は `target/shadow-classes`（`P4PreferredAstMapper` 1 クラスのみ）を
classpath の先頭に置き、**tinyexpression 自身のテストを無変更のまま**同じ JVM で走らせる。
テストは `$TINYEXPRESSION/target/test-classes` から読むだけで、書き込まない。
実行中のクラス出所は毎回印字して確かめている
（`facade の読み込み元: .../target/shadow-classes/`）。

`org/unlaxer/compiler/CompileContext.java:146` は
`"org.unlaxer.tinyexpression.p4.P4PreferredAstMapper"` を**文字列で** `Class.forName` し、
その CodeSource を javac の `-classpath` に足す。shadow クラスは同じ FQN で解決できるので
この経路もそのまま働く（実際 javac 経路のテストが全部通っている）。

値の一致を押さえる。

ここに**入れていない**テストが 1 つある。`p4.P4PreferredAstMapperDiagnosticsTest` は
旧実装の private フィールド・メソッド（`DEFERRED_DIAGNOSTICS_SAFE`、`parseWithRoot`、
`Name.of(P4PreferredAstMapper.class, "parseDeadline")`）をリフレクションで触る実装詳細のテストで、
実装を差し替えれば成立しない。導入 issue でこのテストの扱い（`legacy` モード限定へ移すか削除）を
受け入れ条件に入れてある。

## 5. 段別の時間

`scripts/stage-timing.sh legacy|shadow`。同じドライバを classpath だけ替えて 2 回走らせ、
段ごとに warmup 3 回 + 9 回の中央値を取る。実行だけは 1,000 回の warmup 後 20,000 回の平均（µs/回）。
入力は `examples/p4-java` の 16 fixture と、issue #19 の実運用 fraud-alert 式 5 本（結果型 `_float`）。
master `103842e`（PR #64 の bulk scan 入り）に merge した後の build で測った。

**計測条件の断り**: 共有マシンで別エージェントの Maven / cargo ビルドが並走しており、load average は
15〜18 だった。parse は差が 1 桁以上あるので順位は動かないが、**javac と実行の列の旧/新の差は雑音**である。
両者は同じ AST から同じ Java ソースを作る（パリティで AST 一致を確認済み）ので、
javac と実行に構造的な差は無い。「生成」は `tryEmit` 全体から parse を引いた差なので雑音に弱く、0.00 になる行がある。

| `large-match.tiny` | 80% | 17.5% | 181.2 ms | 38.0 ms |
| `fraud#1` | 76% | 2.5% | 148.0 ms | 75.7 ms |
| `fraud#4` | 68% | 3.6% | 232.6 ms | 38.2 ms |
| `fraud#5` | 98% | 4.3% | 2179.3 ms | 33.4 ms |
| `complex-x64.tiny` | 60% | 50.0% | 2398.5 ms | 154.5 ms |

- **小さい式では javac が支配的**で、parse を速くしても全体はほとんど変わらない。
  `valid-basic.tiny` は旧でも parse が 1%。ここで得はしない。
- **実運用の式では逆転する**。fraud-alert の式は旧で parse が大半を占め、`fraud#5` は 1 式のコンパイルに
  2.2 秒かかっていた。新では parse が数 % に落ち、**javac が支配的になる**。
  全体は `fraud#5` で 2179.3 → 33.4 ms、`fraud#1` で
  148.0 → 75.7 ms。
- **大きい文書ではまだ parse が効く**。`complex-x64.tiny`（20 KB）は新でも parse が
  50%。全体は 2398.5 → 154.5 ms。

## 6. 本番導入の提案

`opaopa6969/tinyexpression#183` として出した:
**https://github.com/opaopa6969/tinyexpression/issues/183**

要点（2026-09-24 にユーザーが決めた方針）:

- **tinyexpression 2.0.0 の既定パーサを ubnfc 生成パーサにする**。opt-in のモード追加ではなく既定の入れ替え。
- 戻せるように、旧 combinator 経路は `CalculatorCreatorRegistry` の **`legacy` emitter mode** として
  2.0 の間は選べるまま残し、**削除は 3.0 へ先送り**する。システムプロパティ
  `-Dtinyexpression.p4.engine=legacy` も同じ意味で受ける。
- 生成パーサは**依存ゼロ**なので tinyexpression に vendoring する
  （`src/main/java/org/unlaxer/tinyexpression/generated/p4/ubnfc/`、22 ファイル）。
  再生成スクリプトは **ubnfc の commit を pin** し、同じ IR から byte 一致で再生成できることを CI で検証する。
- **tinyexpression 2.0.0 は unlaxer-parser の新版を必要としない**（生成パーサが unlaxer に依存しないため）。
  unlaxer-parser は 3.1.0 として別途リリースする（unlaxer-parser #297）。2.0.0 のリリース追跡は
  tinyexpression #176。
- 先に決めておくべき影響: `P4PreferredAstMapperDiagnosticsTest`（実装詳細のリフレクション）、
  `tinyexpression.p4.memoize`（`legacy` 限定になる）、解析期限の意味、LSP/DAP は 2.0 では据え置き。
- 受け入れ条件: 既定を倒した状態で全テスト緑 / `FormulaInfo` 経路 / パリティ表 /
  vendoring と再生成の CI 検証 / `legacy` で戻せること / 段別時間の表。
