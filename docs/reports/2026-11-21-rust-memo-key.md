# Rust の memo キーを lookup と保存で再利用する（#21）

## 変更と帰属

生成パーサは memo 化した式の入口でキーを pack し、hash を求める。式の評価中に表が拡張され得るため、持ち越すのは完全な packed key と容量に依存しない hash に限る。lookup と保存のたびに現時点の容量で slot を選び、衝突時はキー全体を比較する。mode、cursor の両位置とフラグ、scope の state version を引き続き比較する。保存する `Saved`、scope 効果の再生、資源上限の判定は従来どおり。memo が無効ならキーを準備しない。生成 CLI はライブラリの外から memo runtime を参照するため、新しい内部用 API は `#[doc(hidden)]` を付けた公開項目にした。

基準の Callgrind 行別データでは、`Memo::get` と `Memo::insert` はキーを狭める 3 個の変換だけで 9 Ir/call（`core::convert::num` に帰属）を使い、両方の関数で hash も計算していた。probe の slot 読み出しは lookup 672 回に対して 698 回で、衝突による追加は 26 回だった。保存値を変換・複製する `Saved::new` は 505 calls、33,835 自己 Ir/parse（67 Ir/call）。保存でも再利用できる処理を取り除く方を選んだ。

予備 A/B では最大 probe 数の更新を探索終了時にまとめた候補は全体 1,061,938 Ir（基準比 +0.56%）、pack と hash を簡略化した候補は 1,047,698 Ir（−0.79%）だった。キー再利用の候補は既存の hash と probe 順を維持し、保存時の再計算を省く。

## Callgrind

P4 complex 認識の 1 parse あたり。単位 Ir は実行命令数。分岐ミスは Bcm+Bim、D1 は D1mr+D1mw、LL は命令・データの miss の和。miss はすべて模擬値。

| 対象 | calls A → B | 自己 Ir A → B | 分岐ミス A → B | D1 miss A → B | LL miss A → B |
|---|---:|---:|---:|---:|---:|
| `Memo::get` → `get_prepared` | 672 → 672 | 55,467 → 24,846 | 310.6 → 249.1 | 526.6 → 502.0 | 2.1 → 1.3 |
| `Memo::insert` → `insert_prepared` | 505 → 505 | 54,524 → 39,549 | 232.6 → 40.0 | 662.3 → 660.0 | 54.7 → 54.8 |
| `Session::store` | 505 → 505 | 36,401 → 36,401 | 295.3 → 246.1 | 60.2 → 55.4 | 1.4 → 1.3 |
| 3 関数の合計 | 1,682 → 1,682 | **146,392 → 100,796（−31.15%）** | 838.5 → 535.2 | 1,249.1 → 1,217.4 | 58.2 → 57.4 |
| `Saved::new`（参考） | 505 → 505 | 33,835 → 33,835 | 30.9 → 97.8 | 0.0 → 0.0 | 0.5 → 0.5 |
| 認識全体 | — | **1,056,038 → 1,024,817（−2.96%）** | 8,936.7 → 8,148.1 | 6,508.7 → 6,466.4 | 806.5 → 809.3 |

自己 Ir の一部は式入口のキー準備に移る。準備や結果の破棄を含む全体でも 31,221 Ir/parse 減り、3 関数の 15% 減と全体の 2% 減を達成した。3 組を A B A B A B の順に計測し、各側の Ir と表の計数は 3 回とも一致した。

Valgrind 3.19.0、CPU 30、暖機 100 parse の後に 10 parse を計装。I1/D1 は 32 KiB・8-way、LL は 64 MiB・16-way、行は 64 B。各実行直前の `uptime` は 23:47:44–23:47:53 JST、稼働 11 日 1 時間 44 分、load average（1/5/15 分）12.31–12.91 / 10.60–10.66 / 7.99–8.00。

x64 認識の補助計測でも、暖機 10・計装 3 parse で全体 67,698,873 → 65,856,136 Ir/parse（−2.72%）。キー準備を別関数に出す試作は complex 全体 1,041,984 Ir（−1.33%）に留まった。準備を lookup に移す試作では別の native 7 組で x64 中央値が 5.526 → 5.925 ms になった。

## Native

A は `ee1476b`（計測開始時の `origin/master`）、B は `0b6783b`。AMD Ryzen 9 7950X、WSL2、Rust stable 1.100.0（`0ef1bc386`）、release + debuginfo=1。P4 は固定 IR から生成し、既存の scanner registry を使う。認識と所有 AST は観測 off。テキストの読み込みを除き、結果の破棄を含む。

CPU 12 固定、24 parse 暖機、各ケースで AB を交互に 7 組採取した。再測定では A の直前に runnable が 18 以下、同じ物理コアの CPU 13 が短い観測区間で 90% 以上 idle であることを確認した。実行後は両側ともプロセス CPU 時間が壁時計の 97% 以上、CPU 13 の使用率が 15% 以下の組を採用した。両側の負荷に同じ基準を適用し、時間の値で組を選別していない。complex / x64 の認識は各 9 組中 7 組、残り 4 ケースは各 7 組すべてが基準を満たした。各実行直前に `uptime` を保存した。23:59:24–00:00:30 JST、稼働 11 日 1:55–1:56、load average（1/5/15 分）7.50–10.33 / 11.63–12.92 / 10.69–11.02。

## 再現と検証

1. A/B とも [帰属計測の Rust 手順](../../benchmarks/attribution/README.md) と `driver.rs` / `region.c` を使って release バイナリを別々に作る。P4 IR は `ir/fixtures/tools__tinyexpression-p4-lsp-vscode__grammar__tinyexpression-p4.ubnf.ir.json`。入力は `examples/p4-rust/tests/fixtures/complex{,-x64}.tiny`。JSON は JSONTestSuite の `1ef36fa01286573e846ac449e8683f8833c5b26a` から既存の `make-json-inputs.py` で生成する。
2. Callgrind は `--cache-sim=yes --branch-sim=yes --instr-atstart=no --I1=32768,8,64 --D1=32768,8,64 --LL=67108864,16,64`。各 run の直前に `uptime`、次に `taskset -c 30 valgrind --tool=callgrind … <AまたはB> p4 recognize complex.tiny 100 10` を A B の順に 3 組。出力を `python3 benchmarks/attribution/summarize.py callgrind <計装出力> 10` で集計する。
3. Native は `uptime` の後に `taskset -c 12 <AまたはB> <p4|json> <recognize|ast> <入力> 24 <表の反復数>` を A B の順に実行する。負荷を選別する場合は `wait4` のプロセス CPU 時間と `/proc/stat` の SMT sibling の使用率を同じ基準で両側に適用する。
4. 外部 fixture は `scripts/fetch-external-fixtures.sh` の commit pin を使用。memo キーの mode・version、衝突、rollback、scope の再生、資源上限を `ubnfc-rust` の `runtime` / `review` / `round2` / `semantics` で、公開診断と AST を `driver` / `driver_json` で検査した。P4 fixture の既存 golden は受理・AST・span・診断とも一致し、P4 と自己ホストの generation 固定点も一致した。追加した回帰テストでは、lookup miss の後に他のキーを挿入して表を拡張し、準備済みキーで元の式を保存・再取得した。
