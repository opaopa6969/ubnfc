## 1. opt-in の形（D-067）

| | 既定 | `--emit-dap` |
|---|---|---|
| 生成パーサ | 変わらない | 変わらない |
| LSP 包み（11 ファイル） | 出る | **byte 単位で同一**（`ParserUnchangedTest.dapEmissionOnlyAddsFiles`） |
| DAP（5 ファイル） | 出ない | `<lsp-package>.dap/` に出る |
| server jar | lsp4j.debug を引かない | `-Pdap` で lsp4j.debug を引く |

- `ubnfc-lsp --emit-dap` は **`--emit-lsp` を要求する**。DAP は LSP 包みの
  `Positions`（code point → UTF-16）・`Meta`・`Analysis`・`Diagnostics` を**そのまま使う**ので、
  位置変換を 2 箇所に持たない（段階 1 §5.1-1 の UTF-16 取り違えを繰り返さないため）。
- `scripts/build-vsix.sh --with-dap [p4|ubnf|all]` が `--emit-dap` と server の `-Pdap` を一緒に有効にする。
  付けないビルドは従来どおり（jar に `org/ubnfc/*/lsp/dap/` も `org/eclipse/lsp4j/debug/` も 1 件も入らない。実測）。
- 生成される 5 ファイル: `AstWalk`（**文法ごとの `switch`**）/ `Steps` / `EvaluatorBridge` /
  `DebugAdapter` / `DapMain`。文法依存は `AstWalk` だけで、残りは定型。
- **module 名と Maven profile は `lsp` のまま**にした（`ubnfc-ide` へ改名しない）。
  改名すると `pom.xml` / `scripts/build-vsix.sh` / 段階 1・3 の報告書 / README の表 /
  他エージェントが並行して触っている場所の文字列が一斉に動くわりに、得るのは名前だけ。
  README の module 表と本節に「LSP と DAP の両方を出す」と書いて済ませる。

### 反射を使わない

旧スタックの `DAPRuntimeEmitter.collectAstNodeMeta` は `Class.getMethods()` を舐めて子を探していた。
この順序は JVM が保証しないので、**旧 DAP の AST ステップ列は実行ごとに並びが変わり得る**。
ubnfc は IR の `semantics.astTypes`（型・欄・宣言順）から `switch` を生成するので、
並びは**文法の宣言順で決まり決定的**になる（P4 で 86 記録型、UBNF で 49）。

### Java / Rust の対称性について（`AGENTS.md`）

**DAP は LSP と同じく Java 側だけの feature**である（段階 1–3 と同じ）。
`ubnfc-lsp` は lsp4j / lsp4j.debug（JVM のライブラリ）で生成パーサを包む module で、
Rust backend に対応物は無い。これは「言語固有の制約による差」として
ここと issue に明記する（`AGENTS.md` の規定どおり）。Rust 側で同じことをするなら
`tower-lsp` / `dap` crate を使う別 module が要り、それは段階 4 のスコープではない。
**パーサ本体の機能対称性は影響を受けない**——DAP は生成パーサを 1 行も変えないので、
Java / Rust の生成物の観測可能な振る舞いは今までどおり corpus が突き合わせている。

## 2. capability 表

| DAP request / event | ubnfc（生成） | 旧スタック base 生成 | 何から作っているか |
|---|---|---|---|
| `initialize` | ○ | ○ | `supportsConfigurationDoneRequest` のみ true。`supportsEvaluateForHovers` / `supportsSetVariable` / `supportsStepBack` は**正直に false** |
| `launch` | ○ | ○ | `program`（必須）・`stopOnEntry`（既定 **true**）。生成パーサで `buildAst=true` 解析 |
| 解析失敗の報告 | ○ | ○ | `output`(stderr) に **LSP と同じ文面の診断**（`Diagnostics.of`）→ `terminated` + `exited(0)` |
| `configurationDone` | ○ | ○ | `stopOnEntry` なら根で `stopped(entry)`、でなければ最初のブレークポイントまで走る |
| `setBreakpoints` | ○ | ○ | 行 → その行から**始まる AST 節点**があれば `verified=true`。無ければ `verified=false` + 理由（旧は無条件 true） |
| `threads` | ○ | ○ | 固定 1 本（id=1、名前 `<Grammar> parse`） |
| `stackTrace` | ○ | ○ | **根から現在の節点までの鎖**を枠にする（旧は常に 1 枠）。位置は `Positions` で code point → UTF-16 |
| `scopes` | ○ | ○ | `AST node`（節点の欄）と、scope 観測がある文法だけ `Symbols`（その位置までに見えている宣言） |
| `variables` | ○ | ○ | `#type` / `#text` / `#range` / `#doc`（`@doc`・`@declares(description)`）＋ **型付き AST の欄**（入れ子は `variablesReference`）。旧は `runtimeMode` / `astNodeCount` などのメタ情報 |
| `continue` | ○ | ○ | 次の「開始行にブレークポイントがある」ステップへ |
| `next` | ○ | ○（意味が違う） | 同じか浅い深さの次のステップ（＝部分木を飛ばす）。旧は「次の葉トークン」 |
| `stepIn` | ○ | **✕**（呼ぶと `Internal error`。実測 §4） | 列の次（＝子があれば最初の子） |
| `stepOut` | ○ | **✕**（同上） | より浅い深さの次のステップ |
| `pause` | ○（状態を変えず、いまの位置で `stopped(pause)` を返し直すだけ） | ✕ | 走り続ける実行が無い（ステップ列は `launch` で確定する）。黙って成功だけ返すと編集者が「一時停止中」のまま待つ |
| `disconnect` | ○ | ○ | 生成物は**終了を知らせるだけ**。プロセスを畳むのは `DapMain`（旧は `disconnect` の中で `System.exit(0)` していて、テストから叩けなかった） |
| `stopped` / `output` / `terminated` / `exited` | ○ | ○ | reason は `entry` / `breakpoint` / `step` の 3 種（旧と同じ） |
| **`evaluate`** | **拡張点**（既定は明示エラー） | ✕（生成されない） | `EvaluatorBridge.evaluate` が `Optional.empty()` を返すと「文法デバッガでは未対応。`EvaluatorBridge` を実装せよ」の `RequestFailed` |
| **`setVariable`** | **拡張点**（同上） | ✕ | `EvaluatorBridge.setVariable` |
| 条件付きブレークポイント / `stepBack` / watch 式 / `setExpression` / `breakpointLocations` | ✕ | ✕ | 段階 4 のスコープ外（issue #28 に明記） |

「黙って 0 や空文字を返さない」ことは golden が固定している
（`evaluate` / `setVariable` のエラー文面をそのまま golden に書き出している）。

## 3. ステップの意味論

**ステップ列は、`launch` で得た型付き AST を前順（親 → 子、子は文法の宣言順、`List` は要素順）で
平らにしたもので、1 ステップが AST の節点 1 つに対応する。**
`stackTrace` は現在の節点から根までの鎖をそのまま枠にし（枠 0 が現在の節点）、
各枠の範囲はその節点の span を `Positions` で UTF-16 に直したもの。
`stepIn` は列の次（＝子があれば最初の子）へ、`next` は**現在と同じか浅い深さ**の次のステップへ
（＝現在の部分木を飛ばす）、`stepOut` は**より浅い深さ**の次のステップへ、
`continue` は**開始行にブレークポイントがある**次のステップへ進み、いずれも進み先が無ければ
`terminated` + `exited(0)` を送って終わる（このため、根で `next` を押すと
「根を step over する」＝そのまま最後まで走る。木を降りるのは `stepIn`）。
旧スタックの base 生成は token モードが**葉だけ**を左から右へ辿る列で、`next` しか無く
（`stepIn` / `stepOut` は生成されない）、`next` はブレークポイントを見ずに必ず 1 つ進んだ。
ubnfc は型付き AST を持っているので前順にして、親の枠が子より外側に来る
（＝普通の debugger と同じ見え方になる）ようにした。

## 4. 旧 TinyCalc DAP とのパリティ

読み取り専用で回せた。資材は既存のビルド成果物
`unlaxer-parser/unlaxer-dsl/tinycalc-vscode/server-dist/tinycalc-lsp-server.jar`（2026-08-26 ビルド）を
scratch へ複製し、`java --enable-preview -cp <複製> org.unlaxer.tinycalc.generated.TinyCalcDapLauncher`
で起こした（**兄弟リポジトリには 1 byte も書いていない**。maven も走らせていない）。
ubnfc 側は同じ文法の IR（`ir/fixtures/unlaxer-dsl__tinycalc-vscode__grammar__tinycalc.ubnf.ir.json`）から
parser + LSP + DAP を scratch に生成して `DapMain` を起こした。
**両方とも本物の DAP（Content-Length + JSON）を stdio で話す同じ台本クライアント**で駆動している
（[`2026-09-24-dap-stage4/dapclient.py`](2026-09-24-dap-stage4/dapclient.py) /
[`drive.py`](2026-09-24-dap-stage4/drive.py)、生ログは同ディレクトリの `old*.json` / `new*.json`）。

入力（[`sample.tcalc`](2026-09-24-dap-stage4/sample.tcalc)）:

```
var x set 2;
1 + 2 * 3
```

台本: `initialize` → `launch`(stopOnEntry, 旧は `steppingMode=ast`) → `setBreakpoints`(2 行目) →
`configurationDone` → `threads` → `stackTrace`/`scopes`/`variables` → `next` ×4（別セッションで `stepIn` ×4）→ `evaluate`。

| | 旧（base 生成） | ubnfc |
|---|---|---|
| `setBreakpoints`（2 行目） | `verified: true` | `verified: true` |
| `threads` | `{id:1, name:"main"}` | `{id:1, name:"TinyCalc parse"}` |
| ステップ数 | **8**（反射で拾えた AST 節点） | **11**（IR の型から数えた AST 節点） |
| entry の `stackTrace` | 1 枠 `TinyCalcProgram (1/8)` `1:1`、`endLine`/`endColumn` **なし** | 1 枠 `TinyCalcProgram` `1:1`–`3:1` |
| entry の `scopes` | `Current AST Node` 1 つ（`variablesReference` は **固定 1**） | `AST node`（scope 観測がある位置では `Symbols` も） |
| entry の `variables` | `TinyCalcProgram="var x set 2;\n1 + 2 * 3"` / `runtimeMode=ast` / `astNodeCount=8` / `astCurrentNode` / `steppingMode` | `#type` / `#text` / `#range` ＋ **欄** `declarations=List(1)` / `expression=BinaryExpr`（入れ子は展開できる） |
| `next` ×4 | 8 節点を 1 つずつ辿る（`VarDecl` → `BinaryExpr` → …）。枠は常に 1 つ | 根で `next` は「根を step over」＝そのまま `terminated`（§3） |
| `stepIn` | **`Internal error`**（生成されない） | 4 段降りて枠が 1 → 2 → 3 → 4 → 5 本に増える |
| `evaluate` | `success:false` / `"Internal error."` | `success:false` / 「文法デバッガでは未対応。`EvaluatorBridge` を実装せよ」 |

**差の理由（全件）**

1. **枠の数**。旧は「現在のトークン / AST 節点」だけを 1 枠で見せる設計で、親子関係は出ない。
   ubnfc は前順ステップ列に `parent` を持たせているので、根までの鎖をそのまま枠にできる。
2. **ステップ数 8 vs 11**。旧は `Class.getMethods()` を舐めて子を探すので、
   アクセサ経由で辿れない節点が落ちる（並びも JVM 依存）。ubnfc は IR の型から全節点を数える。
   同じ入力・同じ文法で**列の長さが違う**のはこの探索方法の差で、ubnfc 側が AST の全体である。
3. **variables の中身**。旧は「デバッガのメタ情報」（`runtimeMode` / `astNodeCount`）を出す。
   ubnfc は**型付き AST の欄そのもの**を出す（`Optional` は `(none)`、`List` は入れ子）。
   どちらも**式の値ではない**（旧も base 生成では値を出さない）。
4. **`stepIn` / `stepOut`**。旧は仕様書（`unlaxer-dsl/specs/lsp-dap.md`）に「ステップイン/アウトを
   サポートする」と書いてあるが**実装が無い**（`DAPProtocolEmitter` は `next` しか生成しない）。
   実際に叩くと lsp4j の既定実装が走って `Internal error` になる。ubnfc は 3 つとも実装した。
5. **`endLine` / `endColumn`**。旧は設定しない。ubnfc は節点の終端を入れる。
6. **UTF-16**。旧の `stackTrace` は `currentAstSpan()[0]` を
   `codePointOffsetToStringOffset` に通さずに列へ渡している（行だけは変換している）。
   ubnfc は `Positions` を通すので BMP 外文字の後ろでも桁が合う。golden
   `non-bmp-nav.tiny` が `NumberVariableDeclarationExpr` を `1:30`（code point では 28）で固定している。

## 5. 拡張点 `EvaluatorBridge`（案 b の型だけ）

```java
public interface EvaluatorBridge {
    record NamedValue(String name, String value, String type, List<NamedValue> children) { }
    record Evaluation(String result, String type, List<NamedValue> children) { }

    default void onLaunch(String program, String text, Object root) { }
    default void onEnterNode(Object node) { }                       // 旧 onBeforeStep
    default void onExitNode(Object node) { }                        // 旧 onAfterStep
    default List<NamedValue> variables(Object node) { return List.of(); }  // 旧 runtimeVariables / additionalVariables
    default Optional<Evaluation> evaluate(String expression, Object node, String context) { return Optional.empty(); }
    default Optional<Evaluation> setVariable(String container, String name, String value, Object node) { return Optional.empty(); }

    EvaluatorBridge NOOP = new EvaluatorBridge() { };
    static EvaluatorBridge load(String className) { … }             // DapMain --evaluator <fqcn>
}
```

旧スタックは**継承**だった（`TinyExpressionP4DebugAdapterExt extends TinyExpressionP4DebugAdapter` が
`evaluate` / `setVariable` / `variables` を上書きし、`TinyExpressionDapRuntimeBridge` 経由で
手書きの `Calculator` / `CalculationContext` / `ExecutionBackend` を呼ぶ）。
ubnfc は**合成**にした（`new DebugAdapter(scanners, myBridge)`）。生成物を継承しないので、
再生成で著者の実装が壊れない。対応は生成される `EvaluatorBridge.java` の Javadoc に
tinyexpression の Ext/Bridge をどう移すかの例として書いてある。

`Optional.empty()` を返す（＝既定）と `evaluate` / `setVariable` は
`RequestFailed` + 「文法デバッガでは未対応。`EvaluatorBridge` を実装せよ」になる。
`initialize` も `supportsEvaluateForHovers` / `supportsSetVariable` を false で返すので、
**編集者が「値が出るはず」と誤解しない**。

**段階 4 のスコープ外**（issue #28 の記載どおり）: 評価器そのもの（案 a / 案 b の実装）、
`@eval` からの自動インタプリタ、変数スコープ・関数呼び出し・外部呼び出しの評価、
条件付きブレークポイント、watch 式。

## 6. VSIX

`contributes.breakpoints`（言語 id）と `contributes.debuggers`（`configurationAttributes` /
`initialConfigurations` / `configurationSnippets`）を P4 と UBNF の両方に足した。
起動は `extension.ts` の `DebugAdapterDescriptorFactory` が
`java [jvmArgs] -cp <同じ fat jar> <pkg>.lsp.dap.DapMain` を起こす
（LSP は `-jar`。旧スタックの `tinycalc-vscode` / `tinyexpression-p4-lsp-vscode` と同じ使い分け）。
`launch.json` は

```json
{ "type": "tinyexpression-p4", "request": "launch",
  "name": "TinyExpression P4 (ubnfc) grammar debugger",
  "program": "${file}", "stopOnEntry": true }
```

`scripts/build-vsix.sh --with-dap all` で両方の VSIX が組める（実測、1.86 MB / 1.69 MB）。
**`--with-dap` を付けずに組んだ VSIX には `DapMain` が入らない**ので、
デバッグを開始するとクラスが見つからず落ちる。この点は各例の README に書いた。
`code --install-extension` の実機確認はこのマシンに `code` が無いのでできていない（段階 3 と同じ）。
