# rule ごとの memo plan（再入判定、2026-09-24、issue #17）

PR #18（`docs/reports/2026-09-24-java-two-mode.md` §7）が「memo の要否は文法ごとに正反対」を実測した。
Operators 512 atom は **rule 呼出し 2,561 件すべて miss** で認識専用 0.221 → 0.180 ms（memo off が 0.81 倍）、
P4 complex は逆に memo を切ると 0.219 → **14.69 ms（67 倍）**。それでも front の memo plan は
**全 rule 本体を `cacheSuccess=true` / `cacheFailure=true`** にしていた。ここを規則ごとに決める。

## 結論（先に）

- **判定は「確定した経路上で同じ位置へ再入し得るか」**。memo が当たる必要条件は同じ `(rule, position)` が
  2 回評価されることで、位置が戻るのは巻戻しのときだけ。巻戻しで開始位置が一致し得る**兄弟の組**を列挙し、
  両側から同じ rule が**同じ相対位置**（開始 / 開始より後 / 終端の 3 値）で試され得るかを見る（D-057）。
- **Operators / Power / calc 系 / Cardinality / mixed-values は全 rule で memo が外れ、P4 の塔は残る**。
  P4 は 124 rule のうち 118 を保持し、落ちるのは `ImportDeclaration` と 4 つの型ヒント + `TypeHint` の 6 件。
- **動的に裏を取った**（§3）。旧計画（全 rule 本体 memo）の Rust parser に rule ごとの hit 計数を仕込み、
  corpus 106 文法 389 入力 + 24 fixture 文法（1 文法あたり 39〜187 入力、P4 は 16 ベンチ fixture を含む）を通した。
  **新計画が落とす 232 の rule 行はすべて hit 0**。総 hit 62,318 件は全部「残す」側に出ている。
- **Java: Operators 512 atom 認識専用 0.204 → 0.160 ms（0.78 倍）、割当 465,664 → 350,168 B**（＝実行時 memo off と同値）。
  **Rust: 0.176 → 0.115 ms（0.65 倍）**。**P4 は両 backend で悪化なし**（Java complex-x64 認識 15.38 → 15.03 ms、
  Rust 4.62 → 4.68 ms）で、plan が P4 の memo を保っていることは「実行時に memo を切ると complex が
  0.47 → 14.13 ms」で確認した。
- corpus は **Java Pass 1,310 / Rust Pass 1,292、Fail 0、系統別表は既存報告と byte 一致**。
  IR golden の差分は `plan.memo.entries` だけ（semantics / analysis / choices / operators / requiredFeatures は不変）。

## 1. 判定（criterion）

`crates/ubnfc-front/src/analysis/reentry.rs`。式グラフ上を `(式, 種別)` の 2 つ組で明示スタック走査する。
種別は相対位置の 3 値抽象：

| 種別 | 意味 |
|---|---|
| `Zero` | その式の**開始位置**で試される rule |
| `Pos` | 開始位置より**後**で試される rule |
| `Tail` | その式の**終了位置**で試される rule（末尾の 0 消費探索・反復の最後の失敗周回） |

`Zero` は Seq の先頭から `minConsume == 0` の要素を跨いで伝播し、`Choice` は全候補、`Repeat` は本体と
terminator、`Separated` は要素（要素が 0 消費可能なら区切りも）へ降りる。`RuleRef` は自分の rule を
記録してから本体へ降りる。`Tail` は Seq を末尾から 0 消費可能な間だけ遡り、`Optional` / `Repeat` /
`Separated` では本体の `Zero`（＝脱出時に同じ位置で試して失敗した分）も含む。先読みは 0 消費なので
`Tail` = 本体の `Zero`。

巻戻しで開始位置が一致し得る**兄弟の組**は次の 4 つだけを数える。

| 組 | 出どころ | 衝突条件 |
|---|---|---|
| 候補どうし | 巻戻す `Choice`（Predict が fallback 無しで確定するものは 1 候補しか評価しないので除く） | `Zero∩Zero` または `Pos∩Pos` |
| 0 消費要素とその後続 | `Seq` の `x_i..x_{j-1}` がすべて `minConsume == 0` | `Zero∩Zero` または `Pos∩Pos` |
| 直前の要素の終端と後続の先頭 | `Seq` の隣接（間の要素が 0 消費可能な間） | `Tail(x_i) ∩ Zero(x_j)` |
| 反復の周回境界・脱出 | `Repeat` の本体どうし・本体と terminator、`Separated` の要素と区切り | `Tail ∩ Zero` |

交わりに出てきた rule は「再入し得る」＝ memo を残す。加えて**保持側へ倒す**のは次の 3 つ。

- **先読みの中身**：必ず巻戻るので、その部分グラフから到達する rule は全部残す。
- **scope 効果・recovery・Extern token を含む本体**（`ExprAnalysis.effects` が非空）：判断材料が増えるので触らない。
- **走査予算（4,000 万歩）超過**：全 rule を再入し得る扱いにする。4,000 段の規則連鎖でも
  `deep_grammar.rs` の 512 KB スタックで走り切る（すべて明示スタック）。

落とした本体には `omissionProof` を `kind=unreachableRevisit` で付ける（`MemoEntryReason::ProvedOmission`）。
既存の部分式の省略（単一所有）はそのままで、本体が落ちた rule では説明文だけ
「rule 自体が同じ位置へ再入し得ないので本体 memo も省略した」に変わる。

### 例（なぜ Operators は当たらず P4 は当たるか）

- `Expression ::= Term { AddOp Term }` の `Seq[Term, Repeat(AddOp Term)]` は `Term` が非 nullable なので
  「同じ開始位置」の組にならない。効くのは境界だけで、`Tail(Term) = {MulOp}`（内側の反復が終端で
  `MulOp` を試して失敗する）と `Zero(Repeat(AddOp Term)) = {AddOp}` は交わらない。
- `Factor ::= NumericLiteral | '(' Expression ')'` の 2 候補は、候補 1 が `NumericLiteral@Zero` だけ、
  候補 2 は `'('` を消費した後なので `Expression`・`Term`・`Factor`・`NumericLiteral` を **`Pos`** でしか持たない。
  `Zero∩Zero = Pos∩Pos = ∅`。
- P4 の `Expression ::= NumberExpression | BooleanExpression | StringExpression | …` は、候補 1 が
  `NumberExpression → NumberTerm → NumberFactor → VariableRef` を `Zero` で持ち、候補 2 も
  `BooleanExpression → … → BooleanFactor → ComparisonExpression → NumberExpression` を `Zero` で持つので
  塔全体が交わる。`NumberFactor` の `TernaryExpression`（`'(' BooleanExpression '?' …`）と
  `'(' NumberExpression ')'` は `Pos∩Pos` で交わる。これが complex 1 parse あたり 464 hit（Java）の正体。

### 近似の範囲（正直に）

**over-run はモデル化していない**。ある兄弟が消費済み入力を越えて探索してから戻り、その先を別の兄弟が
踏み直す形は、相対位置の 3 値抽象では表せない。memo は最適化なので受理・AST・診断には影響せず
（§3.7 の「hit 時は効果を順序どおり 1 度だけ再生する」契約のまま）、誤って落としたときの代償は速度だけなので、
**動的な hit 計数（§3）で裏を取る**という組み立てにしている。逆向き（残しすぎ）は安全側で、実際
P4 では 118 rule を残しているが 55 入力で hit したのは 22 rule だけ。締めるのは別 issue。

## 3. 動的な裏取り（rule ごとの hit 計数）

`main` 末尾で `UBNFC_MEMO_HITS` のパスへ吐く。`expression` は memo キーの式 index なので、rule 本体の
index を引けば rule 別になる。**IR は旧計画（HEAD、全 rule 本体 memo）で生成**し、hit が起き得る形を

## 4. A/B（両 backend）

`taskset -c 26` に固定（同時進行の issue #19 が 28 を使っているので 26）。**before = HEAD の IR から生成、
after = 本 PR の IR から生成**。同じ機械・同じセッションで before / after を 2 周交互に測った。
