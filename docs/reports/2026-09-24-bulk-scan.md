## 1. front が証明すること（D-072）

対象は**式 1 つを根とする領域**（その式と、そこから規則参照をたどって到達する式すべて）。
次を全部満たすとき `plan.scans` に**追加の行**として載せる（既存のキーは 1 つも動かない）。

1. **終端だけでできている**。許す節点は `Seq` / `Group` / `Optional` / `Choice`（`longest` を除く） /
   `Repeat`（終端子なし・本体が 0 消費で成功し得ない） / 語境界なしの `Literal` / `Any` /
   単一 code point の token（`CHAR_RANGE` / `NEGATION` / `DIGIT` 等の組込み / `CodePointSet`） /
   規則参照。`Separated` / 先読み / `EOF` / `EMPTY` / `REGEX` / `UNTIL` / `Extern` は対象外。
2. **観測を 1 つも要求しない**。領域内のどの式にも capture site（`skip` でないもの）が無く、
   `@recovery` の適用位置が無く、trivia 挿入の境界が無い。領域が通る規則に mapping 型・
   scope 効果・`@recovery`・`@eval`・演算子・左再帰の記録が無い。
3. **子の mode を切り替えない**（`execution.childMode = inherit`）。走査は consumed mode のものだけ生成する。
4. **再帰しない**（規則の SCC が自己ループでない）。走査関数は再帰呼出しになるので、
   資源上限の契約（stack、issue #35 = D-070）を動かさないために対象から外す。
5. **回数が減る形である**。領域に反復が 1 つも無ければ畳んでも回数は変わらないので載せない。

根は**極大**に取る（親も畳めるなら親を根にする）。`@rightAssoc` + 暗黙 trivia の規則がある文法では、
AST の span を「配下の最初の token 事象」から取り直す（`significant_end`）ので**計画そのものを出さない**。

### 1.1 これで何が言えるか

領域の評価が外へ残すものは、上の条件から **(a) 成功したか (b) どこまで消費したか** の 2 つだけになる。
consumed mode では「どこまで」は `consumed` と `matched` の両方で、`advance::<false>` が必ず
`matched = consumed` に揃えるので、途中経過に関係なく**最後の位置だけ**で決まる。
よって「同じ位置から同じ終端列を同じ順序で試す関数」は、同じ受理と同じカーソルを返す。

**失敗したときの診断は D-023 が保証する**。fast session（`Session::<false>`）は display も主診断 DAG も
記録せず、解析が失敗（または末尾入力・recovery・scope 診断・mapping / 資源診断）になったら
生成 driver が**同じ入力を診断 session で最初から解析し直す**。走査は fast session でしか走らないので、
**返される診断は必ず非最適化経路のもの**である。「失敗位置は走査が止まった位置」という一文は、
その位置が公開されるという意味ではなく、fast session の `Step` がそこで失敗すればよいという意味である。

### 1.2 一括走査の表（`charClassRepetition`）

反復 `{ X }` の本体 `X` が順序付き選択のとき、候補 k がクラス `C_k` なら
**`C_k \ ∪_{j<k} mayStart(候補 j)`** の文字は「1 文字で候補 k に確定して 1 code point だけ消費する」。
`mayStart` は先頭文字の**必要条件の上界**（`Facts::chars`）なので、その外の文字では先行候補は
1 文字も消費できずに失敗する（0 消費成功もしない: nullable な候補は除いてある）。
この集合を **ASCII 128 bit の bitset + U+0080 以上の閉区間**として plan に載せる。

候補が**全部**単一 code point のクラスなら表は本体の成功をすべて覆う（`complete: true`）ので、
backend は表が尽きた位置で本体を 1 度も呼ばずに反復を終えてよい。覆わないとき（JSON の
`Char ::= Escape | SAFE_*` のように 2 文字以上の候補が混ざるとき）は、表が尽きたところで
本体の走査へ 1 度だけ落ちる。

JSON での中身:

| 式 | 表 | `complete` |
|---|---|---|
| `Ws ::= { ' ' \| '\t' \| '\n' \| '\r' }` の反復 | `\t \n \r ' '` | true |
| `String` の `{ Char }` | U+0020..U+0021 ∪ U+0023..U+005B ∪ U+005D..U+D7FF ∪ U+E000..U+10FFFF（`"` と `\` を除く） | false（`Escape` が残る） |
| `Escape` の `HEX{4}` | `0-9 A-F a-f` | true |
| `Int` / `Frac` / `Exp` の `{ DIGIT }` / `DIGIT+` | `0-9` | true |

### 1.3 「終端だけの列」は DFA ではなく静的再生にした

issue は `Number ::= [ '-' ] Int [ Frac ] [ Exp ]` を `analysis/regex.rs` の leftmost-first DFA へ
落とすことを挙げていた。**採らなかった。**理由は等価性の証明のほうが高くつくからである。

PEG の `[ X ]` は `X / ε` の**確定した**選択で、`{ X }` は**貪欲で後戻りしない**。
`Int ::= ZERO | ONENINE { DIGIT }` に `0123` を与えると PEG は `Int = "0"` で止まり、
続く `[ Frac ]` が `1` で失敗して `Number = "0"` を返す。leftmost-first DFA は
`REGEX` token の意味論（最長候補を更新しながら進む。`analysis/regex.rs` の
`anchoredAtStart` + 受理更新）なので、同じ入力で `"0"` ではなく別の長さを採り得る。
両者が一致するのは「どの optional / 反復も、その継続と先頭集合が交わらない」形に限られ、
その条件を front で証明して初めて DFA が使える。

代わりに採ったのは**同じ再帰下降をそのまま静的に再生する**ことである。生成するのは
式ごとの `fn s{i}(&self, p: usize) -> Option<usize>`（消費 byte 数）だけで、
`Step` / 事象 arena / 診断 / `mark` / transaction / memo を 1 つも通らない。
構造が元と同じなので **PEG 意味論との一致は構成上自明**であり、証明の負債が残らない。
反復には §1.2 の表引きループが入るので、文字クラスの連なりでは DFA と同じ「1 byte 1 判定」になる。
DFA 化は、上の非交差条件を front が証明できるようになったときの別 issue にする。

### 1.4 backend が走査へ入る条件

`b{i}_c` の先頭に置く分岐は次の 5 つが全部成り立つときだけ真になる。

```
self.options.scan && !DIAG && !self.options.lexical && !self.options.occurrences && !out.state.invert
```

- `options.scan` — 参照経路へ戻す脱出口（`predict` / `factor` と同じ作法）。既定 true。
- `!DIAG` — §1.1。
- `!lexical && !occurrences` — 出現表は領域内の rule / token 事象を**数える**
  （`rule_completion_order` は rule 事象の完了順）。要求されているときは畳まない。
- `!invert` — `Not` の下では終端の意味が反転する（`primitive` の `state.invert`）。

事象は「走査した範囲ちょうど 1 件の token 事象」に畳む。領域の終端は隙間なく範囲を敷き詰めるので、
`selected_extent`（配下の最初の token の開始と最後の token の終了）は同じ span になる。
消費が 0 のときは事象を作らない（参照経路も作らない）。

### 1.5 観測が変わり得る唯一の場所 — 資源上限

走査は**資源を減らす方向にしか動かない**（事象 arena の行数・memo の行数・診断の行数）。
そのため「参照経路では上限に当たって `Resource` 診断で失敗するが、走査経路では成功する」ことが
起こり得る。実測でも既定の上限（`arena_entries = 2,000,000`）のまま json-1m を typed AST で
解析すると、走査 off は `arena budget exceeded` → 診断 session で `diagnostic budget exceeded` になり、
走査 on は成功する（§3.1）。**逆向き（走査 on だけが上限に当たる）は起こらない。**
`predict` / `factor` も同じ性質を持つ（候補を呼ばないぶん診断の行が減る）ので、新しい種類の差ではない。
上限を上げれば差は消える（§3.1 の 303 件は上限を上げて 0 件）。

### 3.1 JSON の全数比較（走査 on / off）

再現（commit していない一時計測。生成 crate に 1 本の bin を足すだけ）:

# $OUT に scan: true / false の 2 回を比較する bin を置いて実行する

### 3.2 差分ファジングの in-backend A/B

`crates/ubnfc-fuzz` の campaign に、**同じ Rust backend を `options.scan` だけ変えて 2 度走らせる
比較**を足した（driver protocol に任意キー `options.scan` を追加。あるときは fast mode で解析する）。
`Summary` に `scanComparisons` / `scanFindings` が増える。

**この比較が観測の全面を覆う理由**: 走査は fast session でしか走らず、fast session が
失敗・末尾入力・recovery・scope 診断・mapping / 資源診断のいずれかを返した解析は、
driver が同じ入力を診断 session で解析し直す（D-023）。したがって走査が公開される観測を
変え得るのは「fast session が成功したまま返した解析」だけで、それがこの A/B の対象そのものである。
なお、走査が**誤って失敗**した場合も再解析で結果は正しくなるが、`hints`（成功解析の投機的失敗）が
再解析の有無で変わるので、この A/B で検出できる。

固定 seed の campaign（`cargo test -p ubnfc-fuzz`）は 5 本とも緑で、走査 on / off の差は
**0 件**（`scanFindings` が空であることを各テストが assert する。要求する最低比較数は
30 / 20 / 20 / 10 件）。CLI で同じ設定を回すと
`ubnfc-fuzz --seeds 4 --start-seed 4001 --inputs 10` で
**`scanComparisons: 40` / `scanFindings: []`**（`comparisons: 40` と同数＝全入力を 2 度走らせている）。
生成器の乱択文法は `@whitespace` の有無・`NEGATION` / `CHAR_RANGE` / 補助面の token・
語境界つきリテラル・左再帰・`@recovery` を含む帯を回すので、走査が付く形（終端だけの反復）と
付かない形（capture / mapping / trivia を含む反復）の両方を踏む。

## 5. Java backend（issue #69 へ）

**Java backend には本 PR の実装は入っていない**（本 PR は `ubnfc-java/**` を 1 行も触らない）。
front の計画（`plan.scans`）は共有なので、Java 側に必要なのは次の 4 つだけである。

1. `plan.scans` の `root: true` の式に対し、`Session` を通さない
   `private int scan<N>(int p)`（消費 code point 数、失敗は `-1`）を **`JavaEmitter` が生成**する。
   構造は `Seq` / `Choice` / `Optional` / `Repeat` / `Literal` / 単一 code point token の再帰下降で、
   Rust の `crates/ubnfc-rust/src/scan.rs` と 1 対 1。
2. `class` が付いた反復には bitset（`long` 2 本）＋非 ASCII 区間の内側ループを出す。
   Java は `String` が UTF-16 なので、走査の単位は **`codePointAt` + `charCount`** にする
   （既存の終端照合と同じ。`04-cursor-and-diagnostics-contract.md` §2 の「単位は code point」）。
   `complete: true` なら表が尽きた位置で本体を呼ばない。
3. 入る条件は Rust と同じ 5 つ。Java は `Session.diag` / `options.lexical()` / `occ` / `invertMatch`
   に対応する旗を既に持っている（D-023 / D-035 / D-056 / D-059）。`-Dubnfc.scan=false` で参照経路へ戻す。
4. 事象は「走査した範囲ちょうど 1 件の token 出現」に畳む。Java の `Match` 木では
   `Session.token(...)` 1 回に相当する。

受け入れ条件は「JSON 1 MB の認識・AST が Java でも同じ比で速くなること」「corpus Java Pass 1,310 /
Fail 0」「`FactorEquivalenceTest` と同じ形の `ScanEquivalenceTest`（走査 on / off × 認識 / AST ×
出現表あり / なし）」。

## 6. 申し送り

1. **暗黙 trivia を持つ反復は畳めない**。`{ X Y }` のように周回の中に区切りの読み飛ばしが入る形は
   条件 2 で落ちる（`{ X }` のように本体が 1 要素なら挿入は外側の列の境界に付くので畳める）。
   読み飛ばしは `skip_{policy}` という純関数なので走査へ入れられるはずだが、
   line comment が consumed mode で `matched` を先へ送る（`tokens.rs` の `out.state.matched=end`）
   ぶんの再現が要る。別 issue。
2. **`REGEX` token を走査に入れる**。DFA は既に plan にあるので、`s{i}` から表を回すだけで入る。
3. **`Separated` と先読み**。`Separated` は反復と同じ形なので入れられる。先読みは
   `matchOnly` mode の走査が要る（本 PR は consumed mode だけ生成している）。
4. **終端だけの列の DFA 化**（§1.3）。非交差条件を front が証明できるようになったら。
5. **Java 移植**（§5、issue #69）。
